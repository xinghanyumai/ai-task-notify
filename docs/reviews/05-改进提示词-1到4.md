## 六、后续改进提示词

### 6.0 怎么用：顺序、依赖、粘贴方式

**粘贴方式**：整段复制（含开头的 `使用 @skill:"..."` 行）到新对话第一条消息。
skill 行必须原样保留 —— 那行的作用是让下一个 agent 先加载对应方法论，
而不是靠它自己的通用直觉来干活。

**不要一次贴多条**。每条提示词都带验收标准，一条做完验收完再做下一条。
同时开多个 agent 改同一个仓库，会产生互相覆盖的冲突。

**执行顺序（有硬依赖，不能随意调换）**：

```
提示词 1  止血 ──────────── ✅ 已完成
   │
   ├─ 提示词 5  过度设计审计 ──── 只读，可随时并行，建议先跑（先瘦身再测试，少写测试）
   │
   ├─ 提示词 8  文档重构 ──────── 会重写 README
   │        ↑ 所以 P0-5 / P0-6 的 README 修复不要单独做，
   │          直接并进这条，否则修完被重写一遍
   │
   ├─ 提示词 2  TDD 测试体系 ──── 必须先于 3 和 6
   │     │
   │     ├─ 提示词 3  CI ──────── 依赖 2（CI 要有测试可跑）
   │     └─ 提示词 6  拆 channels ── 依赖 2（没有测试就重构 = 赌博）
   │
   ├─ 提示词 4  五轴审查 ──────── 建议放在 6 之后（拆完再审查，避免重复提同一批问题）
   │
   └─ 提示词 7  设计复核 ──────── 完全独立，随时可跑，不阻塞任何其他项
```

**每条做完必须自己复核一遍**，不要只信 agent 的「已完成」。上一轮的教训很具体：
它报「6 项全过」，实际 `LICENSE` 还是 `<YOUR NAME HERE>` 占位符。
复核方式就是提示词末尾那几行验收命令，逐条跑、逐条贴输出。

**三条通用复核句式**（粘在任意提示词末尾都能用）：

```
做完后逐条贴实测输出，不要只说「已完成」。
任何一条不达标，如实说明卡在哪，不要用「基本满足」「已处理」这类模糊表述。
如果你改了提示词范围外的文件，单独列出来说明为什么必须改。

```
你是本项目（D:\Code\Work buddy 通知，一个 WorkBuddy/CodeBuddy 任务通知工具）的
发布工程师。目标：把当前目录变成一个可以安全公开的 git 仓库。

- 没有 git 仓库
- config.json 含真实 appid / appsecret / openid
- state/token_cache.json 含真实 access_token

   所有凭证字段为空字符串，通道 enabled 全为 false，只保留 log 通道为 true。

最后明确告诉我：appsecret 必须去测试号后台重置，删文件不等于止血。
