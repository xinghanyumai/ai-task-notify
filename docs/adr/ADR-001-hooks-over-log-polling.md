# ADR-001：挂在 hooks 上，不轮询日志

- 状态：已采纳
- 日期：2026-10

## 背景

WorkBuddy 和 CodeBuddy 都是「跑完一轮就停下等你下一句」的形态。要推通知，第一件事是
判断这一轮什么时候结束。

能观察到的信号有三个：窗口内容、会话日志文件、宿主生命周期事件。前两个都要靠推断，
第三个是宿主主动告诉你的。

## 决策

挂在宿主的 hooks 上。宿主在 `Stop`、`StopFailure`、`PermissionRequest` 这些节点
回调 `hook.py`，把事件 JSON 通过 stdin 交过来。

两个宿主的 hooks 与 Claude Code 同构，一套代码同时服务两边，只靠 `--app` 参数
区分显示名。安装器往两个 `settings.json` 各写 9 个事件。

宿主能发的原始事件有 27 个，但用户只关心五件事。中间加一层语义归类，
把 27 个事件收敛成 `task_done`、`task_failed`、`need_input`、`tool_failed`、
`session_start/end` 五种语义。

## 代价

依赖宿主保持 hooks 的行为不变。事件名和 payload 结构以宿主版本为准，升级后如果改了，
通知会静默失效。缓解手段是 `selftest.py --status` 能看挂载状态，但它看不出事件名变了。

改完 hooks 必须完全重启宿主，因为配置在启动时读取并缓存。WorkBuddy 点关闭按钮
只是隐藏到托盘，这一步很多人会漏。

hook 是同步执行的，宿主会等它返回。所以这个进程不能有任何阻塞操作，
整条链路的 fail-open 设计（吞异常、不写 stdout、stdin 读 3 秒超时）都是这个约束逼出来的。

两个宿主就是两份配置。安装器要处理 `settings.json` 里别人的 hook 条目，
合并而不是覆盖，改动前还要备份。

## 备选方案

轮询 `transcript.jsonl`。会话日志里什么都有，但「这一轮结束了」这件事得自己推断：
看最后一条记录的类型、看有没有工具调用在飞、看时间戳间隔。每条规则都会误判，
而且延迟取决于轮询周期。放弃。

定时截图加 OCR。识别窗口里的状态文字。脆弱，耗资源，中文识别还不准。
缩放比例一变就全乱。放弃。

盯进程。等 `python.exe` 退出。但 agent 一轮结束时进程不退，它只是回到输入提示符。
这个信号和「任务完成」根本不对应。放弃。

宿主插件 API。如果宿主提供进程内的扩展点，能拿到更丰富的上下文。当时没有查文档，
hooks 已经够用，而且它和 Claude Code 同构这件事本身有额外价值（生态里的用法能直接借鉴）。
