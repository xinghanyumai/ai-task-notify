# ADR-002：stdin 管道投递，不落盘

- 状态：已采纳
- 日期：2026-10

## 背景

`hook.py` 拿到事件 JSON 之后要交给后台进程处理，自己立刻退出。交接方式有几种，
最自然的是写个临时文件，子进程起来读。

这条路径在每次任务结束时都会走一遍，所以它的固定开销直接决定 hook 端耗时。
而 hook 是同步的，宿主在等它返回。

## 决策

`subprocess.Popen` 起 `dispatch.py`，`stdin=subprocess.PIPE`，把 JSON 直接写进管道，
关掉 stdin，父进程退出。全程不落盘。

子进程用 `DETACHED_PROCESS | CREATE_NO_WINDOW` 起，宿主退出不会带走它。

## 代价

事件不再有任何持久化痕迹。后台进程如果启动失败，这条通知就没了，只能靠日志发现。
临时文件方案至少能事后翻出来看。

调试变麻烦。想看看 hook 到底投递了什么，得在 `dispatch.py` 里加日志，
不能像临时文件那样直接 cat 一眼。

管道有容量上限。事件 JSON 目前都是几 KB，离 64KB 的管道缓冲区还远，但如果哪天
宿主往 payload 里塞了超大的 transcript 摘要，写管道会阻塞。缓解办法是
`dispatch.py` 一进来就把 stdin 读完再干别的，现在的实现就是这样。

父进程退出后管道会 EOF。子进程必须在这之前把数据读走，实测在 Windows 上
数据已经在缓冲区里，父进程退出不影响读取。这个行为依赖平台实现，
所以 `hook.py` 里对 stdin 的写入是同步完成的，写完才退出。

## 备选方案

临时文件。实测这台机器上删除一个文件约 700ms，删除操作会被安全软件拦一下。
一个事件要「创建加删除」两次文件操作，等于每条通知白等 1.4 秒。
实测端到端 2.02s，换成管道后 0.07s。这就是换掉它的唯一原因，也是唯一理由。

命名管道。不用落盘，但要处理命名冲突、清理残留、子进程没起来时的阻塞。
为了省一次 `Popen` 的复杂度引入另一套 IPC，不划算。

本地 socket 或 HTTP。要占端口，要处理端口冲突，要防别的进程连上来。
一个单用户小工具不值得。

不拆，hook 里直接发 HTTP。网络慢 8 秒，你的对话就卡 8 秒。这条最先被否掉。
