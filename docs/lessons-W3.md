## 2. 六条教训

### 2.1 同一段代码被改三次，就该换结构，不要改第四次

**症状**：每轮都能修对，每轮都只修了一个实例。
**判据**：`git log -L <起始行>,<结束行>:<文件>` 数一下被改过几次。三次以上，停下来。
**为什么三次**：一次是需求，两次是调整，三次说明**这层的形状**和需求对不上。

已固化成 `README.md` §2.1 第 7 条。

### 2.2 验收的最小单位要不断升级

```
一个 bug   →   一条断言   →   一个矩阵
（W3.1–W3.4）  （W3.5 收口审计）  （W3.8b）
```

| 单位 | 一次能抓到 | 局限 |
|---|---|---|
| 一个 bug | 1 处 | 只能修我看到的 |
| 一条断言 | W3.5 一次捞 7 处（含 2 处数据丢失） | 只能覆盖我想到的维度 |
| 一个矩阵 | 30 个组合 + 7 个历史 bug 全部复现 | 需要先定义状态空间 |

**每次升级都因为上一级漏了东西。** 单点修漏了「没人会去查的地方」，
断言审计漏了「时间维度」，矩阵漏了「recent 列」——最后这个是**工具发现的**，
不是我想到的。

### 2.3 声明了 ≠ 做到了

W3.5 在 `architecture.md` 写了一张很漂亮的表：

| 消费者 | 测试记录 |
|---|---|
| 列表的「最后发送时间」 | 用 |
| 侧栏的成败判定 | 不用 |

**写得对，但做不到**——`_last_send_times()` 返回一条记录，`time` 和 `ok`
在同一个槽里，两个消费者要的答案相反，物理上不可能同时满足。

后果：侧栏绿「送到你手机」+ 通道列表红「最近一次失败」，**同一屏**。

**判据**：写完「这里故意不对称」，去数据结构里找**两个**槽位。只有一个，就是没做到。

已固化成 `README.md` §2.1 第 6 条。

### 2.4 期望值必须手算，不能用代码生成

矩阵里的期望值，如果是「跑一遍记下结果」，那它记录的是**当前行为**，不是**正确行为**。
代码错了，期望值跟着错，矩阵永远绿。

**这也是矩阵完整性的检验方式**：拿旧代码跑同一批数据，七个历史 bug 必须红。
某一格不红 = 那格没覆盖到。`recent` 列就是这么被发现的——我写表时凭记忆列出口，漏了一个；
工具不凭记忆，它只看红不红。

### 2.5 改判据，不改被检查对象

W3.8a 有件事：`grep -rn "notify-" wbn/` 命中了 `theme.py` 的**注释**，
执行者把注释里的文件名改了，让 grep 干净。

**动机是错的。** grep 的本意是「找出读日志的代码」，注释不是代码。
正确做法是修判据（加 `--include="*.py"` 并排除注释），不是改被检查对象——
因为下一个人写注释时又会命中。

**这条和「放水」的区别**：修判据是为了让判据更准，改被检查对象是为了让判据闭嘴。

### 2.6 清单式任务书有天花板

七轮任务书都是「修这三处」，执行者只能覆盖这三处。我没想到的他不会碰；
我列错的（W3.1 写「三种按钮」，实际只有两种）他只能按错的做。

W3.8b 换成「30 格 + 旧代码必须全红」，执行者**补了我两处漏洞**：
`recent` 列、T1 要放两种测试写法。这两处我压根没想到。

**任务书要给性质，不要给清单。** 清单只能覆盖写清单的人想到的东西。

## 3. 我自己犯的错（PM 侧）

| 错误 | 后果 |
|---|---|
| 用「哪个数字错了就修哪个」验收 | 同一病换五种形状，修了五轮 |
| 收口审计只做一次，之后又回到清单式 | W3.6 / W3.7 又各修一轮 |
| 18 条断言没有时间维度 | 漏掉跨天累加和零点失忆 |
| 任务书里的期望值也会错 | 脏数据我写 `ok=1 fail=1`，实际 `2/2`——漏数的那条恰好是 W3.3 那个病 |
| 宣布「冻结」三次，破例三次 | 每次都有正当理由，但「冻结」这个词因此贬值 |

最后一条最值得记：**冻结要有例外条款，但例外必须写清「为什么不能等」**。
W3.6 和 W3.7 的例外理由都成立（数据源选错 / 声明与实现不符），
但如果没有那个条款，我会在「守住承诺」和「修对的东西」之间二选一，
而正确的选择永远是后者——那就等于冻结无效。

## 4. 下次遇到同类问题怎么做

```
1. 数改动次数
   git log -L 数同一段代码被改过几次。三次以上 → 跳到 3。

2. 修
   修完立刻问：这个修改是「加一个 if」还是「改一个结构」？
   全是加 if → 下一次还会漏。

3. 换结构
   先抽中间表示（不可变数据 + 命名方法），口径从「循环里的 if」
   变成「方法名」。这一步不许改行为——旧测试一个不动全绿才算忠实。

4. 穷举
   列出状态空间的维度，展开成矩阵。
   期望值手算写死。某一格在旧代码上不红 → 那格没覆盖到。

5. 收口
   定义收敛条件（几条、怎么验），全过才算完。
   之后这一层：先加一格用例，红了才允许改代码。
```

## 5. W3 之后这一层的规矩

`logs.py` / `stats()` / `chain_sentence()` / `channel_state()` /
`delivery_health()` / `_last_send_times()` **语义冻结**。

W4 起发现这一层还有问题，处理方式是：

1. 先在矩阵里加一格能复现的用例（**加用例，不加 if**）；
2. 用例红了才允许改；
3. 改完用例必须变绿，且 30 格其余全绿。

**不允许「先修代码再补测试」。** 七轮里每轮都是先修后补，
所以补的测试只能证明「这个具体场景修好了」，证明不了「这类场景都不会再错」。
