# 性能：首次进入一页的钱花在哪

这份文档回答一个问题：**用户第一次点进某一页要等多久，那笔钱能不能省。**

结论先放这里（**改版后**的数字，第 4 步实测）：

| 口径 | 改版前 | 改版后 | 含义 |
|---|---|---|---|
| 单页隔离（每页一个全新进程） | 123 / 516 / 1410 / 268 ms | **27 / 355 / 452 / 43 ms** | 这一页自己有多贵 |
| **一个进程里顺序建完 4 页** | **3925 ms** | **550 – 1173 ms** | **启动层真正要盖住的钱** |

按 P1 第 5.1 节的三条路线，改版前 >3000ms 落在**路线 C（骨架屏）**；
改版后两个口径都 ≤ 2000ms，落在**路线 A（全量预热）**，启动层实测 2.0 秒交接。
选路线的完整推理见第四节。

第 0 步的 profile（第一、二节）是**改版前**的记录，留着是因为它解释了
「为什么第 3 步要那样改」——但不要再拿它的绝对数字当现状。

---

## 一、先修尺子（0a）

`bench_ui.py` 的 `_cold_ms` 原来是**单次采样 + 同进程**，两个毛病：

1. **单次采样。** 同一页连跑 5 次：`1195 / 128 / 101 / 147 / 85` ms，10 倍差距。
   头一次要付操作系统读 `.py`、加载字体文件的冷缓存钱。
2. **同进程。** 一页建完就进 `_pages` 缓存，第二次量到的是缓存命中（2~10ms），
   差两个数量级；强行踢掉缓存重建，字体也已栅格化，量到的是稳态重建。

改成：**跨进程 + 首样本丢弃 + median-of-3**，并明确它是「冷启动路径」。
阈值常量 `BUDGET_*` 一个没动。

> 这不算「改尺子」。改**判据**（阈值、通过标准）才是禁止的；改**测量方法**
> 是必须做的，否则数据不可信。单独提交，commit message 写明「只改测量方法，阈值未动」。

## 二、钱花在哪（0b）

### 2.1 单页成本（median-of-7，每样本一个全新进程）

| 页 | min | median | max | 7 个样本 |
|---|---|---|---|---|
| triggers | 97 | **123** | 133 | 97 / 131 / 133 / 127 / 123 / 97 / 104 |
| template | 336 | **516** | 556 | 336 / 516 / 536 / 550 / 509 / 472 / 556 |
| status | 1118 | **1410** | 1440 | 1118 / 1440 / 1410 / 1430 / 1348 / 1432 / 1322 |
| guide | 205 | **268** | 295 | 214 / 295 / 268 / 288 / 282 / 205 / 232 |

合计 2389ms。**status 一个人占 59%**，是第二名的 2.7 倍。

### 2.2 顺序口径：3.8–3.9 秒

一个进程里 `App()` 之后依次建 4 页：

```
median 3925 ms    样本 3436 / 3954 / 3925 / 3515 / 4041
逐页       triggers 1080   template 757   status 784   guide 1177
```

**这个数字才是启动层要盖住的**——启动层就是在同一个进程里顺序建页。

它比「单页隔离相加」还多 1.5 秒。查过了，**不是累积效应**：把 5 页都建起来之后
再重建同一页，反而更快（381 / 243 / 302 ms，对比首次 868ms）。差异来自
「进程里第一次建某类控件」的一次性成本，以及单页隔离测量本身偏乐观。

> 口径不一致这件事本身要记一笔：同一个 `guide` 页，隔离口径 268ms、
> 顺序口径 1177ms、同进程二次重建 350ms。三个数都能量出来，说明**现有测量
> 方法对「页」的定义还不够稳**。第 4 步重测时要先把这个口径钉死，
> 否则路线 A/B/C 会选错。

### 2.3 热点一：字体实例化（100–190ms / 字号）

逐次记录 `measure()` 的耗时：

| 字体 | 次数 | 第一次 | 之后中位 |
|---|---|---|---|
| Segoe UI Variable Text 10 | 8 | **11.8 ms** | 0.07 ms |
| Segoe UI Variable Text 8 | 17 | **115.5 ms** | 0.04 ms |
| Segoe UI Variable Text 9 | 32 | **188.9 ms** | 0.07 ms |

**第一次用某个字号要 12–189ms，之后每次 0.07ms。** 差 2000 倍。

这是「Tk 裸建控件 0.27ms/个、一页约 200 个控件 ≈ 54ms，而实测 1200–1723ms
是 22–32 倍」的主要解释：那 22 倍里有一大半不是建控件，是**在等 Tk 实例化字体**。

### 2.4 字体预热是死路（复验）

P1 提示词里把「预热字体组合」列为上一轮已排除的死路。**复验结论：确实是死路，
而且比不预热更糟。**

| 页 | 不预热 | 全字号预热 | 差 |
|---|---|---|---|
| triggers | 102 ms | 1163 ms | −1040% |
| template | 546 ms | 851 ms | −56% |
| status | 1451 ms | 1333 ms | +8% |
| guide | 290 ms | 1492 ms | −415% |
| **合计** | **2389 ms** | **4839 ms** | **−103%** |

原因很直白：预热 7 个字号 × 2 个字重 = 14 个组合，每个约 150ms，**预热本身要 2 秒**，
省下的远不够付的。只有 status 一页赚了 8%（它自己就要用 3 个字号）。

**这条对 P1 的直接含义**：字号层级从 7 档收到 4 档，不只是排版纪律，
**本身就是性能优化**——每少一个字号就少一次 100–190ms 的实例化。

### 2.5 热点二：status 页的 `elide`

`elide()` 用二分查找把文字裁到指定宽度，每次迭代都调一次 `measure()`。
status 页 40 次 `measure` 全部来自它（36 次 `elide`），占该页 **50%**（413ms / 830ms）。

其余三页：triggers 8 次 measure（占 19%），template / guide **0 次**。

改法（P1 重写时做）：`elide` 只在文字确实超宽时才二分，且用「按平均字宽估算
切点 + 一次校正」代替纯二分，把 5 次 `measure` 降到 1–2 次。

### 2.6 热点三：`Timeline` 整表重绘

status 页的 `Timeline.reveal()` 在 240ms 里逐帧重绘**整张表**（每帧都
`delete("all")` + 重画全部行）。cProfile 里 `_paint` 单次 560ms。

P1 第 4.1 节明确「最新一条在顶部，**不带入场动画**」——这条要求顺带把这笔钱
整个去掉：`reveal()` 删掉，`set_rows` 之后只画一次。

### 2.7 排除项：GC 不是元凶

| 页 | 开 GC | 关 GC | 差 |
|---|---|---|---|
| triggers | 138 ms | 125 ms | −9% |
| template | 506 ms | 560 ms | +11% |
| status | 1574 ms | 1506 ms | −4% |
| guide | 275 ms | 238 ms | −14% |

全在噪声内。`gc.freeze()` 之类的方向不用再试。

## 三、改版后的实测（第 4 步）

第 0 步的结论是「版式一动，这些数字就作废」。第 3 步把 5 页全部重画完之后，
按**同样的两种口径**重测了一遍。

### 3.1 单页隔离口径（`bench_ui.py --runs 5`，跨进程 median-of-5）

| 页 | 第 1 次 | 第 2 次 | 预算 | 改版前（median-of-7） | 倍数 |
|---|---|---|---|---|---|
| 启动建界面 | 206 | 234 | 400 | 255–305 | 持平 |
| triggers | 31.6 | 26.9 | 900 | 123 | **4.5×** |
| template | 327 | 355 | 900 | 516 | **1.5×** |
| status | 452 | 412 | 900 | 1410 | **3.2×** |
| guide | 42.4 | 42.6 | 900 | 268 | **6.3×** |
| **4 页合计** | **854** | **837** | — | **2389** | **2.8×** |
| 切页 | 1.0–14.1 | — | 100 | 2–4 | 持平 |
| 整页重建（切主题） | 244 | 251 | 300 | 56–61 | 变慢（见 3.3） |

两次独立运行差 2%，可以当判据用了。

### 3.2 顺序口径（一个进程里 `App()` 之后依次建 4 页，median-of-5）

这才是启动层 T1 要盖住的钱（2.2 定义的口径）。

| 收尾方式 | 4 页合计 | 逐页（一次样本） |
|---|---|---|
| `update_idletasks()`（只布局） | **550 ms** | 30 / 354 / 45 / 46 |
| `update()`（跑完事件循环，含 after 回调） | **1173 ms** | 310 / 515 / 68 / 281 |

两个数差一倍，差在**进场动画**上：每建一页 `_enter_anim` 会排一个 160ms 的
`slide_in`，`update()` 会把它们跑完，`update_idletasks()` 不跑。真实用户
在启动层后面看到的是后者（窗口还没映射，动画跑了也看不见），但**选路线时
按大的那个算**——宁可保守。

改版前同一口径是 **3925 ms**（样本 3436 / 3954 / 3925 / 3515 / 4041），
现在是 550–1173 ms。

### 3.3 为什么能快这么多（对账 2.3–2.6）

| 项 | 2.x 的估算 | 实际做法 | 结果 |
|---|---|---|---|
| 字号 7 档 → 4 档 | 省 300–500ms | `theme.TS` 收成 title/section/body/small 四级 | 每次启动少实例化 3 个字号 |
| `elide` 纯二分 | 省 300ms | `measure()` 加 `(font, text)` 缓存；`elide` 先测全长，超宽才二分 | status 页从 1410 → 452 |
| `Timeline` 逐帧重绘 | 省 500ms | `reveal()` 改成空实现，`set_rows` 后只画一次 | 这笔钱整个消失 |
| 去卡片化（本轮新增的发现） | 未估算 | v1 每个区块一张 `Card`（Canvas + 阴影层 + 圆角重绘），一页 5–8 张 | **最大的一笔**：triggers 123 → 31，guide 268 → 42 |

第 0 步把「一页 200 个控件、裸建 54ms，实测 1200–1723ms 是 22–32 倍」记成
「22 倍的放大就是浪费」。现在回头看，那 22 倍里最大的一块不是字体，
是 **Canvas 自绘的卡片**：每张卡要建一个 Canvas、画阴影两层、画圆角矩形、
再绑 `<Configure>` 重画。v2 全站卡片数量 = 0，这笔钱跟着没了。

### 3.4 一处变慢：整页重建（切主题）244–251ms

预算 300ms，还在内，但比改版前的 56–61ms 慢了 4 倍。

原因是重建路径变长了：现在 `_rebuild()` 除了重建控件，还要 `_reset_pages()`
清缓存、再重建当前页（v1 切主题后内容区是空的，等于**没重建内容**，所以快）。
这一条是**修好 D1 的代价**，不是性能退步：以前那个 56ms 换来的是一个空白页。

## 四、路线选择：A · 全量预热

按 5.1 的表格，判据是「4 页合计」：

| 路线 | 触发条件 | 本次实测 |
|---|---|---|
| **A · 全量预热** | ≤ 2000ms | **550–1173ms ✓** |
| B · 部分预热 | 2000–3000ms | — |
| C · 骨架屏 | > 3000ms | — |

**落进 A，而且是大幅落进。** 两个口径（550 / 1173）都远低于 2000ms，
所以这个选择对「用哪个口径」不敏感——这是最让人放心的地方。

按 5.1 的要求，选 A 不需要降 P2 的预算，`BUDGET_COLD = 900` 原样保留，
四页现在全部在内（最慢的 status 452ms）。

### 4.1 启动层时间轴（实测，不是设计值）

`wbn/splash.py` + `ui._boot()`，三次独立运行：

| 阶段 | 实测 | 屏幕 | 后台 |
|---|---|---|---|
| 进程启动 → Tk 就绪 | 113–134 ms | 系统光标 | import、`Tk()`、DPI 标定 |
| T0 启动层上屏 | 263–319 ms | 320×200 圆角窗口，alpha 0.3→1.0（220ms） | — |
| T0' 主窗口建完 | 409–498 ms | 同上 | `App()`：侧栏 / 顶栏 / 底栏 / 首屏（≈180ms） |
| T1 逐页预热 | 498 → ≈1400 ms | 进度线 40%→90%，按页推进（每页 400ms 补间） | triggers / template / status / guide，每页之间 `after(60)` |
| T2 走满 + 淡出 | ≈1400 → ≈1900 ms | 进度线 90%→100%（180ms）→ 整层 alpha 1→0（300ms） | — |
| T3 交接 | **1978–2052 ms** | 主窗口 `deiconify` + 首屏 8px 上移就位 | 启动层销毁 |

**从双击到主窗口 ≈ 2.0 秒**，落在 5.4 说的「用户只在这里停留 1–2 秒」的上沿。

T1 结束时间 = 4 页实测合计 × 1.15 = 1173 × 1.15 ≈ 1349ms（5.2 的公式），
实测 498 + 605(建页) + 180(让出) ≈ 1283ms，公式和实测差 5%。

### 4.2 三条降级路径（都实测过）

| 路径 | 行为 | 实测 |
|---|---|---|
| 减弱动效 | 不做淡入淡出，进度直接跳格，100% 后停 300ms 交接 | 交接 2.9s（含完整预热），无逐帧绘制 |
| Esc 跳过 | 立刻走满 + 淡出，**不再补那 180ms 进度** | 按 Esc 后 511ms 交接，只建了 2 页就停 |
| 其他输入 | 放弃剩余预热，已建的页留着 | 同上 |

### 4.3 一个必须记下来的坑：重入事件泵会死循环

`_apply_titlebar()` 里原来有一句 `self.root.update_idletasks()`（想让窗口先被
realized）。在「启动层把 5 页全部预建好、再一次性 `deiconify`」这个新场景下，
它会**永久卡死**：一屏的 `<Configure>` → `pack_configure` → 又一轮 `<Configure>`
全挤在 idle 队列里，`update_idletasks()` 永远排不空。

症状很有欺骗性：交接那一刻界面出来了，然后整个程序无响应，没有任何异常，
`after()` 定时器一个都不再触发。

改法：窗口没映射就直接返回，不泵事件。已映射时 `wm_frame()` 本来就是有效的，
不需要那一句。同一个坑在 `Splash._handoff()` 里也踩过一次（在 `after` 回调里
`destroy()` 掉自己所在的窗口），改法是**把销毁延后 120ms 交给 root**。

## 五、给 P1 重写的四条硬要求：落地情况

| # | 要求 | 落地 | 证据 |
|---|---|---|---|
| 1 | 字号只用 4 级 | ✓ | `theme.TS` = 17/13/10/9，`check_style` 校验档位数 |
| 2 | `elide` 不许纯二分 | ✓ | `measure()` 带缓存，`elide` 先测全长再二分 |
| 3 | `Timeline` 不做入场动画 | ✓ | `reveal()` 是空实现，`set_rows` 后只画一次 |
| 4 | 预热绝不越过 T2 | ✓ | `Splash.alive` 在交接时置假，`_boot.step()` 每次先查 |
