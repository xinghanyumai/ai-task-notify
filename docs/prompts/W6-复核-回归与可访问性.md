## 0.5 先补一刀：`ord(ch) > 0xFF` 的注释与测试（20 分钟，必须在跑基线之前）

W6.2 的 `_strip_emoji()` 用 `ord(ch) > 0xFF` 收窄了剥除范围。**这个收窄保留**，
PM 已裁定。理由：去掉它，`25°C` 变成 `25C`，代码里的 `` ` `` `^` `~` 全被吃掉
（反引号是 `Sk` 类，markdown 代码标记当场阵亡）——代价远大于收益。

**但那段 docstring 现在只说了一半，这跟 R41 / R46 / R47 是同一类病：
行为对、话不全对，而话会被当成依据。**

### 它现在说的

> 非 Latin-1 只剥这个区间的。Latin-1 里的 So/Sk 是**排版符号**
> （`° © ® ¨ ^ ~`），剥掉会把 `25°C` 变成 `25C`……

### 它没说的

`0xFF` 是 **Latin-1 上界**，不是**表情下界**。实测 Latin-1 里恰好 10 个 So/Sk，
全是排版符号（`` ^ ` ¦ ¨ © ® ¯ ° ´ ¸ ``）——这半句是对的。但 **> 0xFF 的 So/Sk 里
也有非表情的符号**：

| 字符 | 码位 | 类别 | 剥完之后 |
|---|---|---|---|
| `℃` | U+2103 | So | `25℃` → `25` |
| `™` | U+2122 | So | `ACM™` → `ACM` |
| `№` | U+2116 | So | `№3` → `3` |

这是**已知取舍**（这些符号在任务通知里出现率极低，而漏剥 emoji 每次都会发生——
微信每次都丢、还留下前导空格）。**但代码里没写，下次有人看到 `25℃`→`25` 会当成
bug 去"修"，一修就把 `°C` 和反引号也放回来了。**

### 要做三件事

1. **`wbn/channels.py` 的 `_strip_emoji` docstring**：在现有那句后面补一段，
   说明 > 0xFF 里也有非表情符号（`℃ ™ №`）会被一起剥掉，这是有意取舍并附理由。
   **不许改代码逻辑，一个字符都不许动。**

2. **`tests/test_wxmp_emoji.py` 补测试**，把当前行为钉成「有意为之」：
   - `25°C` → `25°C`（保留；已有断言，别删）
   - `25℃` → `25`（记录损失）
   - `ACM™`、`№3` → 剥掉后剩下的部分（记录损失）
   - 测试 docstring 必须写：**「这是取舍不是 bug。要改先读 roadmap R43 / R45。」**

3. **`docs/roadmap.md`** 在 R43 那条后面加一行 **R49**，登记这个边界：
   剥除判据是 `So/Sk 且 ord > 0xFF`，代价是 `℃ ™ №` 一起消失，理由是……

### 判据

| # | 判据 | 怎么验 |
|---|---|---|
| 1 | 只动了注释和测试 | `git diff -U0 wbn/channels.py` 里**只有 `#` / docstring 行**，没有一行可执行代码 |
| 2 | 新测试真能拦住「放宽边界」 | 把 `and ord(ch) > 0xFF` 临时删掉 → 新测试必须红；恢复 → 绿 |
| 3 | 全量绿 | `pytest -q` → `484 passed` 变 `485 passed` 以上，0 failed |
| 4 | 静态检查 | `ruff check .` → `All checks passed!` |
| 5 | R49 已登记 | `grep -n "R49" docs/roadmap.md` 有输出 |

**第 2 条是这次补丁的全部意义。** 只加注释不加变异验证，等于没加——谁也不知道
那条测试是真的在守边界，还是恰好也绿。

### 2.2 键盘可达

| 检查 | 标准 |
|---|---|
| Tab 顺序 | 与视觉顺序一致（侧栏 → 顶栏 → 内容区），不许往回跳 |
| 焦点可见 | 每个可聚焦元素都有 ring，**不许 `outline: none` 而没有替代** |
| Esc | 关闭当前弹层（如果有） |
| 空格/回车 | 开关、按钮、通道行都能用键盘激活 |
| 焦点陷阱 | 模态框打开时 Tab 不跑出去（如果有模态框） |

### 2.3 减弱动效

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: .01ms !important;
    transition-duration: .01ms !important;
  }
}
```

验法：Windows 设置 → 辅助功能 → 视觉效果 → 关闭动画 → 重启应用 → 切页、
开关、数字滚动都应该瞬间完成。

### 2.4 语义与标签

| 检查 | 标准 |
|---|---|
| 每个 input 有 `<label for>` | 不许只有 placeholder |
| 必填项有 `aria-required` | 光有 `*` 不够，读屏读不出来 |
| 错误信息用 `aria-describedby` 关联 | 错误块要能被读屏念出来 |
| 导航用 `<nav>` + `<a href="#...">` | 不许全是 `<div onclick>` |
| 状态变化用 `aria-live` | 保存结果、测试结果要能播报 |

## 4. 性能

### 4.1 三个数字

> **本节已执行完毕，预算已由 PM 裁定改写 → 见 [W6.3 §2](W6.3-复核裁定落地.md)。**
> 结论：600ms 作废（tkinter 时代口径），改成双基线
> **A ≤ 2500ms（仅源码形态，exe 待 W7 重测）+ B 自研段 ≤ 100ms**。
> 下面是当时的原始条款，保留作决策依据。

| 指标 | 怎么量 | 目标 |
|---|---|---|
| 窗口出现 → 首屏可交互 | `app.py` 打点：`webview.start()` 前 / `pywebviewready` 回调里 | ~~≤ 600ms~~ → A ≤2500ms + B ≤100ms |
| 切页 | DevTools Performance：点导航 → 首帧绘制 | ≤ 100ms |
| 保存 | 点保存 → 反馈出现 | ≤ 200ms |

**为什么原来的首屏目标是 600ms**：来自 `archive/perf.md` 6.1 的 649ms（进程起 → 启动层上屏）。
**注意那条是 250% DPI、含解释器启动、旧代码**，而 `baseline-tkinter.md` 是 200% DPI、
`App()` 起算、新代码——两套数字不能相减，详见 `baseline-tkinter.md` §1.1。

#### 最终口径（W6.3 §2 裁定，**以这一节为准**）

```
首屏预算（双基线，两条一起守）：
  A. 进程起 → 首屏可交互
     - 源码形态：≤ 2500ms（实测 1934–2237ms）
     - exe 形态：**待 W7 实测后另定，不许直接沿用 2500**
  B. 自研代码段（进程起 → Bridge() 完成里属于本项目的那部分）：≤ 100ms（实测 38–44ms）
```

**两条一起守，不许只留第一条。** A 是架构决定的（pywebview 的 208ms + WinForms
程序集的 1009ms + WebView2 运行时的 878ms，96% 不是我们的代码），B 才是防回归的：
以后谁在 `Bridge.__init__` 里同步读日志、同步打网络，A 会涨、B 也会涨，
**而只有 B 能指到是我们自己写的哪一段**。

`tools/bench_ui.py` 一次输出两个数（`app.py` 在 `WBN_BENCH=1` 下打
`[bench] self-code` 和 `[bench] first-interactive` 两行），不用手工插桩。

> 历史：600ms 是 tkinter 时代的口径（Tk 直接用 GDI，没有独立运行时）。
> webview 版必然要付一次 .NET + Chromium 运行时装载，用同一把尺子量两种架构是错的。
> 当时列的三个选项（加回启动层 / 优化 WebView2 / 重定基线）里选了第三个，
> 理由见 W6.3 §2.3；**没有选「把 600 改成 2200 了事」**——那只换了数字，没换尺子。
> 旧的三个数（A 进程起算 / B `App()` 起算 / C DPI 缩放）里，C 仍然要报：
> 不是 200% 时 A、B 都不可比（本机 120% 文本缩放 → DPR 2.4）。

### 4.2 一个必须查的点

`stats_today()` 要解析两个日志文件。日志大的时候（跑了几周）会慢。
- 量一次：日志文件 1MB 时 `insight.stats()` 要多久
- 超过 50ms 就改成"先返回缓存，异步刷新"

> **查完了，结论是不修（W6.3 §5 裁定，P1 → P3）。** 当时的探针造了 1.25MB，
> 但**真实上限是 2 天 × 单日日志量**，而真实单日只有 23.7KB：
> `stats()` 只读 `days=2`（`wbn/insight.py`），`notify-*.log` 有 14 天清理，
> 而 `notifications.log` 不喂任何数字（有测试钉着）。要碰到 50ms 得每天 350KB
> （15 倍），这个工具一天发不出 6000 条通知。
>
> 改缓存 + 异步刷新是行为改动（首次进页面先显示旧值），收益配不上风险。
> 换成**持续守卫** `tests/test_stats_perf.py`：2 天 × 400KB（真实量的 17 倍）
> 断言 `stats()` < 100ms，且**先断言真读到了事件**——只断言耗时的话，
> 日志造空了也是绿的。理由登记在 `docs/roadmap.md` 的 R50。

### 4.3 内存

```
内存目标（WebView2 单窗口的物理下限，不是优化目标）：
  私有   ≤ 400MB      （实测 349.6MB）
  工作集 ≤ 700MB      （实测 601MB）
  切页 20 次后堆不持续增长（实测 9.5MB → 9.5MB）
```

**为什么压不下去**：WebView2 一个窗口固定起 6 个进程，这是它的架构，不是我们的代码：

| 进程 | 职责 |
|---|---|
| 浏览器进程 | 主控、窗口、导航、进程管理 |
| GPU 进程 | DirectComposition 合成（本项目的界面就是靠它画的） |
| 渲染进程 | Blink + V8，跑 `webui/` 那一套 |
| 工具进程 | 辅助（DevTools 协议、诊断） |
| 崩溃处理进程 | Crashpad |
| 网络进程 | 请求栈（本项目只加载本地 `index.html`，但它照起不误） |

**exe 形态要重测**（同 §4.1 的 A 数）：PyInstaller 的自解压会额外占一份临时目录。
「切 20 页后堆不增长」那条**不变**，它和绝对大小无关，查的是泄漏。
