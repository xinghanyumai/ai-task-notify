**R46 · `_wrap_detail` 的 docstring 在教人插 `\n`（改注释，W6 第一件事）**

实测（15:20，直调 API 绕开 `_flatten`）：

### 2.2 键盘可达

| 检查 | 标准 |
|---|---|
| Tab 顺序 | 与视觉顺序一致（侧栏 → 顶栏 → 内容区），不许往回跳 |
| 焦点可见 | 每个可聚焦元素都有 ring，**不许 `outline: none` 而没有替代** |
| Esc | 关闭当前弹层（如果有） |
| 空格/回车 | 开关、按钮、通道行都能用键盘激活 |
| 焦点陷阱 | 模态框打开时 Tab 不跑出去（如果有模态框） |

### 2.3 减弱动效

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: .01ms !important;
    transition-duration: .01ms !important;
  }
}
```

验法：Windows 设置 → 辅助功能 → 视觉效果 → 关闭动画 → 重启应用 → 切页、
开关、数字滚动都应该瞬间完成。

### 2.4 语义与标签

| 检查 | 标准 |
|---|---|
| 每个 input 有 `<label for>` | 不许只有 placeholder |
| 必填项有 `aria-required` | 光有 `*` 不够，读屏读不出来 |
| 错误信息用 `aria-describedby` 关联 | 错误块要能被读屏念出来 |
| 导航用 `<nav>` + `<a href="#...">` | 不许全是 `<div onclick>` |
| 状态变化用 `aria-live` | 保存结果、测试结果要能播报 |

## 4. 性能

### 4.1 三个数字

| 指标 | 怎么量 | 目标 |
|---|---|---|
| 窗口出现 → 首屏可交互 | `app.py` 打点：`webview.start()` 前 / `pywebviewready` 回调里 | ≤ 600ms |
| 切页 | DevTools Performance：点导航 → 首帧绘制 | ≤ 100ms |
| 保存 | 点保存 → 反馈出现 | ≤ 200ms |

**为什么首屏目标是 600ms**：来自 `archive/perf.md` 6.1 的 649ms（进程起 → 启动层上屏）。
**注意那条是 250% DPI、含解释器启动、旧代码**，而 `baseline-tkinter.md` 是 200% DPI、
`App()` 起算、新代码——两套数字不能相减，详见 `baseline-tkinter.md` §1.1。

所以 W6 报告里必须**同时给三个数**，缺一个就没法判断：

| 数 | 口径 | 对照对象 |
|---|---|---|
| A. 双击 → 首屏可见 | 进程起算，含解释器 + WebView2 初始化 | 600ms 目标 |
| B. `App()` 构造 → 首屏可交互 | 不含进程启动 | `baseline-tkinter.md` 的 164.1ms |
| C. 实际 DPI 缩放 | `GetDpiForWindow` 实测值 | 必须是 200%，否则 A/B 都不可比 |

如果 A 超过 600ms，先看是解释器/WebView2 初始化慢，还是 `Bridge.__init__` 里读了日志
或配置（同步阻塞）。**这两者的修法完全不同**，别混着猜。

> **W5 已经把 A 量出来了：1997 / 2147ms（两次独立实测，超预算 3.5 倍）。**
> `import webview` 只占 226ms，其余 1.7s 全在 WebView2 初始化 + 首帧。
>
> 也就是说这不再是「猜是哪里慢」的问题，而是一个**决策**：
>
> | 选项 | 代价 |
> |---|---|
> | 加回启动层（`splash`，W5 刚删掉） | 首屏"可见"变快，但"可交互"没变——用户看到的是空壳 |
> | 优化 WebView2 初始化（预热、`--no-sandbox` 已有、延迟加载非首屏资源） | 天花板大概在 1.2–1.5s，到不了 600ms |
> | 重新定基线（把预算改成 2s 左右） | 必须写清「为什么 webview 的 2s 比 tkinter 的 0.6s 可以接受」，否则就是调阈值放水 |
>
> **600ms 是 tkinter 时代的口径，直接套在 webview 上等于用旧尺子量新东西。**
> W6 必须三选一并给出理由——**不许静默把预算调高**（这是 W6 自己的纪律：
> 不达标就退回改，不许调阈值让检查通过）。

### 4.2 一个必须查的点

`stats_today()` 要解析两个日志文件。日志大的时候（跑了几周）会慢。
- 量一次：日志文件 1MB 时 `insight.stats()` 要多久
- 超过 50ms 就改成"先返回缓存，异步刷新"

### 4.3 内存

| 指标 | 目标 |
|---|---|
| 空闲时进程总内存 | ≤ 200MB（WebView2 自身约 80–120MB） |
| 连续切页 20 次后 | 不持续增长（DevTools Memory 快照对比） |

## 5. 新旧并排对照

每页一张，左边 tkinter 版（`git stash` 后跑 `ui.py` 截图），右边 web 版。

> **对照前必须记三个数，否则这组图是假的**：`devicePixelRatio`、`innerWidth`、
> `HKCU\Software\Microsoft\Accessibility\TextScaleFactor`。
>
> 这台机器的 `TextScaleFactor = 120`，于是：
>
> | | tkinter 版 | web 版 |
> |---|---|---|
> | 是否读文本缩放 | **不读**（Tk 只认 DPI，`theme.S.scale = 1.9988`） | **读**（DPR = 2.0 × 1.2 = 2.4） |
> | 14px 正文的实际物理高度 | 28 px | 33.6 px |
>
> **所以 web 版的字看起来会大 20%，那不是回归，是它尊重了你的辅助功能设置。**
> 不做说明就并排贴出来，看图的人会得出「新界面字太大」的错误结论。
>
> 三种处理，选一种并在报告里写明：
> 1. 把 Windows 文本大小临时调回 100%，两边各截一次（**最干净，推荐**）
> 2. 保留 120%，但在图上标注「web 版按 120% 文本缩放渲染，等比缩小 20% 后与左侧可比」
> 3. 只比结构不比字号，并在图注里写清不比字号

> **性能对照的基线数字取自 [`../baseline-tkinter.md`](../baseline-tkinter.md)，不是 `archive/perf.md`。**
> 前者是 W0 之后测的最终态（删预热、抽 insight 之后），后者是 P1/P2 时代的中间态，两组测的不是同一份代码。

**逐项对照的不是像素，是功能**：

| 对照项 | 怎么对 |
|---|---|
| 字段数量与顺序 | 数一遍 |
| 默认值 | 同一份 config，两边显示的值要一样 |
| 说明文字 | 逐字读，不许"改得更好" |
| 禁用态触发条件 | 清空必填项，两边按钮都该灰 |
| 空状态文案 | 一样 |

## 6. 汇报格式

```
1. 12 条基线勾选表（第 12 条如果是"未验"，如实写）
2. 对比度实测表（浅色 + 深色，各 5 行以上）
```

一份说清"哪 2 条没验、风险多大"的报告才有。
