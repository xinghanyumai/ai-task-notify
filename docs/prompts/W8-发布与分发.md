# W8 · 发布与分发（Phase 8）

> 前置：W7 完成（有一个在干净机器上验证过的 exe）
> 主执行 skill：`ci-cd-and-automation` ｜ 审查 skill：`code-review-and-quality`
> 产出：版本号 + 发布包 + 升级路径 + 首次运行引导

---

## 0. 这一步真正要解决的问题

不是"把 exe 传到 GitHub"，而是**让已经装了旧版的用户升级时不丢配置、不断链路**。

旧版是「一个目录 + `python ui.py`」，新版是「一个 exe」。两者之间有三处会断：

| 断点 | 后果 |
|---|---|
| WorkBuddy 里的 hook 配置指向 `python hook.py` | 升级后 hook 找不到文件，通知彻底不发 |
| `config.json` 在旧目录里 | 新版 exe 读不到，用户要重填 10 个通道的凭证 |
| 旧目录的托盘还在跑 | 两个托盘图标、两套单实例锁，行为诡异 |

**这三条必须都有明确的迁移路径，否则这次发布就是"让所有老用户重装一遍"。**

---

## 1. 版本号与发布节奏

用 `1.MINOR.PATCH`，写进三个地方并保持一致：

| 位置 | 谁读 |
|---|---|
| `version_info.txt`（exe 文件属性） | 用户右键看属性、任务管理器 |
| `app.py` 的 `__version__` | `--version` 输出、关于页 |
| `CHANGELOG.md` 的最新一节 | 人读 |

**加一个测试守住一致性**（`tests/test_version.py`）：
三个地方的版本号必须相同，否则 CI 红。这条能防住"发了新 exe 但关于页还是旧版本号"。

## 2. 发布包结构

```
notify-v1.0.0-win64.zip
├── 通知.exe                  ← 唯一可执行文件
├── config.example.json       ← 首次运行的模板（不含真实凭证）
├── README.txt                ← 三句话说清怎么用（不是 README.md，用户不装 md 阅读器）
└── 使用说明.pdf              ← 可选，给不看 README 的人
```

**zip 里不要放**：`config.json`（含凭证）、`logs/`、`state/`、源码、`.py` 文件。

README.txt 只要三句：
```
1. 双击「通知.exe」打开设置，填一个推送通道，点「发送测试」确认手机能收到。
2. 点「安装」，它会自动配置 WorkBuddy 的通知钩子。
3. 之后关掉窗口即可，托盘图标常驻。
```

## 3. 升级路径（最重要的一节）

### 3.1 `install.py migrate` 子命令

新增一个子命令，专门处理"从旧版目录迁到 exe"：

```
通知.exe migrate --from "D:\Code\Work buddy 通知"
```

它做四件事：

| 步骤 | 动作 | 失败时 |
|---|---|---|
| 1 | 从 `--from` 目录读 `config.json`，校验 JSON 合法 | 报错并停止，不覆盖现有配置 |
| 2 | 把 `config.json` 写到 exe 旁边的 `config.ROOT` | 报错并停止 |
| 3 | 重写 WorkBuddy 的 hook 配置：`python hook.py` → `通知.exe hook` | 列出需要手改的路径，让用户手动处理 |
| 4 | 提示用户旧目录可以删，但**不自动删** | — |

**第 3 步不许"猜着改"。** WorkBuddy 的 hook 配置可能在：
- `~/.workbuddy/settings.json`
- `%APPDATA%\WorkBuddy\...`
- 用户自定义路径

`install.py` 已经有写入逻辑（`--also-legacy` 说明它知道多个位置），
迁移时**复用同一套探测逻辑**，不要新写一套。

**第 4 步"不自动删"是故意的**：删错了就没退路。让用户自己删，
或者在文档里写"确认新版能用之后，可以删除旧目录"。

### 3.2 升级不丢配置的验收

```bash
# 模拟升级：旧版目录 + 填好的 config.json
1. 旧目录里配好 3 个通道，保存
2. 把 exe 放到一个新目录
3. 通知.exe migrate --from "旧目录路径"
4. 打开新版 → 3 个通道的凭证都在 → 点「发送测试」→ 手机收到
5. 旧目录还在（没被删）
```

**第 4 步的"发送测试"必须真发**。配置读出来是对的、但凭证字段错位的情况，
只有真发才能发现。

## 4. 首次运行引导

第一次打开（`config.json` 不存在）时，不要直接进主界面，走三步引导：

```
① 选一个通道 → 只列 3 个最容易的：微信测试号 / Bark / 写入本地日志
② 填最少必要字段 → 微信测试号只要 appid + secret + template_id
③ 点「发送测试」→ 成功才允许进主界面，失败就地显示原因和排查建议
```

**为什么强制先配通道**：这个工具的价值是"手机上收到消息"。
如果用户进来看到 10 个通道不知道选哪个，很可能直接关掉。

引导页复用 W3 的表单组件，不要单独写一套。

## 5. 卸载

```
通知.exe uninstall
```

做四件事：

| 步骤 | 动作 |
|---|---|
| 1 | 停掉托盘进程（发退出信号，不是 `taskkill /f`） |
| 2 | 移除 WorkBuddy 的 hook 配置（只移除自己写的那条，不动别的） |
| 3 | 删除开机自启项（注册表 `Run` 或启动文件夹快捷方式） |
| 4 | **保留** `config.json` 和 `logs/`，并告诉用户它们在哪 |

第 4 步是故意的：卸载重装很常见，删了配置用户要重填。
但要明确打印路径，让想彻底删的人知道删哪。

## 6. 发布检查单

发版前逐项打勾，一条不过不发：

```
[ ] pytest 全绿（含新增的 test_frozen_paths / test_version）
[ ] ruff 全绿
[ ] CI 的 package job 产出了 exe
[ ] exe 在干净机器上：双击能开、五页能进、hook 能触发、手机能收到
[ ] 从上一版升级：配置完整、hook 自动迁移、旧目录没被删
[ ] 卸载：托盘退出、hook 移除、配置保留
[ ] CHANGELOG 写了这一版改了什么（用户能看懂的话，不是 commit 列表）
[ ] 版本号三处一致
[ ] README.txt 三句话准确
[ ] 发布包 zip 里没有 config.json / logs / 源码
```
