### 1.1 体积字节数写错 1,000,000 B

是你本机跑出来的，带出去等于把配置一起发出去。

**判据**：`docs/` 里不再出现「dist/ 里只有一个文件」这种与代码判据不符的绝对说法。

### 1.3 只读回落「icacls 拒写实测生效」——现场没有证据

报告第 4 条说：只读回落「用 `icacls` 拒写实测生效」。**我没找到痕迹**：

- `%LOCALAPPDATA%\WBNotify\` **不存在**
- `tmp/w7/ro/` 里**只有 exe 副本**，没有 `config.json`

回落生效的话，配置应该落在 `%LOCALAPPDATA%\WBNotify\config.json`。现在两处都没有。
可能你测完清了，也可能没真跑到回落那条路上。**结论我先不采信，也不算你错**——
但必须补一次带证据的。

**怎么验（照做，别改顺序）**：

```bash
# 1. 清场
rm -rf "$LOCALAPPDATA/WBNotify"

# 2. 造一个不可写目录：拷 exe 进去，然后断掉继承、只给读+执行
mkdir -p tmp/w7/ro2 && cp dist/通知.exe tmp/w7/ro2/
icacls tmp/w7/ro2 /inheritance:r /grant:r "$USERNAME:(OI)(CI)RX"

# 3. 跑一次，改一个值（比如把主题切深色），退出

ls -l tmp/w7/ro2/                        # 期望：这里没有 config.json
```

**收尾**：`icacls tmp/w7/ro2 /inheritance:e` 或直接删目录，别把 ACL 留在仓库里。

### 1.4 【新发现·报告没提】`%TEMP%` 里 5 个 `_MEI*` 残留，共 165MB

我刚数了一下：

```
33MB  2026-10-30 14:17:38  _MEI000006602
33MB  2026-10-30 14:17:21  _MEI00000b2c2
33MB  2026-10-30 14:16:21  _MEI0000169c2
33MB  2026-10-30 14:17:17  _MEI00002afc2
33MB  2026-10-30 14:17:27  _MEI00004e482
```

**5 × 33MB = 165MB，全是 W7 测试时段（14:16–14:17）留下的。**
这和你登记的 R54 是同一个根：每次启动都要把 19MB 解成 33MB。

onefile 正常退出会自己删；被强杀（`taskkill`、崩溃、看门狗交棒）不会。
现在的问题是：**我们不知道正常路径会不会留**。这个必须给答案，因为
「一个通知解压两次」× 长时间跑，用户 `%TEMP%` 会攒。

**怎么验（三组，缺一不可）**：

```bash
count() { ls -d "$TEMP"/_MEI* 2>/dev/null | wc -l; }

# A. 正常退出会不会留
before=$(count)
for i in 1 2 3; do ./dist/通知.exe --version; done
after=$(count)          # 期望 after == before

# B. hook 子命令（快速退出的那条路）
before=$(count)
./dist/通知.exe hook --app wbn-selftest      # 需要 webhook 配好
after=$(count)          # 期望 after == before

# C. 被强杀会不会留
./dist/通知.exe &
pid=$!; sleep 6; taskkill //F //PID $pid
after=$(count)          # 期望 after == before + 1（这就是那 165MB 的来源）
```

**判据**：三组都给**前后个数**，不给结论词。然后按结果决定登记方式：

- A、B 都不留 → 这 165MB 是 C 类残留。登记 R59（P3）：**用户机器上不会自己攒，
  但崩溃/强杀会留 33MB/次**，`docs/troubleshooting.md` 加一小节
  「`%TEMP%` 里一堆 `_MEIxxxx` 是什么、能不能删、怎么删」。
- A 或 B 会留 → **升 P1**。那意味着每一条通知漏 33MB，一小时几十条就上 GB。
  这种情况先回来找我，别自己改 `runtime_tmpdir`（那会让 exe 旁边多出用户看不懂的目录）。

**不许怎么做**：不许写「onefile 会自动清理」了事。上面那 5 个目录就在你机器上摆着。

## 2.5 README 补一节「已经有别的方案了，还需要这个吗」

**背景**：PM 去核了 GitHub 和 PyPI 上现有的第三方方案，确认**微信单通道这件事
本项目是重复建设**。具体核到的东西写在 `docs/roadmap.md` 新登的 R60 里。

这条要求只有一件事：**在 README 里诚实说清重叠**，别让人重复装一套。

**怎么写**：在 README「常见问题」前加一节，标题用
`## 已经有官方通知 / MCP 推送了，还需要这个吗？`，内容必须包含下面三块：

**第一块——别人已经有的（照抄这张表，不要改数字）**：

| 已有方案 | 覆盖什么 | 本项目的差异 |
|---|---|---|
| WorkBuddy 自带的桌面通知 | 电脑上弹窗 | 我们多一层「手机也能收」和「历史可查」 |
| `wechat-clawbot-push`（PyPI，MIT，MCP 连接器） | 任务结果 → 个人微信，复用已绑定的 ClawBot，不占名额 | 我们多 9 个通道、6 类事件模板、去重/静音、多宿主 |
| 企业微信群机器人 | 微信群/个人微信收消息 | 我们是同一个通道，但会按事件类型分模板 |
| `wexin-claw-hook`（Tauri 单 exe，本地 9720 webhook） | 任意脚本 curl 一行推微信 | 我们不要求宿主能发 HTTP |

**第一块后面必须补一句实测结论**（PM 已在 2026-10-30 跑过，别改数字）：

> `wechat-clawbot-push` 在**本机**实测：链路通（`--diag` 第 5 步 HTTP 200、
> 4 个 IPv4 TLS 握手全 OK），但**照 README 逐字配置会失败**——它把路径硬编码成
> `~/.workbuddy/...`，而 WorkBuddy 当前实际用的是 `~/.workbuddy-ai/...`
> （`~/.workbuddy` 是 legacy 目录，本项目 `install.py` 里也是这么标的）。
> 后果是：MCP 注册进一个不会被读的文件、凭证发现失败、`--diag` 直接建议你跑
> `--login`，而 `--login` 会占掉微信侧唯一名额、**顶掉 WorkBuddy 原生微信连接**。
> 三个路径都要加 `-ai`，且**绝不能跑 `--login`**。
> 另外实测 `ret=-2`：光有 `bot_token` 不够。但**真正的前提不是 `context_token`，
> 是「最近活跃会话」**——用户在微信里给 bot 发过一条消息之后，**不携带
> `context_token` 也能直接推**（实测 `HTTP 200 发送成功（未携带 context_token，
> 走最近活跃会话）`）；没发过就是 `ret=-2`。所以「装好就能推」要补一个前提：
> 先让那个微信会话热起来。另外 `--refresh`（`acquire_token` 长轮询）在
> WorkBuddy 同时运行时**抢不到消息**（`getupdates` 超时）——两边用同一个 bot
> 轮询会互相抢，这也说明依赖 `context_token` 的路子不可靠。

**第二块——差异到底是什么（一句话，别吹）**：

> 那些方案解决的是「**怎么把一句话送到我手机上**」；本项目解决的是
> 「**哪些事该发、发什么、发过没有、发失败了算谁的**」。
> 如果你只是想让任务结果出现在微信里，装 `wechat-clawbot-push` 就够，
> 不用装本项目。如果你要的是「六类事件分模板 + 十个通道任选 + 不依赖
> 任何私有目录」，再往下看。

**第三块——本项目不依赖私有结构（这是唯一站得住的硬差异）**：

写明：本项目只读宿主**公开的 hooks 协议**（`~/.workbuddy-ai/settings.json`
的 `hooks` 字段）；第三方 MCP 方案需要读 `~/.workbuddy-ai/claw-state/` 下的
内部游标文件，那不是公开 API，宿主改结构就断。

**判据**：`grep -n "还需要这个吗" README.md` 命中，且那一节里同时出现
`wechat-clawbot-push` 和「不用装本项目」两句。

**不许怎么做**：不许把这一节写成「我们更强」。**重叠是真的**，
把重叠说清楚反而让人信你后面那几条差异。
