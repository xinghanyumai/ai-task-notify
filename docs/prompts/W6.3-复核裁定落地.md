## 2. 首屏预算：双基线 + 形态标注

### 2.1 为什么要改

W6 报告的分段是对的，但 **`A ≤ 2500ms` 这个数只对源码形态成立**。

W7 要打成单文件 exe，PyInstaller 的自解压（解压到 `%TEMP%`）会让 A 再涨，
**涨多少现在不知道**。现在把 2500 写死，W7 一打包就立刻破，然后又得重新吵一次。

### 2.2 改成什么

在 `docs/prompts/W7-单文件打包.md` 和 W6 正文里都写：

```
首屏预算（双基线，两条一起守）：
  A. 进程起 → 首屏可交互
     - 源码形态：≤ 2500ms（实测 2056–2101ms）
     - exe 形态：**待 W7 实测后另定，不许直接沿用 2500**
  B. 自研代码段（进程起 → Bridge() 完成里属于本项目的那部分）：≤ 100ms（实测约 40ms）
```

### 2.3 为什么必须两条

- **A 是架构决定的**，不是优化目标。600ms 来自 tkinter 时代（Tk 直接用 GDI，无独立运行时），
  webview 必然要付一次 .NET + Chromium 运行时装载。用同一把尺子量两种架构是错的。
- **B 才是防回归的**。以后谁在 `Bridge.__init__` 里同步读日志、同步打网络，A 会涨而 B 也会涨，
  **但只有 B 能定位到是我们自己的代码**。没有 B，A 涨了只能猜。

### 2.4 判据

| # | 判据 | 怎么验 |
|---|---|---|
| 1 | 三处文档口径一致 | `grep -rn "2500\|600ms" docs/prompts/W6*.md docs/prompts/W7*.md docs/*.md` 无残留「600ms 目标」 |
| 2 | B 数可自动化 | `tools/bench_ui.py` 能单独输出自研段耗时，不是靠手工插桩 |
| 3 | 预算写进 W7 的前置 | W7 §0 里有一行「打包后必须重测 A，不许沿用源码数字」 |

**第 2 条是这次改写的全部意义。** 只把 600 改成 2500 而不加 B 的自动化，等于把尺子扔了。

## 3. `.btn-secondary`：不是"豁免有争议"，是令牌误用

### 3.1 根因

`.btn-secondary`（`webui/assets/shell.css:519`）：

```css
.btn-secondary {
  background: var(--bg-card);      /* #ffffff，对页面 #fafafa = 1.00:1 */
  border: 1px solid var(--border-strong);   /* #d6d6db，对白 = 1.45:1 */
}
```

而 `webui/assets/tokens.css:31` 白纸黑字：

> `--border` / `--border-strong` **只做装饰分隔线**（卡片描边、区块之间）。

**所以这不是 WCAG 豁免的边界问题，是拿「装饰专用」令牌当交互控件边框。**
注释和用法自相矛盾——**这跟 R41 / R46 / R47 / R49 是同一类病：话和用不一致。**

而 `tokens.css:34` 自己已经写了解法：

> 输入框的边框就是那种信息，所以单开一个 `--border-input`（见下）。

### 3.2 裁定

**改用 `--border-input`**（`#86868d`，对白 **3.62:1** ✓）。

**不要新开令牌**：`#86868d` 视觉上和"按钮边框该有的重量"匹配，且 `--border-input` 的语义
（「这个边框是信息，不是装饰」）正好覆盖按钮。

### 3.3 判据

| # | 判据 | 怎么验 |
|---|---|---|
| 1 | 边框对比度 ≥3:1 | 实测 `.btn-secondary` 边框对 `--bg-card` 与对 `--bg` 都 ≥3.0 |
| 2 | 不许顺手改 `--border-strong` | `git diff` 里 `tokens.css` 的 `--border-strong` 行**零改动** |
| 3 | 深色也要过 | 深色下 `.btn-secondary` 边框对 `#151518` ≥3.0 |

**第 2 条防的是"图省事把 `--border-strong` 调深"**——那会让所有装饰分隔线一起变重，
是拿全局换局部。

## 5. 日志 202.6ms：**P1 降 P3，不修**（执行者高估 26 倍）

### 5.1 执行者漏了三个事实

1. **`stats()` 只读 `days=2`**（`wbn/insight.py:175`），不是 14 天
2. **`notifications.log` 不喂任何数字**（`wbn/insight.py:149` 明写「只作为正文存档给人翻」），
   且有测试钉住：`tests/test_insight.py:210 test_stats_recent_does_not_read_notifications_log`
3. **`notify-*.log` 有 14 天清理**（`wbn/store.py:258 prune_logs`，`dispatch.py:74` 默认 14 天）

所以真实上限是 **2 天 × 单日日志量**，不是 14 天，更不是随便造的 1.25MB。

### 5.2 PM 实测（先证明探针真读到数据，否则数字是空气）

| 场景 | 2 天总量 | 事件数 | `stats()` 中位 |
|---|---|---|---|
| **典型（现在的真实量）** | 47KB | 124 | **4.5ms** |
| 重度 | 378KB | 992 | 28.1ms |
| 极重 | 946KB | 2480 | 70.4ms |
| 执行者的假想值 | 2460KB | 6448 | 186.1ms |

**现在的真实单日日志是 23.7KB / 290 行。** 要碰到 50ms 需要**每天 350KB（15 倍）**；
要复现 202.6ms 需要**每天 625KB（26 倍）**。

这个工具是「AI 任务完成通知」，每天 6000+ 条通知不可能发生。

### 5.3 裁定：不修，但加一条守卫

**不改代码逻辑**（改缓存+异步刷新是行为改动，收益配不上风险）。

**加守卫测试** `tests/test_stats_perf.py`：

- 造 2 天 × 每天 400KB 的 `notify-*.log`
- 断言 `insight.stats()` < **100ms**
- **必须先断言读到了事件**（`len(facts.events) > 0`），否则测的是空气

理由：把「一次性测量」变成「持续守卫」。以后谁改了解析逻辑让它变慢，测试会红。
这比「记下来等裁定」有用。

### 5.4 判据

| # | 判据 | 怎么验 |
|---|---|---|
| 1 | 守卫测试存在且真读到数据 | 测试里 `assert len(events) > 0`，删掉这行后把日志造空必须红 |
| 2 | 守卫能咬住 | 把 `logs.read` 里的解析循环改成 O(n²)（或加 `time.sleep(0.15)`）→ 必须红 |
| 3 | roadmap 里 R50 登记「日志性能不修的理由」 | `grep R50 docs/roadmap.md` |

**第 2 条是变异检验，跟 W6.2 一样。** 只加测试不验证它能不能咬，等于没加。

## 6. 焦点丢失：修，P1

### 6.1 现状

`sw.disabled = true`（保存中禁用）会让当前焦点元素 blur → 焦点掉到 `body`。
键盘用户按一下空格切总开关，下一个 Tab 从页面开头重走 **30 个元素**。

### 6.2 裁定

**修。** 两种修法，任选其一并在汇报里说明选了哪个：

| 修法 | 做法 | 代价 |
|---|---|---|
| A. `aria-disabled` | 保留可聚焦，用 `aria-disabled="true"` + 拦截 click/keydown | 要自己防重复提交 |
| B. 保存完 `focus()` 回来 | 保存结束时 `sw.focus()` | 保存期间焦点仍会短暂丢失 |

**禁止用 `tabindex="-1"` 糊过去**——那是把控件从 Tab 序列里踢出去，比丢焦点更糟。

### 6.3 判据

| # | 判据 | 怎么验 |
|---|---|---|
| 1 | 空格切换后焦点还在开关上 | `document.activeElement` 是那个 switch，不是 `BODY` |
| 2 | 连按 3 次空格能翻 3 次 | 状态 ON→OFF→ON→OFF，不丢焦点 |
| 3 | 焦点环仍可见 | 切换后立刻有 `outline`，不用先按 Tab |
| 4 | 第 10 条基线没被改坏 | 30 个焦点元素仍能走一圈，0 个缺环 |

## 8. 空状态：必须补，不许挂「未验」

### 8.1 为什么不能挂「未验」

这是**用户第一次打开程序看到的东西**。而且 tkinter 版在这上面出过问题
（旧 `audit.py` B 项专门查空状态，说明当年踩过）。

本机日志非空导致「最近通知」永远有数据，所以 W6 没验——但**"造不出场景"不等于"场景不存在"**，
新用户就是空场景。

### 8.2 验法（低风险，改名不删）

1. `logs/` → `logs_bak/`（**改名，不删**）
2. 启动 → 截 5 页 × 2 主题
3. `logs_bak/` → `logs/`（**改回来，并核对文件数一致**）

**不许用 `mv` 到 `/tmp` 以外的地方，不许 `rm`。** 改完必须核对：
`ls logs/*.log | wc -l` 与改名前一致。

### 8.3 判据

| # | 判据 | 怎么验 |

| 1 | 5 页空状态都截了 | 10 张图（5 页 × 2 主题） |

## 10. 交互控件对比度扫描（新增守卫）

**这一条是 W6.3 的附加价值，不是裁定里的。**

W6 发现开关 ON 态不达标，是**偶然**——如果当时没量到那个元素就漏了。
所以要一个**能重复跑的扫描脚本**，不是一次性实测。

### 10.1 要求

`tools/a11y_contrast.py`（或 CDP 脚本，你定）：

- 扫所有**交互控件**的边界与填充：`button` / `input` / `select` / `textarea` /
  `[role=switch]` / `[role=checkbox]` / `[role=radio]` / `a[href]`
- 每个元素取**真实计算样式**（`getComputedStyle`），不是令牌字面值
- 对比对象是**它实际压着的背景**（要向上找第一个非透明背景，不是硬编码 `--bg`）
- 输出表格：元素 / 前景 / 背景 / 比值 / 要求 / 结论
- **浅色深色各跑一遍**
- 有任一 <3.0（边界类）或 <4.5（文字类）→ 退出码非 0

### 10.2 判据

| # | 判据 | 怎么验 |
|---|---|---|
| 1 | 能扫出 W6 那三处 | 拿改之前的 commit 跑，必须报出开关 ON 2.19 和 `.btn-secondary` 1.45 |
| 2 | 修完后全绿 | 当前代码跑，退出码 0 |
| 3 | 背景是"实际压着的" | 在卡片内和页面底各放一个同款按钮，比值不同则说明找对了 |

**第 1 条是关键**：一个扫描器如果扫不出已知的问题，它绿了也不代表没问题。
