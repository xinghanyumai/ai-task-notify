## 1. 根因：两层，缺一不可

### 1.1 第一层（上游）：`TaskCompleted` 在一个 turn 里会触发多次

宿主对一个 turn 的「完成」不是发一次就完。实测一个 turn 内 3 秒一次连发三条。
**这一层我们改不了，只能扛。**

### 1.2 第二层（我们的）：去重键把「渲染结果」当成了「事件身份」

`wbn/pipeline.py:16`：

```python
def _dedup_key(kind, session, title, content) -> str:
    raw = f"{kind}|{session}|{title}|{content}".encode("utf-8", "replace")
    return hashlib.sha1(raw).hexdigest()[:16]
```

`content` 是**渲染后**的正文，而默认模板里带 `{duration}`、`{summary}`、`{time}`：

```
**项目**：{project}
**耗时**：{duration}
**时间**：{time}

{summary}
```

同一个 turn 的三次 `TaskCompleted`，`{duration}` 必然递增（12s / 15s / 18s），
`{summary}` 也可能变。于是**三条 content 三个样 → 三个不同的 dedup key → 三条全发**。

**去重本身没坏**，PM 用同一个 payload 连发三次验证过：

```
[14:59:45] skip dedup kind=task_done title=✅ wbtest 任务完成
[14:59:48] skip dedup kind=task_done title=✅ wbtest 任务完成
```

第一次发，第二三次都 `skip dedup`。`dedup_seconds = 180` 也是够的。
**问题只在于键选错了字段。**

## 2. 修法：终态事件按「事件身份」去重，不按「渲染结果」

`state/sessions/<sid>.json` 里已经有 `turn_index`。**用它。**

```
终态事件（kind ∈ {task_done, task_failed}）
    键 = sha1(f"{kind}|{session}|{turn_index}")
    含义：同一个 turn 的「完成」只值一条通知

非终态事件（need_input / tool_failed / session_start / session_end）
    保持现在的 content 键 + 现有频率闸门
    理由：一个 turn 里真的可能问两次、真的可能连续失败三次，
          按 turn 去重会把真通知吃掉
```

**`dedup_seconds` 保留**，作为兜底（比如 turn_index 读不到时的退路）。
**`turn_index` 读不到（旧会话文件 / 首次事件）时，退回 content 键**，
不许因为读不到就整条不发——宁可多发一条，不许丢。

`turn_index` 的语义先确认再写：`wbn/store.py` 里它是怎么增的、什么时候归零。
**如果它在一个 turn 内会变**（那就不能当身份用），回来找 PM，别自己改语义。

## 3. 守卫：四条，第 2 条最重要

**这轮的风险不是修不好，是修过头——把「用户连续做完两件事」的两条通知吃掉。**
所以守卫必须成对：一条证「该合的合了」，一条证「该分的还分」。

| # | 场景 | 期望 | 为什么必须有 |
|---|---|---|---|
| M1 | 同一 turn 连发 3 条 `TaskCompleted`（`duration` 递增） | **只发 1 条** | 直接对应本次 bug |
| M2 | **两个不同 turn** 各发 1 条 `TaskCompleted` | **发 2 条** | 防修过头。这条红了说明去重键把 turn 丢了 |
| M3 | 同一 turn 发 2 条 `PermissionRequest`（→ `need_input`） | **发 2 条** | 非终态不许按 turn 去重 |
| M4 | 同一 turn 一条 `task_done` + 一条 `task_failed` | **发 2 条** | kind 必须参与键 |

写法要求：**不要只断言 `sent is False`**。M1 要同时断言「第二条的 `skipped` 原因是
`turn 内重复`」——只断言没发出去的话，将来任何别的原因（静音、频率闸门、通道全关）
都能让这条测试假绿。M2 要断言**两条的 `dedup_key` 不同**，而不是只数条数。

`.venv\Scripts\pythonw.exe hook.py`。

W7.0 改的 `install.py`（frozen 分支写 `"{exe}" hook`）逻辑是对的，
但**没人重新跑过 `install`**，旧快捷方式和旧 hooks 还在。

**这轮不改这个**（改了就动用户的桌面和宿主配置，要用户点头）。只做两件事：

1. 在汇报里明确写一句：**当前跑的还是源码形态，exe 未启用**

   `通知.exe install` 会重写快捷方式和 hooks、以及重写后桌面图标会变
