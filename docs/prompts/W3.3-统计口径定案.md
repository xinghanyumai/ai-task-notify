# W3.3 · 口径定案：三个数只算远端通道

> 前一段：W3.2 已提交 `0566aa4`（270 passed）。`today` 摆脱了通道开关。
> 这一段把**单位**统一，并修 W3.2 带出来的一个可见回归。

---

## 0. 为什么还有一段

W3.2 把 `today` 从 `sent=True` 换成了「pipeline 写的汇总行」，取数对了。
但你在汇报第 6 条里自己指出了剩下的问题，而且**指对了**：

```
今天的账：today=16  ok=16  fail=14
其中 remote_ok=True 的只有 2 条
```

也就是说屏幕上「今日通知 16」里，**14 条从没到过手机**——全是 `wxmp` 的
`errcode=40037 模板 ID 无效`，只有 `log` 通道把正文写进了本地文件。

这不是"数字不好看"，是**三个数不在同一个宇宙里**：

| 数 | 单位 | 今天的值 |
|---|---|---|
| `today` | 事件，只要有一个通道成功就算 | 16 |
| `ok` | 通道投递次数，**`log` 也算一次投递** | 16 |
| `fail` | 通道投递失败次数 | 14 |

`log` 通道既让 `today` +1，又让 `ok` +1。**它是调试用的落盘，不是投递目标。**

---

## 1. 裁定（D14，已写进 `DECISIONS.md`）

```
今日通知 = 有 remote_ok=True 的事件数
通道成功 = 远端通道投递成功次数
通道失败 = 远端通道投递失败次数
```

三个数都只算**远端通道**。改完今天应该是 **2 / 2 / 14**。

**我在 W3.2 任务书里写过「`ok`/`fail` 一个字都不许动」，这里收回。**
当时的理由是「别为了让数字好看去改」；现在要改的理由不同——是**单位不一致**，
不改就会出现「16 条通知、16 次成功、14 次失败」这种读不出结论的卡。

---

## 2. 三处改动

### 2.1 `today` 的判据：`sent=True` → `remote_ok=True`

`pipeline.py:92` 已经算好了：

```python
remote_ok = any(o for t, o, _ in results if t not in ("log",))
```

`remote_ok` 就是「至少一个非 log 通道成功」。改判据即可，不用新增字段。

### 2.2 `ok` / `fail` 排除 `log` 通道行

日志行长这样：

```
[10:24:23] channel=log ok=True msg=已记录
[10:40:04] channel=wxmp ok=False msg=errcode=40037 模板 ID 无效
```

判据：**锚定时间戳右侧第一段**取出通道名，`!= "log"` 才计数。

```python
_CHANNEL_LINE = re.compile(r"^\[(\d{2}:\d{2}:\d{2})\] channel=(\S+)")
```

**不许用 `"channel=log" in line`**——`msg=` 里是通道返回的原文，可能包含
`channel=`（和 `test` 那个坑同源）。必须锚定首段。

### 2.3 `recent` 排除测试条目

删掉 `kind == "test"` 之后，「最近通知」开始出现 `通知测试` 且带绿色 ✓
（实测 `10:53:17 | True | 通知测试` 已进前两条）。

**这个特判要加回来，但放在对的位置**：

```python
kind = m.group(4)
if kind == "test":
    continue          # 测试正文不是通知，不进 recent
rows.append(...)
```

区别在于**位置**：W3.1 那个特判错在拿它去阻止 `today` 计数（`today` 根本
不该读这个文件），不是错在它存在。`kind` 表达的就是「这条记录是什么事件」，
判断「是不是通知」正是它的本职。

## 3. 不许做的事

| 不许 | 理由 |
|---|---|
| 改 UI 上的四张卡、文案、顺序 | 数字口径变了，标签不用变：「今日通知」= 到手机的通知 |
| 把 `log` 通道从「启用通道 N/10」里去掉 | 它是真的启用了，用户要知道 |
| 停止写 `notifications.log` | 它是 `recent` 的唯一数据源 |
| 顺手把 `chain_sentence()` 也改了 | 它**已经**排除了 `log`（「只写入本地日志，手机上收不到」），本来就对 |
| 为了"别让用户看到 2"而保留 16 | 2 是事实。14 条失败是真实故障，用户需要看见 |

---

## 4. 验收（6 条）

| # | 验收项 | 标准 |
|---|---|---|
| 1 | 三个数落到 2 / 2 / 14 | 在今天的真实日志上跑 `stats()`，贴出来；并贴手算：`remote_ok=True` 行数、非 log 通道行数 |
| 2 | 关掉 `log` 通道仍涨 | 临时目录（**四个目录一起隔离**，见 `architecture.md`）关掉 `log`，真发一条，`today` +1 |
| 3 | 只开 `log` 通道 → 三个数全 0 | 同时 `chain_sentence()` 必须是「只写入本地日志，手机上收不到」+ `warn`。**两句要一致** |
| 4 | 测试仍不进统计 | 连点 3 次「测试此通道」，`today` / `ok` / `fail` 一个都不变 |
| 5 | `recent` 干净 | 「最近通知」里**不再出现**「通知测试」；仍是 8 条；✅/⚠️ 仍被剥掉 |
| 6 | 假通道名不误伤 | 造一行 `channel=wxmp ok=False msg=upstream said channel=log failed`，它**必须**计入 `fail`（证明锚定首段生效） |

第 6 条是这一段唯一的技术陷阱。前面三轮的 bug 全出在「在整行里找子串」，
这次改的又正好是取通道名——不测这一条，很可能第四次踩同一个坑。
