## 1. 现场

`notifications.log` 的唯一写入方是 `channels._send_log`（全项目 grep 只有
`channels.py:1362` 一处）。也就是说：

```
「今日通知」= log 通道投递成功的次数
```

而 `log` 通道有开关，`auto_enable` 也尊重 `manual_off`。用户完全可能关掉它
（"我又不看日志文件"），然后就出现：

```
关掉 log 通道
真实发送一次 → notify-*.log 有 1 行，notifications.log 不存在
stats → 今日通知=0  成功=0  失败=1
```

真实机器上是冻结不是归零（历史行还在），所以更难看：`今日通知` 停在 5 不动，
`通道成功` 一直在涨。

---

## 2. 改法

`today` 改成数 `notify-*.log` 里的**事件汇总行**：

```
[10:24:23] event=Stop kind=task_done sent=True remote_ok=False elapsed=1.17s title=…
```

判据：时间戳后第一段是 `event=`，且行内含 `sent=True`。

三个理由：

1. **由 `pipeline.notify()` 写，与通道开关无关**——通道全关它照样写。
2. **`send_test` 不经过 `pipeline.notify()`**，所以测试行天生不会被数进去，
   `kind == "test"` 那条特判可以**删掉**（少一个特判，少一处会过期的知识）。
3. 一天只有几十行，解析成本和现在一个量级。

**`sent=True` 而不是全部 `event=`**：`sent=False` 表示所有通道都失败了，
那不算"发出去了"。保持现在「今日通知 = 发出去了几条」的语义。
（`skip event=…` 开头的行本来就匹配不上 `event=` 在首段，天然排除。）

### 2.1 顺带清理

- `stats()` 里 `kind == "test"` 的分支删掉，docstring 同步删那一段。
  **如果留着，就是留了一段"以后不会再触发"的代码**——下一个读的人会以为它还有用。
- `notifications.log` 的解析**仍然需要**，它供 `recent`（最近 8 条通知）用。
  只是不再供 `today`。docstring 要把这两个用途分开写清楚。

## 3. 不许做的事

| 不许 | 理由 |
|---|---|
| 改 UI 上的四张卡、文案、顺序 | 这一段只换数据源。数字对了就是对了，别顺手改设计 |
| 动 `ok` / `fail` 的算法 | 它们一直是对的（数通道投递次数） |
| 为了"让数字一致"把 `ok`/`fail` 也改成按事件算 | 那会丢掉「哪个通道挂了」的信息，而这是用户最需要的那条 |
| 删 `notifications.log` 或不再写它 | 它是 `recent` 的数据源，也是用户唯一能读的正文记录 |

---

## 4. 验收（4 条）

| # | 验收项 | 标准 |
|---|---|---|
| 1 | **关掉 log 通道，`today` 仍然涨** | 临时目录：`log` 通道 `enabled=False` + `manual_off=True`，跑一次真实发送，`today` +1 |
| 2 | 测试仍然不算 | 连点 3 次「测试此通道」，`today` / `ok` / `fail` **一个都不变** |
| 3 | 三个数仍能对上 | 当前日志上跑一遍：`today` 应等于 `event=… sent=True` 的行数（今天 12），`ok + fail` 应等于真实通道行数（今天 24） |
| 4 | `recent` 没坏 | 状态页「最近通知」仍显示 8 条，标题里的 ✅/⚠️ 仍被剥掉 |

第 1 条是这一段的核心。**它证明的不只是"修好了"，是"这个数不再依赖用户能关的东西"。**

第 3 条要贴出你手算的行数和 `stats()` 的返回值，两个数并排。
