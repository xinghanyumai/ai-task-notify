## 当前基线（P0 实测，2026-10-27，各跑 3 次）

> ⚠️ **P1 重做版式后这张表全部作废，必须重测。** 保留在这里只作为"改前"参照。

```
启动建界面（冷）            255–305 ms   预算 400    ✓
切页                        2–4 ms       预算 100    ✓
整页重建（切主题）           56–61 ms     预算 300    ✓
首次进入 triggers   1370 / 1364 / 1200 ms   预算 900   ✗
首次进入 template    943 /  882 /  912 ms   预算 900   ✗
首次进入 status     1139 / 1013 / 1140 ms   预算 900   ✗
首次进入 guide      1579 / 1388 / 1723 ms   预算 900   ✗
```

**四页首次进入全部超预算，且合计 5031–5988ms。** 这不是 P0 造成的——
`redesign-base` 上同样超，是 v1 页面缓存引入后一直存在的问题。

### ⚠️ 这批数字的可靠性：一半可信，一半不可信

| 指标 | 可信度 | 原因 |
|---|---|---|
| 启动 / 切页 / 整页重建 | **可信** | 单次执行、路径确定，波动小 |
| **首次进入** | **不可信** | `_cold_ms` 两个缺陷，见下 |

`_cold_ms` 的两个缺陷（P0 发现，P1 第 0a 步修）：

1. **取样太早**：`App()` 之后只跑 `update_idletasks()`，赶在预热定时器 `after(400)` 之前，
   所以它**结构上量不到预热的作用**。有预热 / 无预热两组数字在噪声内无差别，就是这么来的。
2. **单次采样**：没有中位数，同一份代码两次跑能差 2 倍（triggers 485 → 1370）。

**所以 P2 开工前必须先确认 P1 第 0a 步已经修好了 `_cold_ms`。** 没修就别测，
测出来的数字不能当判据。

> 附带结论：v1 文档里那张「465 / 569 / 259 / 788ms」的旧表是用有缺陷的量法测的，
> **作废**，不要拿它和现在的数字比。

## 两个必须分清的指标

| 指标 | 含义 | 用户什么时候付 |
|---|---|---|
| **切页** | 页面已在内存，`pack_forget` + `pack` | 每次点导航 |
| **首次进入** | 这一页第一次被建出来（建控件 + 文本排版 + 首轮布局） | 每个页面一次/每次启动 |

这两个数差 20–300 倍。混在一起看会得出"切页很快"的错误结论，
而用户第一次点某一页时付的是"首次进入"的钱。

### v1 的判断与它的代价（已废弃）

v1 把"首次进入"挪到启动后的**无限期后台预热**里。代价是：预热是同步建页面，
一次最长冻结 790ms，四个页面合计约 2081ms，与「发送期间界面不冻结」直接冲突，
`check_responsive.py` 因此失败（停顿 390ms）。

**v2 改为 D8 方案：预热只发生在启动动画期间。** 见下。

## 硬约束

1. **不许为了让数字好看而改预算值。** 预算写在 `bench_ui.py` 顶部，那四个常量是尺子。
2. **不许改检查脚本**。理由同上一条。
3. **不许用「感觉流畅了」结案**。改前改后数字必须并列贴出来。
4. **不许牺牲功能换性能**。禁止为了快而少画东西、少校验、少更新。
5. **发送期间主线程最大停顿必须 < 120ms**。这是 P0 的承诺，性能优化不能反过来破坏它。
6. 行为约束四条：临时脚本只进 `tools/_scratch/` 且用完删；不改白名单外文件；
   一次只做这一条；不许为了让检查变绿改检查脚本。

## 动作

### 第 1 步：确认 D8 已定为启动动画方案

原 A/B/C 三个选项**作废**。D8 已裁定为 **D 方案**（`DECISIONS.md` 第三节）：

> 预热窗口被限制在启动动画期间（T0–T2，约 1.9 秒），动画结束即销毁预热定时器，
> 之后任何时候都不许再后台建页。

**这条裁定的直接后果**：`check_responsive.py` 的"发送期间停顿 390ms"自动消失——
发送请求发生时启动动画早已结束，没有后台任务抢主线程。

P2 要做的不是重新选方案，而是**验证 D 方案真的成立**：

| 验什么 | 怎么验 | 期望 |
|---|---|---|
| 预热确实不越过 T2 | 在 `_warm_pages` 里打日志，记录每次建页的时间戳 | 最后一次建页 ≤ 启动层销毁时间 |
| 动画结束后无后台任务 | `check_responsive.py` 的停顿项 | < 120ms |
| 启动层期间不冻界面 | 录屏看进度线是否连续 | 无 > 100ms 的停帧 |
| Esc 跳过后仍能正常用 | 启动时按 Esc，然后逐页点 | 每页都能开，不报错 |

### 第 2 步：重测基线（P1 之后必做）

P1 换了版式骨架，**所有数字都要重测**，不许沿用上表：

```bash
python tools/bench_ui.py --runs 5
```

重测后**重定预算**。判断标准不是"和 v1 比快了多少"，而是：
- 切页 ≤ 100ms（预算不变，这是硬指标）
- 启动到首屏可交互 ≤ 1900ms（新增指标，对应启动层时间轴）
- 整页重建（切主题）≤ 300ms

### 第 3 步：把"首次进入"的钱花在明处

在 `docs/perf.md` 里写清三件事：

- 首次进入的真实成本（P1 后重测，预计 250–800ms 量级）
- 这笔钱现在由谁付：**启动层的 1.7 秒动画**
- 为什么不能更便宜：Tk 建控件 + 汉字首轮栅格化是硬成本。已实测排除的路径——
  换字体组合、预解析字体（A/B 中位数 725→697ms，噪声级）、合并 `after_idle`
  （反而更慢）、`gc.freeze()`（启动更慢且有界泄漏）。**这些不要再试一遍。**

**这一条比优化本身重要。** 不写清楚，下一个人会再花半天重试同样的死路。

### 第 4 步：只在有证据时优化

切页若已是个位数 ms，**没有优化空间，不要动**。真要找活干只有两个方向：

1. **启动 232ms**：占比最大的是建侧栏 + 顶栏 + 首屏。预算 400 已宽松，收益有限。
2. **整页重建 34.8ms**（切主题）：用户几乎感觉不到，不建议动。

**结论：本轮很可能不需要写任何优化代码。** 若确实如此，如实说"无需优化"，
不要为了交差造一个改动。

### 第 5 步：复测并列

```bash
python tools/bench_ui.py --runs 5
python tools/check_responsive.py
```

把 P1 改后基线（第 2 步）与最终数字并列贴出来。

## 卡住怎么办

- **启动层总时长压不进 2200ms** → 减少预热页数（先建用户最可能点的 2 页），
  不要为了凑时间缩短动画——动画短了盖不住，用户会看到主窗口闪一下。
- **预热仍导致停顿超标** → 说明预热越过了 T2。按 P1 的 5.2 第 5 条收口，**不要调阈值**。
- **切页数字变差了** → 先 `git diff` 看是不是有人又在切页路径上加了同步工作，别急着优化。
- **`bench_ui.py` 需要改才能测新指标** → 停下来说明，等确认。不要直接改。
- **启动层在 2× DPI 下尺寸不对** → 用 `theme.S()` 换算，不要写死像素。
