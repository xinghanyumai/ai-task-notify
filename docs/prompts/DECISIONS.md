## D1 · 保留 tkinter 版作为降级路径？

**这是核实外来方案时发现的硬矛盾**：方案 3.1 说删 6 个文件，9.1 又说建议保留
`ui_legacy.py`。但 `ui.py` 依赖那 5 个模块，删了模块 legacy 就 import 不了。
"保留 legacy"必须连 3708 行一起保留。

| 选项 | 内容 | 代价 | 收益 |
|---|---|---|---|
| A | 保留 `ui_legacy.py` + 5 个模块 | 仓库常驻 3708 行死代码，每次改 ruff / 升 Python 都要陪跑 | WebView2 缺失的机器功能完整 |
| **B（推荐）** | 全删，降级改为原生提示框 | 那些机器没有图形设置界面 | 仓库干净，删掉 6084 行 |
| C | 移到 `legacy/` 子包 | 3708 行还在，只是换位置；十几处 import 要改 | 主目录干净 |

**已裁定 B（2026-10-27）。** 理由：

1. WebView2 从 Win10 1803（2018-04）起预装，Win11 全系自带。2026 年还在用更早
   系统的机器，本来就跑不动这个工具的其他部分。
2. 3708 行死代码不是"存着不用"——每次 ruff 升规则、每次 Python 升版本都要陪跑，
   而且总有人会"顺手优化"它。
3. **退路不需要留在工作区**：W0 打了 `git tag tkinter-final`，需要时一条命令拿回：

```bash
git checkout tkinter-final -- ui.py wbn/widgets.py wbn/theme.py \
                               wbn/tokens.py wbn/anim.py wbn/splash.py
```

4. 降级体验可以接受：原生 messagebox 告诉用户缺 WebView2 + 给下载链接 +
   「打开配置目录」。**能改配置、能看日志，只是没有图形设置界面。**

**选 A 的话**，必须在 `docs/architecture.md` 写死一句：
「`legacy/` 下 3708 行是只读历史代码，不接受任何功能改动。」否则半年后
会有人把它捡起来改，两套 UI 同时维护。

## D2 · 自绘窗口边框做不做？

方案自己承认"极痛苦"，然后 Phase 0 就 `frameless=True`。这一步要单独算账。

| 能力 | 原生边框 | frameless |
|---|---|---|
| 边缘/角落 resize | 系统处理 | 自己做 8 个方向命中区 |
| 双击标题栏最大化 | 系统处理 | 自己绑 |
| Win + ←/→ 贴边 | 系统处理 | 行为异常 |
| Aero Snap（拖到顶部最大化） | 系统处理 | 自己实现 |
| 200% DPI 下的命中区 | 系统处理 | 边框几像素，更难点中 |

**已裁定：不做（2026-10-27）。永久使用原生窗口边框。**

原计划的"W5 三条验收"取消——结论已定，不用再验。理由：VS Code、Figma、
Notion 桌面版全都用原生边框，用户根本不会注意到；而自绘边框要自己实现
resize / 贴边 / Aero Snap，任何一个做不好都会让程序显得更廉价，不是更高级。

W5 里相关的实验步骤一并删除，不再保留。

## D3 · 前端样式怎么产出？

外来方案说「Tailwind CDN 或本地文件」。**CDN 必须排除**：便携工具、可能断网、
CDN 还可能被墙，断网即白屏。

| 选项 | 优点 | 缺点 |
|---|---|---|
| Tailwind CLI 产物入库 | 写法快，原子类 | 要装 node；产物 10–20KB；改样式要重新构建 |
| **手写 CSS（推荐）** | 零构建链，改一行生效 | 要自己写，但只有 5 个页面 |
| 引 Tailwind 运行时 JS | 不用构建 | 运行时要解析 DOM，首屏变慢，体积 100KB+ |

**已裁定：手写 CSS（2026-10-27）。零构建链，产物就是源码。** 理由：

1. 5 个页面、一套 token，手写 `tokens.css` + `shell.css` + 3 个页面 CSS
   大约 800 行，比配一条 node 构建链简单。
2. **构建链是长期成本**：半年后想改个颜色，还得记得 `npm run build`。
3. 设计 token 本来就是 CSS 变量，不需要 Tailwind 的原子类来表达。

选 Tailwind 也行，但产物 CSS 必须入库，`.gitignore` 不许忽略它，
且 README 要写清"改样式后要重新构建"。

## D8 · 分发形态（已改判）

**原决策**：不做 pip 安装包，保持"目录 + python"便携形态。
**新决策（2026-10-27）**：**做单文件 exe**，绿色便携，解压即用。

改判理由：用户明确要求"最终打包成一个可执行的 exe 文件"。
这个约束的连锁反应比 UI 重构更大：

1. 6 个入口（hook / dispatch / tray / ui / install / selftest）合并成 1 个 exe + 子命令。
2. `ROOT = Path(__file__).parent.parent` 在 frozen 下指向 `%TEMP%`，退出即删。
3. WorkBuddy 里已配的 hook 路径要迁移。
4. 老用户升级不能丢 `config.json`。

pip 包仍然不做——单 exe 更符合"便携"定位。

## D10 · onefile 还是 onedir

| | onefile | onedir |
|---|---|---|
| 产物 | 1 个 exe | exe + `_internal` 目录 |
| 启动 | 慢 0.8–2.0s（每次解压到 `%TEMP%`） | 快 |
| 杀软误报 | 高（自解压像打包器） | 低 |
| 便携 | 拷一个文件 | 拷整个目录 |

**默认 onefile**（用户要"一个 exe 文件"），但**必须先实测**：

- 判据：冷启动中位数 ≤ 3.0s 就接受
- 超过：先上 `--splash` + `--exclude-module` 裁剪，再超就回来重新拍板

**这条决策不能凭感觉定。** 它和"启动要快"直接冲突——之前花了两轮把启动从
2.5s 压到 1.4s，onefile 的解压可能又还回去 1s。

## D11 · 数据放哪

| 选项 | 优点 | 缺点 |
|---|---|---|
| **exe 旁边（推荐）** | 真正的绿色便携，拷走就带走配置 | 放 `Program Files` 下无写权限 |
| `%LOCALAPPDATA%` | 任何位置都能写 | 不再是"绿色"，用户找不到配置 |
| 混合 | 两者兼顾 | 要写探测逻辑 |

**推荐混合**：优先 exe 旁，探测不可写就回落 `%LOCALAPPDATA%\WBNotify`。
回落之后 UI 要显示实际路径，否则用户找不到自己的配置。

探测方法：在 exe 目录试写一个临时文件，失败即回落。

## D13 · 要不要随包 Inter 字体

W2 把 `--font` 栈写成 `"Inter", "Segoe UI Variable Text", "Segoe UI", "Microsoft YaHei UI"`，
但 `webui/assets/fonts/` 是空的——构建环境无外网，拿不到 Inter 的 woff2。

| 选项 | 代价 | 效果 |
|---|---|---|
| 不随包，用系统栈 | 0 | Win11 走 Segoe UI Variable Text，Win10 走 Segoe UI。**字形与 Inter 不同，字宽略宽** |
| 随包 Inter（100KB woff2 + OFL 许可文件） | 仓库多两个文件 | 三端字形一致，但要有人能联网下载一次并提交 |
| 从 CDN 引 | 0 | **不可行**：W2 的 CSP `font-src 'self'` 会拦，离线也加载不了 |

**裁定：不随包。** 理由：

1. 单 exe、离线可用是硬约束，字体不该成为运行时依赖。
2. 14px 正文下，Segoe UI Variable Text 与 Inter 的观感差异很小（W2 截图已验收）。
3. 一旦随包，就得管许可文件、`--add-data`、`excludes`，为 100KB 增加三处维护点。

`tokens.css` 末尾那段被注释掉的 `@font-face` **保留**，作为"以后想加怎么加"的说明。
但**不许留着 `url()` 指向不存在的文件**（会在 Console 里留 `ERR_FILE_NOT_FOUND`，
违反 W2 验收第 6 条）——W2 这点做对了。

**要改的话只有一处**：把 woff2 放进 `webui/assets/fonts/`，放开注释，栈不用动。

## D14 · 「今日通知」到底数什么

**问题**：`stats()` 的 `today` 有三种可能的口径，选哪个决定了用户看到什么。

| 口径 | 今天的值 | 含义 |
|---|---|---|
| `sent=True`（当前） | 16 | 至少一个通道成功——**包括只有 `log` 通道成功** |
| `remote_ok=True` | **2** | 至少一个**远端**通道成功，即真的到手机了 |
| 全部 `event=` 行 | 16 | 触发过的事件数，不管发没发出去 |

**裁定：`remote_ok=True`（2026-10-28，PM 决定，理由如下）**

1. 产品的成功标准是「手机上收到」。`log` 通道是调试用的落盘，**它不是投递目标**。
2. 今天的账：16 条"今日通知"里 **14 条从没到过手机**（`remote_ok=False`，
   全是 `wxmp` 的 `errcode=40037 模板 ID 无效`）。现在的 16 把真实故障盖住了。
3. `remote_ok` 已经在汇总行里算好了（`pipeline.py:92`，`t not in ("log",)`），
   零额外成本，不用新增字段。
4. 只有 `log` 通道时 `today` 恒为 0——这**不是缺陷**，是事实（没有通知发出去），
   而 `chain_sentence()` 早就会说「只写入本地日志，手机上收不到」。两句一致。

### 连带：`ok` / `fail` 也排除 `log`

W3.2 任务书写过「`ok`/`fail` 的算法一个字都不许动」，**这里收回**。理由不是"数字好看"，
是单位必须统一：

```
今日通知 2（事件） / 通道成功 16（含 16 次 log 落盘） / 通道失败 14
                          ↑ 这三个数不在同一个宇宙里
```

排除 `log` 后变成 `2 / 2 / 14`——三个数都在说「手机」这一件事。

**代价**：`log` 通道写盘失败（磁盘满）不再进统计。可接受——它是调试通道，
失败原因在日志 tail 和它自己的「测试此通道」里都能看到。

### 连带：`recent` 要排除测试条目

删掉 `kind == "test"` 之后，`recent`（「最近通知」）开始出现 `通知测试` 且带绿色 ✓。
**这不是"特判"，是这个字段的正确用法**：`kind` 表达的就是「这条记录是什么事件」，
测试的 kind 是 `test`，它不是通知。

之前那个特判错在**位置**（拿它去阻止 `today` 计数），不是错在存在。

## D15 · 「送到你手机」是状态，不是承诺

**问题**：`chain_sentence()` 只读配置。微信连续 15 次投递失败，侧栏仍然是绿点 +
「送到你手机」。配置确实没变——**变的是结果，界面没跟上**。

这是「界面替失败背书」的第五处。前四处都是数字（今日通知 / 通道成功 / 通道失败 /
启用通道），这一处是文案和颜色，也是用户唯一会先看到的那一处。

**裁定（2026-10-28）**：`chain_sentence()` 与 `channel_state()` 增加可选的
「最近一次投递记录」入参，按下面四档降级：

| 最近一次远端投递 | 侧栏文案 | level | 通道列表 |
|---|---|---|---|
| 没有记录 | 送到你手机 | `ok` | 已启用 |
| 全部成功 | 送到你手机 | `ok` | 已启用 |
| 部分失败 | 最近一次部分没送到 | `warn` | 成功的仍「已启用」 |
| 全部失败 | 但最近一次没送到 | `danger` | 最近一次失败：`{原文前 20 字}` |

### 三条约束，都不是风格问题

1. **没有记录必须是 `ok`。** 首次启动 / 日志被清 / 今天还没发过，都维持原样。
   把「没发过」判成失败，是拿一个不存在的故障吓用户，比不显示更糟。
   验收时这一条必须和「全失败」**成对**测——只测后者，你不知道自己是不是
   把「没发过」也算进去了。
2. **失败原因不进侧栏那句话。** 240px 宽、`--fs-aux` 一行约 16 个汉字，
   塞 `errcode=40037` 会撑成三四行。原文只去通道页，且**先 `redact` 再截断**。
3. **`channel_state()` 的配置问题优先于运行时问题。** 字段没填完连试都试不了，
   说「最近一次失败」只会让人去查网络。

### 冻结

**W3.4 之后统计与健康信号冻结。** W4 起不再回头改 `stats()` / `chain_sentence()` /
`channel_state()` 的语义。新发现的问题记进 `roadmap.md`，不插队。

冻结的理由：这条线连着改了三轮（W3.1 过滤 → W3.2 换数据源 → W3.3 定口径），
每轮都是因为上一轮没把「什么算一条通知」想清楚。口径已经定完（D14 + D15），
再动就是在已经对齐的三个数上重新制造偏差。

## D16 · 保存要不要卡必填

**问题**：现在「保存配置」和「测试此通道」用同一个门控——必填没填完，两个都禁用。

后果是**半成品存不下来**：

```
填了 8 个字段，差 1 个
→ 保存按钮灰的
→ 关窗
→ 8 个字段全丢，没有任何提示
```

**裁定：保存不卡必填，测试卡（2026-10-28，PM 决定）**

| 动作 | 语义 | 要不要必填 |
|---|---|---|
| 保存配置 | 「记下我现在填了什么」 | **不要**。填一半是正常状态 |
| 测试此通道 | 「现在就发一条」 | 要。缺字段发不出去，只能报错 |

保存后 `auto_enable()` 会把凭证不全的通道强制关闭（`channels.py:283` 已有这条逻辑），
所以"存了半成品"不会让一个坏通道处于启用态。安全。

**保留的部分**：「还需要填写：appid」这行提示继续显示在按钮旁边——
它现在是**测试按钮的说明**，不再是保存按钮的说明。

### 连带：关窗要拦

保存不再卡必填之后，丢数据的窗口只剩「改了不保存就关窗」。
`isDirty()` 已经在算了，只是没人用。要接 `window.events.closing`：
dirty 时 `cancel = True` + 确认框「有未保存的改动，确定关闭？」。

## D17 · 「最近通知」的数据源

**问题**：`today` 在 W3.2 换掉了 `notifications.log`，`recent` 没换。
而 `notifications.log` 全项目只有 `channels._send_log` 写——也就是「写入本地日志」
通道。用户关掉它，「最近通知」永久为空，空态还写着「**还没收到通知**」。
通知其实送到了。

**裁定（2026-10-28）**：`recent` 与 `today` 同源，读 `notify-*.log` 的 `event=` 汇总行。

| 项 | 取值 |
|---|---|
| 文件 | `notify-{今天}.log` + `notify-{昨天}.log`，两个都读 |
| 行 | `_EVENT_LINE` 锚定 `event= kind= sent= remote_ok= elapsed= [title=]` |
| 跳过 | `kind == "test"`（测试正文不是通知） |
| 成败 | `remote_ok`（不是 `sent`，理由同 D14） |
| 跨天 | 昨天那份带 `day="yesterday"`，前端拼「昨天 23:50」 |
| 数字 | **一个都不许再喂给 `notifications.log`** |

### 为什么读两天

只读今天，跨零点之后界面上只剩凌晨那几条，昨晚的全部消失——用户会以为丢记录。
读两天能把「昨晚跑到一半、今早来看」这个最常见的场景接住。

### 为什么 `day` 由后端算

前端只做字符串拼接（`dayLabel(day) + hhmm(time)`），不做日期比较。
一旦前端自己算「这条是不是昨天」，时区、夏令时、跨月全部要自己处理一遍，
而 Python 那边已经有 `datetime.date.today()`。

### `notifications.log` 还留着

它仍然是「写入本地日志」通道的产物，仍然供人肉排查用（正文完整、可 `tail`）。
**只是不再是任何界面上数字的来源。** 写侧一行没改。

## D18 · 「最近一次」的时间范围

**问题**：W3.5 把 `recent` 改成读今天+昨天，其他所有「最近一次」语义仍是单日。
零点一过，界面失忆。

**三条实测（临时目录 + 真机）**：

```
① 昨天 3 成功 2 失败 + 今天 1 成功 → stats() = ok 4 / fail 2     应为 1 / 0
② 真机 logs/（今天 29 条投递行，昨天 39 条）→ fail=66           今天真实失败 27
③ 昨天 23:50 全失败、今天没发过
   chain_sentence → ('…送到你手机', 'ok')      ← 绿点回来了
   channel_state  → ('已启用', 'ok', True)      ← 绿点回来了
```

第 ③ 条是 R16 的复发：R16 修的是「有记录且失败」，零点一到记录归零，绿点回来。
而「昨晚跑了一夜，早上来看」是用户最常做的事。

**裁定（2026-10-28，PM 决定）**：

| 概念 | 字段 | 时间范围 |
|---|---|---|
| 今日通知 | `today` | 只今天 |
| 通道成功 / 失败 | `ok` / `fail` | 只今天 |
| 最近通知 | `recent` | 今天 + 昨天 |
| 最后发送时间 | `last` | 今天 + 昨天，取最近一条 |
| 投递健康 | `delivery_health` | 跟着 `last` 走 |

> **计数问「今天做了多少」，状态问「上次怎么样」。**
> 混用就会出现「今日通知 2 / 通道失败 66」这种读不出结论的卡。

### 为什么 `today` 不跟着读两天

它叫「今日通知」。改成两天，名字就是假话，而且用户没法知道「今天到底发了多少」。
跨天的需求由 `recent` 和 `last` 承接，各管一件事。

### 为什么日期判断只在取数层

`channel_state()` / `delivery_health()` 收到的是「某条通道最近一次记录」，
不该知道这个记录来自几个文件。日期是 `_last_send_times()` 的事——
它读几个文件、怎么覆盖，是它自己的实现细节。判定层加日期判断，
等于把「取数」和「判定」重新搅在一起，那是这一整段反复出问题的原因。

### 连带：`last` 的展示要带「昨天」

`channels_list().last` 从 `"23:50"` 变成 `"昨天 23:50"`（昨天的记录）。
不标的话，昨天 23:50 和今天 00:10 在界面上都是 `23:50` / `00:10`，用户以为是同一类东西。

## D19 · 一条通道要存两种事实

**问题**：W3.5 §3 声明了「时间用测试记录、成败不用」，但 `_last_send_times()`
返回的是**一条**记录——一个槽位同时装 `time` 和 `ok`，两个消费者要的答案相反，
物理上做不到。

**两个实测（临时目录）**：

```
面 1  今天只有一次测试失败
      channel_state()   → ('最近一次失败：errcode=40037', 'danger', True)   红
      delivery_health() → 'none' → chain_sentence ('…送到你手机', 'ok')     绿
      ← 同一个界面上下矛盾

面 2  昨天真实失败 + 今天一次测试
      _last_send_times() = {'wxmp': {'time':'08:00','day':'today','ok':False,'test':True}}
      delivery_health() = 'none' → 侧栏回绿
      ← 今天的测试记录**遮蔽**了昨天的真实失败，R25 修好的东西被打回原形
```

**裁定（2026-10-28，PM 决定）**：一条记录装两种事实，两个槽。

| 事实 | 来源 | 消费者 |
|---|---|---|
| 什么时候试过（含测试） | 最近一条记录 → `time` / `day` / `test` | 通道列表的「最后发送」、状态页 `last` |
| 真实投递成不成 | 最近一条**非测试**记录 → `ok` / `msg` / `ok_day` | `delivery_health()` / `channel_state()` |

**`ok` 是三态**：`True` / `False` / `None`。
`None` = 「真实投递一次都没发生过」，不是成功也不是失败。

所以判定必须写 `is False`，不能写 `not last.get("ok")`——`None` 是 falsy，
只有测试记录时会把「没发生过」误判成「失败了」。

### 为什么不用两个函数

可以拆成 `_last_send_times()` 和 `_last_real_send_times()`，各读一遍日志。
不这么做：两个函数读同一批文件，早晚有一处改了另一处没改——这正是
`_CHANNEL_LINE` / `_LOG_CHANNEL` 两份正则已经带来的维护成本（R26）。
一个函数返回两个槽，至少「读哪些文件」这件事只有一处。

### 连带：`ui.py` 补上 `last`

`ui.py:438` 一直调 `insight.chain_sentence(self.cfg)` 没传 `last`，
W3.4 的降级只覆盖了 web 侧。结构变了以后更该同步，一行。
