## 0. R39 的定性

W4.1 在通道页复核时挖出来的，**是 W4 自己引入的缺陷，不是历史遗留**。

```
channels.css:325   @media (max-width: 820px) { .fields { … } }   ← 旧规则没删
shell.css:744      @media (max-width: 760px) { .fields { … } }   ← 断点写成了 760
```

后果：CSS 视口 **761–820** 这一段，通道页落成一列、触发页和模板页还是两列。
用户把窗口拖到那个宽度，会看到两个页面的表单宽度不一样。

**为什么像素比对没抓到**：W4.1 的比对是在 973px 视口下做的，那个宽度两份规则都不触发。
**像素相同只能证明「这一个视口下相同」，不能证明「规则相同」。**

**为什么 820 是对的、760 是编的**：820 在 `channels.css` 上面有一段完整推导——

```
973 时表单栏 = 973 - 64(内边距) - 240(列表) - 24(间距) = 645，两列各 310，
装得下 appID 这种 20 多字符的值；窗口缩到 880 时 CSS 视口 726，
表单栏只剩 398，两列就挤了 —— 断点定在 820。
```

760 没有任何推导，是搬家时顺手写的。**数字和它的理由必须一起搬**——
只搬数字，下一个人就没法判断该不该改，于是随手改。

### 0.1 先说清一件事：两个页面的可用宽度本来不一样

我按 `.fields` 的真实使用方核了一遍（只有两个页面用它，模板页不用）：

| 页面 | 表单可用宽度 | 两列什么时候开始挤 |
|---|---|---|
| 通道页 | 视口 − 64 内边距 − 240 列表 − 24 间距 | 820 以下就挤（这就是 820 的来历） |
| 触发页 | `min(720, 视口 − 64)`，**没有左侧列表** | 760 以下才开始挤 |

所以「一个断点服务两个页面」本身就有张力：820 对通道页是刚需，对触发页偏保守
（820 时触发页表单还有 720 宽，两列各 348，完全装得下）。

**这一轮的选择：统一用 820，接受触发页在 761–820 区间提前落成一列。**

理由：保守方向的代价是「一个数字输入框铺满 720 宽」，难看但不坏；
反方向（统一 760）的代价是通道页两列各 234px，装不下 appID 这种 20 多字符的值，
**是坏**。两害相权。

> **不要因为「触发页 820 太早」就把断点拆成两档。** 拆档意味着两个选择器
> （比如 `.page-channels .fields` 820 / `.fields` 760），那是两个数字、两份理由，
> 60px 的收益换一份长期维护负担，不值。**如果将来真要拆，先在这里写清楚再动手。**

## 1. 修 CSS（两处）

### 1.1 `channels.css`：删掉残留

删 `channels.css:325` 那条 `@media (max-width: 820px) { .fields … }`，
连同它上面那段推导注释**一起搬到 `shell.css`**（不要留在 channels.css 里当"历史"）。

搬完 `channels.css` 里不许再出现 `.fields`（注释里提到可以，选择器不行）：

```bash
grep -nE "^\s*\.fields" webui/assets/channels.css     # 必须为空
```

### 1.2 `shell.css`：断点改回 820 + 带上理由

```css
/* ---- 窄窗口：字段落成一列 ------------------------------------------------
   断点按 **CSS 视口** 算，不是窗口逻辑像素：本机 1180×780 的窗口，
   CSS 视口只有 973×621（TextScaleFactor 120% × DPI 200% = dpr 2.4）。
   973 时表单栏 = 973 - 64(内边距) - 240(列表) - 24(间距) = 645，
   两列各 310，装得下 appID 这种 20 多字符的值；窗口缩到 880 时
   CSS 视口 726，表单栏只剩 398，两列就挤了 —— 断点定在 820。

   **这个数不许单独改。** W4 搬家时把 820 写成 760 且没搬这段注释，
   结果 761–820 区间通道页一列、另两页两列（R39）。 */
@media (max-width: 820px) {
  .fields { grid-template-columns: minmax(0, 1fr); }
}
```

## 2. 加一条防漂移测试（这一轮真正的产出）

手工比 69 条声明找到了这一处，但**手工比对不会在下次搬家时自动再跑一遍**。

放在 `tests/test_guide_copy.py`（这个文件已经是「静态检查 CSS/JS 文本」的家），
或者新建 `tests/test_css_single_source.py`——二选一，别塞进 `test_bridge_w4.py`（那是契约测试）。

```python
def test_no_selector_defined_in_two_stylesheets():
    """同一个选择器不许在两个样式表里各定义一次。

    为什么：W4 把 `.field` 整族从 channels.css 搬到 shell.css，69 条声明搬对 68 条，
    漏下的那条是 `@media (max-width: 820px) { .fields … }`，而 shell.css 里
    写成了 760。两份规则同时存在时，谁生效取决于加载顺序 + 视口宽度，
    像素比对在默认视口下看不出任何异常（R39）。

    **零白名单。** 这个项目里没有「故意在两个文件定义同一个选择器」的合法场景。
    """
```

实现要求：

1. 只扫 `webui/assets/shell.css` 与 `webui/assets/channels.css`（`tokens.css` 只有变量，不扫）
2. **必须剥掉注释再解析**（注释里会提到 `.fields`，不能算定义）
3. **必须跳过 `@keyframes` 内部**（`from` / `to` / `50%` 不是选择器）
4. 报错信息要给出：选择器、在 A 文件的哪一行、在 B 文件的哪一行——**只报名字等于让人再找一遍**
5. 正则解析要**括号配平**，不许用 `[^}]*`（`@media` 嵌套会把它切断）

## 3. 边界视口证据（不是默认视口）

W4.1 的教训是「只在一个视口下比像素」。这次要在**断点两侧**各取一张：

| 视口（CSS px） | 期望 |
|---|---|
| **780**（820 以内） | 通道页、触发页的 `.fields` **都是一列**（模板页不用 `.fields`，不参与） |
| **900**（820 以外） | 通道页、触发页都是**两列** |

取证方式二选一，用能给出**数字**的那种：

- 在页面里 `getComputedStyle(document.querySelector('.fields')).gridTemplateColumns`，
  数里面有几个值（`"321px"` = 1 列，`"310px 310px"` = 2 列），两页各报一次；
- 或 `getBoundingClientRect()` 比两个 `.field` 的 `top` 是否相等。

**不要只交截图。** 截图要人眼数格子，数字不用。截图附上作为旁证即可。

如果窗口最小宽度限制了 780（`min_size=(880,600)`，CSS 视口 ≈726），
就用 DevTools 的设备模拟或直接改窗口尺寸试；实在不行，用
`webview.create_window(width=…)` 临时起一个测试窗口，**测完还原**。
