## 0. 先定调：975 接受，数值不再动

W4.3 把 950 改成 975，理由成立（950 会留下 951–969 一段仍被切的窗口）。我复核了拟合公式：

```
通道页 .fields = 视口 − 632     两列各 (视口 − 648) / 2
触发页 .fields = min(720, 视口 − 314)
```

用你给的 9 个实测点回代，误差全在 1px 内。**632 / 314 / 318 是对的，我任务书里的
631 / 304 / 327 是错的**——304 漏了 `.content` 的 10px 滚动条，327 的差额跟着错。

**975 定案，这一轮不许再改这个数。** 理由：

- 它是第 3 次调同一个断点（W4.2 820 → W4.3 975 → 再来一次就是第 4 次）。
  W3 教训第 7 条：**同一层修三次，停下来换结构，不要修第四次。**
- 结构性的答案已经找到了，但不属于这一轮，见 §3 的 R40。

**但有一件事要说清**：默认窗口是 `1180×780` → CSS 视口 973，而 973 < 975，
所以**用户一打开软件，通道页就是一列**。这是本轮的设计变化，不是副作用。
你汇报里说「这是设计变化」是对的，但**理由写错了**：

> 「之前 163px 的两列其实还能勉强装下 appID，只是模板 ID 和 openid 已经贴着边了」

模板 ID / openid 都是 14 字符，按 appID 实测的 8.89px/字符算约 124px，
在 161px 的框里还剩 37px——**不贴边**。真正贴边（零余量）的只有 appID 那一个。
理由要写准，否则下一个人会以为「三个字段都危险」，进而做错决定。

## 1. 守卫有个真窟窿（我实测出来的，不是推测）

W4.3 的 `test_channels_breakpoint_is_wider_than_generic` 用了**乐观聚合**：

```python
generic_max = min(mw for mw, _ in generic)   # 通用：取最小
scoped_max  = max(mw for mw, _ in scoped)    # 通道：取最大
gap = scoped_max - generic_max
```

两个方向都往「通过」那边取。我用临时目录复现了三种情况，**两条测试全绿**：

| 往 `shell.css` 末尾追加 | 单源测试 | 断点测试 |
|---|---|---|
| `@media (max-width: 820px) { .fields … }` | 绿 | 绿 |
| `@media (max-width: 820px) { body[data-route="channels"] .fields … }` | 绿 | 绿 |
| `@media (max-width: 1400px) { body[data-route="channels"] .fields … }` | 绿 | 绿 |

第一行就是 **R39 的原始形状**——同文件、同选择器、低断点。`test_no_selector_defined_in_two_stylesheets`
只管**跨文件**，同文件重复它不看；断点测试又因为 `min()` 把它吞了。
**R39 可以原地复活，两条守卫都不会叫。**

复现脚本（你可以直接用，不用改仓库文件）：

```python
import pathlib, shutil, tempfile, sys
sys.path.insert(0, 'tests')
import test_css_single_source as t
tmp = pathlib.Path(tempfile.mkdtemp())
for n in ('shell.css', 'channels.css'):
    shutil.copy(f'webui/assets/{n}', tmp / n)
(tmp / 'shell.css').write_text(
    (tmp / 'shell.css').read_text(encoding='utf-8')
    + '\n@media (max-width: 820px) {\n  .fields { grid-template-columns: minmax(0,1fr); }\n}\n',
    encoding='utf-8')
t.ASSETS = tmp
t.test_channels_breakpoint_is_wider_than_generic()   # 现在是绿的
```

## 2. 修法

### 2.1 断言「每个选择器只能有一条 max-width 规则」

这是根因。有两条时，谁生效取决于书写顺序，任何聚合方式都是在猜。

```python
def test_each_fields_rule_has_one_breakpoint():
    """`.fields` 的两个窄窗规则各自只能有一条断点。

    有两条时，谁生效取决于书写顺序 + 视口，聚合（min/max）只能猜——
    W4.4 实测：同文件再加一条 `@media (max-width: 820px) { .fields … }`
    （R39 的原始形状），单源测试和断点测试**双双绿**。
    """
```

断言：`[(mw, sel) …]` 里，`.fields` 出现 1 次、`body[data-route="channels"] .fields` 出现 1 次。
报错给出全部出现的行号。

### 2.2 聚合改成保守方向

```python
generic_max = max(mw for mw, _ in generic)    # 「不许太高」→ 取最大
scoped_min  = min(mw for mw, _ in scoped)     # 「不许太低」→ 取最小
gap = scoped_min - generic_max
```

含义变成「最坏情况下差多少」。配合 2.1 的「只能一条」，两条断言互相兜底。

### 2.3 清掉测试里的过期数字

| 位置 | 现在 | 改成 | 依据 |
|---|---|---|---|
| docstring 第 2 行 | 「差 327px（240 列表 + 48 内边距 + 24 间距 + 15 滚动条）」 | 「差 318px」+ 与 `shell.css` 注释同一组分解 | 实测拟合 |
| 通用断点报错信息 | 「可用宽度宽 327px」 | 318px | 同上 |
| 差值报错信息 | 「appID 这类 15 字符的值」 | 「appID 这类 18 字符的值」 | 实测 appID 18 字符 |

**这不是挑字眼。** 你上一轮刚把 CSS 注释里的两套数字合并成一套，
测试里又留了另一套（327 / 15）——下一个人读测试 docstring 得到的结论
会和读注释得到的相反。同一件事只能有一个说法。

### 2.4 注释补一句「973 落一列是有意的」

在 `shell.css` 那段注释的 975 段落后加：

```
   975 > 973（默认窗口 1180×780 的 CSS 视口），所以**一打开软件通道页就是一列**。
   这是有意的：972 也能让 973 保持两列（列宽 162.5、appID 零余量 1.2px），
   但「刚好装下」正是 R39 那一类问题的土壤——换台机器、换个更长的 appID 就又截断。
   宁可少一列，不要一个零余量的状态。

   真要两列：把 975 改成 972，同时接受 appID 在 973 时只剩 1px 余量。
   更深一层的修法见 roadmap R40（长字段跨列）。
```

## 3. 记 R40（结构性答案，W6 评估）

`shell.css` 里早就有 `.field[data-span="2"] { grid-column: 1 / -1; }`，
但 `channels.js:470` 只给 `textarea` 用了。appID / appsecret / 模板 ID / openid / url
都是长值，**它们的问题不是「视口窄」，是「内容长」**——用视口断点治内容问题，
就是这三轮的来历。

R40 内容：

| 字段 | 说明 |
|---|---|
| 症状 | 通道页在窄视口把长值字段压成 126–162px，appID 被切；靠调断点治，治了三轮 |
| 根因 | `.fields` 两列网格假设「一列装得下一个字段」，但 appID 18 字符需要 ≥161px，两列在 973 视口只有 162.5 |
| 现成机制 | `.field[data-span="2"]` 已存在，只有 `textarea` 用；`channels.py` 的字段元组可加一个 `span` 位 |
| 建议 | 长值字段 `span=2`，宽视口下也跨列（或只在 `max-width` 区间跨列）。做完之后断点可以退回通用 760，**两个断点合并成一个** |
| 风险 | 动 `channels.py` 字段元组会影响 `channels_meta()` 的消费方（`test_bridge.py` 有断言），W6 一起做 |
| 谁做 | W6（布局/可访问性复核那一轮），**W4.4 不做** |
