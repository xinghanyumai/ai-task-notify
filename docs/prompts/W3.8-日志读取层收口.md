## 1. 第一步（W3.8a）：建层，**行为一个字都不许变**

### 1.1 新建 `wbn/logs.py`

```python
"""日志读取层：全项目唯一读 `notify-*.log` 的地方。

职责边界：**只做文本 → 结构**。什么算成功、要不要降级、显示什么文案，
全部属于 `insight`，这里一概不管。

为什么单独一层：W3 到 W3.7 七轮修复全部落在这个边界上，因为解析逻辑
分散在 `insight.stats()` 和 `bridge._last_send_times()` 两处、用三份正则、
各自决定读几天。每加一个消费者就暴露一次不一致——W3.6 的
「`ok`/`fail` 跨天累加」就是两份实现各有一套时间口径的直接后果。
"""

from dataclasses import dataclass


@dataclass(frozen=True)
class Delivery:
    """一次投递尝试。"""
    time: str        # "08:00"
    day: str         # "today" | "yesterday"
    channel: str
    ok: bool
    msg: str         # 已 redact，已截断 120 字
    test: bool


@dataclass(frozen=True)
class Event:
    """一条事件汇总行（`pipeline.notify()` 写的）。"""
    time: str
    day: str
    event: str
    kind: str
    sent: bool
    remote_ok: bool
    title: str       # 已剥掉开头 emoji


@dataclass(frozen=True)
class ChannelFacts:
    """一条通道的**两件事实**（D19）。"""
    time: str                  # 最近一条，含测试
    day: str
    test: bool
    ok: bool | None            # 最近一条**非测试**；None = 真实投递一次都没发生过
    msg: str
    ok_day: str | None


@dataclass(frozen=True)
class Facts:
    events: tuple[Event, ...]         # 两天，时间升序
    deliveries: tuple[Delivery, ...]  # 两天，时间升序

    def events_of(self, day: str) -> tuple[Event, ...]: ...
    def deliveries_of(self, day: str, *, remote_only: bool = False) -> tuple[Delivery, ...]: ...
    def last_by_channel(self) -> dict[str, ChannelFacts]: ...
    def recent(self, limit: int = 8) -> tuple[Event, ...]: ...


def read(days: int = 2) -> Facts:
    """读最近 `days` 天的日志。文件不存在就当那天没有数据，不抛。"""
```

**`Facts` 的四个方法就是全部口径的定义处。** 现在散在循环里的
「只算今天」「排除 log」「排除测试」「remote_ok 才算送到」，全部搬到这里，
**每个口径只写一次**。

### 1.2 改两个消费者

```python
# insight.stats(cfg)  —— 签名不变
def stats(cfg: dict) -> dict:
    facts = logs.read(days=2)
    today_events = facts.events_of("today")
    remote = facts.deliveries_of("today", remote_only=True)
    return {
        "today": sum(1 for e in today_events if e.remote_ok),
        "ok": sum(1 for d in remote if d.ok),
        "fail": sum(1 for d in remote if not d.ok),
        "channels": len(config.enabled_channels(cfg)),
        "recent": [...],      # 用 facts.recent(8)，结构保持 {time, day, channel, summary, ok}
    }
```

```python
# bridge._last_send_times()  —— 函数名保留，改成薄封装
def _last_send_times() -> dict:
    return logs.read(days=2).last_by_channel()
```

**为什么保留这两个函数名**：312 个测试直接调它们，`ui.py` 也调 `stats`。
第一步不许改测试、不许改调用方——这是判断「搬家是否忠实」的唯一标准。

## 2. 第二步（W3.8b）：矩阵，穷举而不是列举

### 2.1 三个维度

| 维度 | 取值 |
|---|---|
| 数据分布 | 今天有 / 只有昨天 / 两天都有 / 两天都无 |
| 记录类型 | 无 / 只有测试 / 只有真实 / 测试+真实 |
| `log` 通道 | 开 / 关 |

**4 × 4 × 2 = 32 格。** 用 `pytest.mark.parametrize` 展开，一格一个用例。

### 2.2 每格断言什么

六条不变量（对每格都成立）：

```python
def invariants(facts, cfg):
    today_events = facts.events_of("today")
    remote = facts.deliveries_of("today", remote_only=True)
    s = insight.stats(cfg)

    assert s["today"] == sum(1 for e in today_events if e.remote_ok)
    assert s["ok"] + s["fail"] == len(remote)
    assert s["ok"] == sum(1 for d in remote if d.ok)

    # recent 的每一条都能在 events 里找到
    for row in s["recent"]:
        assert any(e.time == row["time"] and e.day == row["day"]
                   for e in facts.events), row

    # 只有测试记录 → ok 必须是 None
    for ctype, cf in facts.last_by_channel().items():
        if cf.ok is not None:
            assert any(d.channel == ctype and not d.test
                       for d in facts.deliveries), ctype

    # Facts 只由文件决定
    assert logs.read(days=2) == facts
```

再加每格的具体出口值（`chain_sentence` 的 level、`channel_state` 的等级）。

### 2.3 矩阵必须能复现那七个历史 bug

**这是矩阵是否完整的唯一客观检验。** 用 `git stash` 或临时切到旧提交，
在旧代码上跑矩阵，下面七格必须红：

| 历史 bug | 对应的格 |
|---|---|
| W3.1 测试发送进统计 | 记录类型=只有测试 × log=开 |
| W3.2 `today` 依赖 log 通道 | 数据=今天有 × log=关 |
| W3.3 `log` 冒充投递 | 记录类型=只有真实 × log=开 |
| W3.4 界面替失败背书 | 记录类型=只有真实（失败） |
| W3.5 `recent` 依赖 log 通道 | 数据=今天有 × log=关 |
| W3.6 跨天累加 / 零点失忆 | 数据=只有昨天 |
| W3.7 测试遮蔽真实投递 | 记录类型=测试+真实 × 数据=只有昨天 |

**某一格在旧代码上不红 = 那一格没覆盖到**，矩阵要补。

### 2.4 变异测试（第 5 条收敛条件）

往日志里塞脏行，看会不会崩、会不会误算：

```
[10:00:00] channel=bark ok=True msg=upstream said ok=False but we won
[10:00:01] channel=bark ok=False msg=server replied ok=True in body
[10:00:02] channel=bark ok=False msg=upstream said channel=log failed
[10:00:03] event=Stop kind=task_done sent=True remote_ok=False
[10:00:04] channel=                    ← 缺通道名
[10:00:05] 完全不是日志的一行
[10:00:06] channel=bark ok=True msg=<120 字以上的超长串>
```

期望：不抛异常；`ok=1 fail=1`（第一条成功、第二条失败）；`msg` 里提到
`ok=False` / `channel=log` 的都不影响判定；脏行静默跳过。

## 3. 第三步（W3.8c）：一次加载只读一遍

现在状态页加载会 `stats()` + `chain_sentence()` + `channels_list()`，
每个都自己 `logs.read()`。改成 bridge 里缓存一份 `Facts`：

```python
def _facts(self) -> logs.Facts:
    """一次页面加载共用一份。文件按 mtime 失效，不是按时间失效——
    用「缓存 5 秒」会让用户点完测试立刻刷新时读到旧数据。"""
```

验收：加计数器，一次 `stats_today` + `chain_sentence` + `channels_state`
调用序列，`logs.read` 只被调 **1** 次。

**这一条是判断「中间层有没有真的起作用」的标志。** 如果还是读两遍，
说明 `Facts` 只是个形式，消费者还在各自读文件。

## 4. 不许做的事

1. **第一步不许改任何测试。** 312 个必须原样全绿。
2. **不许在 `logs.py` 里做业务判断。** 它不知道「log 通道不算投递」，
   那是 `remote_only=True` 这个参数的含义，由调用方决定。
3. **不许为了过矩阵去放宽断言。** 矩阵红了就是代码错，不是用例错。
   （例外：用例本身写错了——那要在 commit message 里说明旧断言错在哪。）
4. **不许在矩阵之外「顺手」再修别处。** 发现新问题记 roadmap，W4 再说。
5. **不许把 `stats()` / `_last_send_times()` 的函数名改掉。** 312 个测试和
   `ui.py` 都直接调它们。
