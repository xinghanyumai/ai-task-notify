## 0. 为什么单独开一段

W3 汇报里有一句：

> 点侧栏「运行状态」：**页面正常切换**，统计里「通道失败」从 4 跳到 5
> （说明那次测试真的发出去并失败了）

**这句话是对的，但它证明的东西是错的。** 那个 `+1` 不是"测试真的发出去了"的证据，
它是一条 bug 在计数：手动点「测试此通道」被记进了今日统计。

现场（2026-10-28，本机，未做任何清理）：

```
$ python -c "from wbn import config, insight; s=insight.stats(config.load()); print(s['today'], s['ok'], s['fail'])"
今日通知=7  成功=7  失败=6        ← 7 + 6 = 13 > 7
$ grep -c "test channel=" logs/notify-2026-10-28.log
3
```

三个数各自都对，放在一起就是自相矛盾的。

## 1. 修统计隔离（§3.5）

### 1.1 根因链

```
pipeline.send_test()
  └─ store.log(f"test channel={ct} ok={ok} …")
       └─ 写 logs/notify-YYYY-MM-DD.log        ← 和真实发送同一个文件
            └─ insight.stats() 解析它
                 └─ if "channel=" not in line: continue     ← "test channel=" 命中了
```

`stats()` 的 docstring 写的是「只数 `channel=` **开头**的行」，代码写的是「**包含**」。
**文档和代码对不上，所以这条一直没人发现。**

### 1.2 改法（两条选一条，不许都不做）

- **A（推荐）**：`send_test` 的日志行改成 `test-send type=bark ok=False msg=…`，
  不含 `channel=` 子串。零过滤逻辑改动。
- **B**：`stats()` 里显式跳过 `test ` 开头的行。

选 A 的理由：`stats()` 的过滤条件越少越不容易错，而且日志 tail 里 `test-send`
比 `test channel=` 更一眼能认出是测试。

### 1.3 必须一起做的三件事

1. **docstring 对齐**：改完 `stats()` 的过滤表述，要能逐字对上代码。
   别再写「开头」而代码用 `in`。
2. **回归测试**：临时日志里塞 `test-send … ok=False` 一行 + `channel=bark ok=False` 一行，
   断言 `fail == 1`。放在 `tests/test_insight.py`。
3. **日志里留着测试行**，只是不进统计——用户排查"我点了测试为什么没反应"时需要看它。

## 2. 修超时口径（§3.4）

### 2.1 现在的账

| 位置 | 值 | 来源 |
|---|---|---|
| `_get_json`（取 access_token） | 10s | `wbn/channels.py` 默认参数 |
| `_post_json`（发消息） | `http_timeout`，默认 8s | `config.advanced.http_timeout` |
| 微信测试号后端最坏耗时 | **18s** | 10 + 8 |
| 前端 `TEST_TIMEOUT` | **10s** | `channels.js:38` 写死 |

前端比后端短 8 秒。后果不是"多等一会"，是**反向说谎**：

```
t=0    点测试
t=10   前端超时 → dropCb(cb) → 显示「等待超时」
t=18   后端其实成功了 → _push() → cbMap 里已经没有这个 id → 静默丢弃
```

用户看到的失败是假的，真实结果永远到不了屏幕。而 `_push()` 里 `if not h: return`
正是 W3 写的"已经超时放弃了"——**这段兜底逻辑是对的，错的是它被触发的时机。**

### 2.2 改法

```js
TEST_TIMEOUT = (10 + http_timeout + 2) * 1000      /* 下限 20000 */
```

`http_timeout` 由 `channels_meta()` 一并下发，前端**不自己读 config、不自己猜**。
`http_timeout` 改成 3 → 前端超时变 15s→ 实际是 20s（下限兜住）。

顺带：`insight.py` 里那两个 10 / 8 是魔数，提到模块级常量并在注释里写清
「改这里要同步改前端超时的推导」。

## 3. 补 W2 欠的第 8 条：焦点环

W2 验收第 8 条要求「所有可交互元素都有 `:focus-visible` 焦点环」。
W3 补了 `.chan-row` / `.field-reveal`，**还差两处**：

- 主题分段控件（浅色 / 深色 / 跟随系统）
- 所有按钮（主按钮、次按钮、危险按钮）

全局 `:focus-visible { outline: … }` 不算过关——它的对比度没量过，
而且在深色底上可能只有 1.2:1。要求：

1. 每个可聚焦元素都有**可测量**的焦点环，对所在底色 ≥ 3:1（WCAG 2.4.11）。
2. 键盘走一遍整页（Tab 到底再 Shift+Tab 回来），焦点顺序 = 视觉顺序。
3. 焦点环不许只靠颜色区分（`outline` + `offset` 两者都要）。

## 5. 验收（4 条）

| # | 验收项 | 标准 |
|---|---|---|
| 1 | 统计隔离 | 连点 3 次测试（含 1 次失败）→ `stats_today()` 的 `ok`/`fail` **一个都不变**；`tail_log()` 里能看到这 3 行 |
| 2 | 统计不误伤 | 真发一条通知（`selftest.py`），`fail` 该 +1 就 +1。**证明过滤没把真行一起滤掉** |
| 3 | 超时派生 | `http_timeout=8` → 前端 20s；改成 3 → 前端 20s（下限）；改成 20 → 前端 32s。三个值贴出来 |
| 4 | 焦点环 | 主题分段 + **全部两种按钮**（`btn-primary` / `btn-secondary`）的焦点环对比度实测值（对所在底色），全键盘走一遍截图 |
| 5 | `today` 不依赖通道开关 | 临时目录里关掉 `log` 通道再真发一条，`today` 仍 +1 |

第 1 和第 2 条必须**成对**做。只做第 1 条，你不知道自己是不是把真行也滤了——
这就是「修完真问题还抓得到吗」的尺子。

> **勘误**：本任务书初稿写「三种按钮（主/次/危险）」，是照抄通用设计系统的惯性。
> 实际代码里只有 `btn-primary` / `btn-secondary`，**没有也不该有** `.btn-danger`——
> 唯一有破坏性的操作是「清空日志」，而它在 W4 才出现。执行者没有为了凑数造一个
> 按钮，判断正确。

## 5.1 验收时冒出来的第 4 个数

改完前三条后，「今日通知」还是会被测试污染——因为 `today` 数的是
`notifications.log`，而**「写入本地日志」这个通道把正文写进那个文件**，
测它一次就等于记一条通知。按 `kind == "test"` 排掉即可（`render_message` 传的
事件名，真实事件永远不会叫这个）。

**但这暴露了更深的一层**：`today` 的数据源是 `log` 通道的副产物，
`ok` / `fail` 的数据源是 `notify-*.log`。**两个数据源，其中一个用户能关。**

```
关掉 log 通道 → notifications.log 不再增长 → 今日通知冻结
              但 通道成功 / 通道失败 继续涨
```

第 5 条验收就是钉这个。正确数据源见 `architecture.md`「统计口径」最后一节：
`notify-*.log` 里每个事件一行 `event=… sent=True`，由 pipeline 写，与通道开关无关。
