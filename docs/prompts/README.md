## 1. Skill 分工（三层，不混在一起）

**原则：一条提示词只配一个「主执行 skill」和一个「审查 skill」。**
主执行负责把事做出来，审查负责挑毛病。两者判据不同，混在同一个 skill 里必然有一头被牺牲。

### L1 · 主执行层（做这件事）

| Skill | 它真正负责什么 | 用在哪 |
|---|---|---|
| `frontend-design` | 视觉方向、排版、配色、版式的**判断与取舍**。核心是"不做模板默认值" | P1 |
| `impeccable` | UI/UX 全流程：布局、动效、微交互、空/载/错三态、设计系统 | P1、P3 |
| `systematic-debugging` | 定位根因，禁止猜。先复现再改 | P0、P2 |
| `ponytail-audit` | 全仓过度设计审计，按"该删多少"排序 | P4 |
| `deprecation-and-migration` | 删旧、迁路径、分阶段下线，保证不中断 | A1、A2、P4 |
| `tdd` | 测试先行，把"能打勾的清单"变成"能跑的断言" | P0 |

### L2 · 质量审查层（检查这件事）

| Skill | 它真正负责什么 | 用在哪 |
|---|---|---|
| `impeccable`（审查模式） | a11y、WCAG、动效、响应式、设计评审 | P1、P3 |
| `ui-ux-pro-max` | UX 规则库：对比度、焦点环、Tab 顺序、触控尺寸 | P3 |
| `code-review-and-quality` | 代码质量、可维护性、是否越界改动 | A2、P0、P2、P5 |
| `ponytail-review` | diff 级过度设计检查 | P4 |

### L3 · 辅助支撑层

| Skill | 用在哪 |
|---|---|
| `documentation-and-adrs` | P5（ADR、README、CHANGELOG） |
| `ci-cd-and-automation` | P5（CI 门禁、ruff、pytest） |
| `context-engineering` | 全程（跨轮次上下文管理） |

### ⛔ 明确排除的 skill（**必须看这一节**）

| Skill | 为什么**不**用 |
|---|---|
| **`brand-guidelines`** | **这是最容易踩的坑。** 它是 **Anthropic 官方品牌规范**：Poppins 标题 + Lora 正文 + 暖色底 `#faf9f5` + 橙 `#d97757`。本项目已定为**中性灰阶 + ink 主操作色**，套上去直接打架。更关键的是 `frontend-design` 把 `#d97757` 明确列为"AI 生成感"的特征之一（原话："Anthropic's own Claude-interaction accent, so on a user's brief it reads as a tell"）。**用它审查 = 把项目往模板化方向推。** |
| `browser-testing-with-devtools`、`playwright-cli` | 本项目是 Tkinter 桌面程序，没有浏览器 |
| `workbuddy-pptx`、`workbuddy-docx`、`workbuddy-sheet-*` | 本项目不产出 Office 文档 |
| `web-access`、`multi-search-engine` | 不涉及联网检索 |
| `humanizer`、`caveman`、`grilling` | 与任务无关 |

### ⚠️ Tkinter 项目的 skill 适配边界

`frontend-design` / `impeccable` / `ui-ux-pro-max` 三个 skill **都是 web 导向的**（HTML/CSS/React）。
用在这个项目上，**只能取原则，不能取实现**：

| 能取 | 不能取 |
|---|---|
| 排版层级、行宽控制、字重选择 | CSS 写法、Tailwind class、React 组件结构 |
| 配色层次、语义色用法 | 大面积渐变、背景模糊、真阴影 |
| 渐变/光晕的**用法判断**（用在哪、用多大） | CSS `linear-gradient` / `filter: blur()` 语法 |
| 动效节奏、缓动选择、时长上限 | CSS transition / keyframes 语法 |
| 留白与视觉节奏 | 响应式断点（Tkinter 只有窗口尺寸，没有媒体查询） |
| 空/载/错三态的设计语言 | 组件库、设计 token 的 JSON 导出 |

**注意「渐变」那一行**：Tkinter **能做**线性渐变（Canvas 逐线绘制），只是面积越大越慢。
所以 skill 里的渐变**思路可以取**，但要换成 Canvas 实现，并把面积压在 320×200 以内。
**模糊（blur）是真做不到**，别试。

**不写这条边界，执行方会照着 skill 写 CSS，然后发现一行都用不上。**

## 3. 可直接复制的提示词

按你给的 skill 模板结构组织：**执行 skill → 需求四要素 → 两条约束 → 审查 skill → 审查维度**。

### 这三层东西各管什么（**先读，否则 P0–P5 那些文件是死的**）

| 层 | 在哪 | 装什么 | 谁读、什么时候 |
|---|---|---|---|
| **任务指令** | 本节下面的代码块 | 做什么、范围多大、谁审查。**短到一眼看完** | 你粘进对话的第一句话 |
| **执行细节** | `P0-xxx.md` … `P5-xxx.md` | 步骤、白名单、验收命令、卡住时的分支判断、5 页版式图、12 条基线表 | AI 读完指令后**按路径去读** |
| **背景依据** | [`DECISIONS.md`](DECISIONS.md)、[`../repo-layout.md`](../repo-layout.md) | D1–D8 为什么这么定、回退边界在哪 | 有疑问时才查 |

**为什么不能合成一份**：一段 10 行的提示词装不下 250 行的执行细节——
P1 里 5 页的 ASCII 版式图、10 个交互的反馈要求、9 条动效时长，全塞进去提示词会变成 300 行，
你就没法一眼看出"这条到底要干什么"。

反过来，只有提示词没有文件也不行——**"12 条功能基线是哪 12 条""哪些文件不许动"
这类东西没法靠一句话交代清楚**，AI 只能自己编。

**所以每段提示词的第一句都写了 `@docs/prompts/PX-xxx.md`。**
这个 `@` 不是装饰：它让文件内容直接进上下文，AI 不用猜。
**如果你手抄时把这一句删了，那条提示词就只剩骨架，AI 会按自己的理解做——这正是上一轮跑偏的方式。**

## 4. 三条使用纪律

1. **一次只贴一条。** 做完贴验收输出就停，不要顺手续做下一条。上一条验收没过，下一条的产出就不可信。
2. **主执行和审查分开。** 不要让同一个 skill 既做设计又做验收——它会给自己的产出打高分。
3. **判据失效时停下来问，不要改尺子。** 上一轮就是在这里跑偏的：`tools/audit.py` 误报时直接改了审查脚本。
