## 1. 项目形态与角色

### 1.1 形态

| 项 | 定 |
|---|---|
| 产物 | **单个 `通知.exe`**，双击即用 |
| 技术 | pywebview + 系统 WebView2 + 原生 HTML/CSS/JS |
| 数据 | `config.json` / `logs/` / `state/` 在 **exe 旁边**（不可写时回落 `%LOCALAPPDATA%`） |
| 分发 | zip 绿色包，解压即用 |
| 不做 | 网页版、pip 包、自动更新、多用户、云同步 |

**"单 exe"是硬约束，它连锁改变四件事**（详见 roadmap §0）：

1. 6 个入口合并成 1 个 exe + 子命令。
2. `ROOT = Path(__file__).parent.parent` 失效（frozen 后指向 `%TEMP%`，退出即删）。
3. WorkBuddy 里已配的 hook 路径要迁移。
4. 老用户升级不能丢 `config.json`。

### 1.2 角色边界

| 谁 | 做什么 | 不做什么 |
|---|---|---|
| **PM（我）** | 拆任务、写提示词、定验收、维护依赖、阶段间质检 | **不写实现代码**、不跑重构 |
| 执行者（每条提示词里的 AI） | 按提示词实现、自测、按格式汇报 | 不改硬约束、不扩范围、不改检查器 |
| 你 | 拍板 D1–D12、验收每阶段 | — |

**PM 的产出只有四样**：提示词、路线图、决策记录、阶段验收单。

### 2.1 九条不能破的规则

1. **W7 之前的所有阶段都是开发态**（`python app.py`），不许提前打 exe。
   打包会掩盖问题，也会让每个阶段的迭代变慢 10 倍。
2. **每个 W 结束要停下来**，按该文件的「汇报格式」交作业，我验收后才进下一个。
3. **改判据 = 放水，改测量方法 = 让数据可信。** 后者可以做，但必须单独提交，
   并在 commit message 里写清"旧尺子检查了什么、新尺子怎么覆盖"。
   > 注意区分**改判据**和**修脚本 bug**：C0.1 时断链脚本因为不跳过代码块报了 13 条假断链，
   > 修它是修 bug 不是放水。判断标准：**修完以后，真的问题还抓得到吗？**
   > 假阳性修完真问题仍能抓到 → 是修 bug；阈值调低后真问题漏过去 → 是放水。
4. **删代码或改布局时，文档要同步改，且要用 `grep` 找散落副本。**
   同一句话往往散在多处（emoji 那条散在 README 1 处 + troubleshooting 2 处）。
   按清单逐条改完就收工，一定漏。**先 grep 关键词，搜到几处改几处。**
5. **每个 W 验收前，先做一次「断言审计」，再动手改。**
   把这一阶段界面/接口对用户说的**每句话、每个数字、每种颜色**列成表，
   逐条追到数据源，判「会不会说谎 / 会不会被关掉 / 会不会过期」。

   > **这条是被 W3 逼出来的。** W3 到 W3.4 修了五轮，每轮都是「这个数字错了 → 修这个数字」，
   > 结果同一个病换了五个形状：测试算进统计 → `today` 依赖可关的通道 → `log` 冒充投递 →
   > `msg` 冒充通道名 → 绿点替失败背书。每轮都修对了，每轮都只修了那一个实例。
   >
   > 换成断言审计之后，一次就捞出了 7 处，其中两处（跨通道草稿被冲、填一半关窗全丢）
   > 是前五轮完全没看见的**数据丢失**——因为它们不是"数字不对"，没人会去查。
   >
   > **验收的最小单位是「一条断言」，不是「一个 bug」。** 见
   > [`W3-收口审计.md`](W3-收口审计.md) 的表格格式。

   **审计必须带时间维度**：每条断言再问一次「**换一天会怎样**」。
   四种状态各看一遍——今天有数据 / 只有昨天有数据 / 两天都有 / 两天都没有。

   > **这条是被 W3.6 逼出来的。** 18 条断言的维度是「数据源对不对」，
   > 没有一条问「换一天会怎样」，于是漏掉了 `ok`/`fail` 跨天累加
   > 和「零点后健康信号失忆」。这两个 bug **只在第 2、4 种状态里出现**，
   > 而开发时日志永远是今天刚写过的——怎么点都测不出来。

   **视觉比对必须带视口维度**：截图和像素 diff 只能证明「这一个视口下相同」，
   证明不了「规则相同」。

   > **这条是被 W4.1 逼出来的。** 通道页迁移后在 973px 视口下逐像素比了 362 万点，
   > 0 差异——但 `@media (max-width: 820px)` 被搬成了 760，两份规则同时存在，
   > 只是 973 视口下都不触发。**761–820 区间通道页一列、另两页两列**，
   > 用户拖窗口就能看见（R39）。像素为 0 反而让人更放心，比没比更危险。
   >
   > 判据：凡是响应式规则搬家，必须在**断点两侧各取一个视口**验证，
   > 而且要报**数字**（`gridTemplateColumns` 有几个值），不要报截图。
6. **一个字段有两个消费者时，先把每个消费者的期望写出来并排看。**
   两个消费者要的答案相反，就**必须有两个字段**，不能靠文档说「这里故意不对称」。

   > **这条是被 W3.7 逼出来的。** W3.5 在 `architecture.md` 写了一张表：
   > 「时间用测试记录、成败不用」，写得很好。但 `_last_send_times()` 返回的是
   > 一条记录，`time` 和 `ok` 在同一个槽里——**声明了做不到的事**。
   > 后果是同一个界面上下矛盾：侧栏绿「送到你手机」，通道列表红「最近一次失败」。
   >
   > 判据：写完「故意不对称」那段话之后，去数据结构里找**两个**槽位。
   > 只有一个，就是没做到。
7. **同一层被修了三次以上，停下来换结构，不要再修第四次。**
   三次是信号：不是某个 bug 难，是这一层的**形状**错了——每加一个需求就漏一次。

   > **这条是被 W3 全段逼出来的。** W3.1 到 W3.7 七轮，7/7 改 `insight.py`、
   > 6/7 改 `bridge.py`，全在同一层。`stats()` 里现在叠了十层 `if`，
   > 每一层对应一次修复——那段代码是迭代的化石层，能跑，但没人能说出
   > 十层合起来是什么语义。
   >
   > 判据：**数一下同一段代码被 `git log -L` 改过几次。** 三次以上，
   > 下一步不是修，是抽出中间表示、然后穷举状态空间验证。
   > 见 [`W3-根本原因与收敛方案.md`](W3-根本原因与收敛方案.md)。
8. **W3 之后，这一层的问题一律「先加一格用例，用例红了才允许改代码」。**
   不许先修后补。

   > **这条是被 W3.1–W3.7 七轮「先修后补」逼出来的。** 每轮都是用户报症状 →
   > 补一条断言 → 修。补的断言只能覆盖**想到的**组合，而七个 bug 全部藏在
   > 「两个维度交叉」的地方（测试 × 跨天、log × recent、测试 × 跨天）。
   >
   > 现在的防线是 `tests/test_logs_matrix.py` 的 30 格矩阵 + 六条不变量，
   > 外加 `tools/verify_matrix_against_old.py`——它把七个历史 bug 还在的那一版
   > 代码加载进来，要求**七行全红**。矩阵某格在旧代码上不红，就说明那格
   > 没覆盖到。这条检验当场抓到过一次漏（`recent` 列不在表里，见 roadmap R32）。
   >
   > 收敛判定八条见 [`../roadmap.md`](../roadmap.md)「W3 收敛判定」。
9. **写「已有测试钉住 / 已修 / 已删」时，必须当场给出一条可执行证据。**
   测试 → 贴 `grep -n "def test_xxx" tests/` 的输出；已修 → 贴 commit；
   已删 → 贴 `git ls-files | grep` 为空。**没有证据的「已经」就是「没有」。**

   > **这条是被 W4 逼出来的。** `roadmap.md` 的 R37 写着「W4 用
   > `test_bridge_w4.py` 断言 `ui_meta().kinds` 的键序 =
   > `DEFAULT_CONFIG["triggers"]` 的键序，漏一处会红」——**那条测试不存在**。
   > 当时只有 `template_kinds` 有钉，`kinds` 和 `fields` 都没钉，
   > 而 R37 想防的洞恰好就在这两处。文字读起来像防线，实际是空白。
   >
   > 这和第 3 条是同一个病（声明了 ≠ 做到了），只是这次声明的是**测试**，
   > 比声明行为更容易糊过去——因为没人会去跑一条不存在的测试。
   > 补丁见 [`W4.1-键集对齐与迁移复核.md`](W4.1-键集对齐与迁移复核.md)。

   **同一个道理也管数字。** 写进注释、文档、汇报的每一个绝对值（断点、宽度、
   行数、条数）都要有实测出处——命令 + 输出，或者一个能重跑的脚本。
   照抄上一版注释里的算式不算。

   > **这条是被 W4.2 / W4.3 逼出来的。** `channels.css` 里那段断点推导写着
   > `973 - 64 - 240 - 24 = 645`，我照抄了，于是判定「两页可用宽度只差 60px，
   > 一个断点够用」。实际公式是 `视口 − 631`（**漏了 240px 左侧栏**），
   > 两页差 327px——照抄的算式把 820 定成了错的值，通道页两列被压到 86–126px，
   > appID 直接截断。**一个抄来的数字能污染三个决策**（断点值、要不要拆两档、
   > 要不要改设计）。
