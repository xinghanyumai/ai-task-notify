## 0. 这一页为什么最难

| 难点 | 现状 |
|---|---|
| 10 个通道，字段各不相同 | `CHANNEL_META` 里已有完整定义（label / summary / help / fields） |
| 每个字段有 4 种控件 | `fields` 元组是 `(key, label, type, default, hint)`，type 有 `text` / `password` / `textarea` / 以及隐含的开关 |
| 测试要发真网络请求，8 秒超时 | 现在 `_run_bg` + `after(60)` 轮询，web 版要换成线程 + `evaluate_js` |
| 必填校验 + 自动启用 | `REQUIRED` / `missing_fields` / `auto_enable` 现成可用 |
| 分组 | `CHANNEL_GROUPS` **现在在 `ui.py:127`**，要搬到 `channels.py` |

**好消息**：不需要在前端硬编码 10 套表单。`CHANNEL_META` 就是 schema，
前端遍历 `fields` 渲染即可。硬编码的话，加一个通道要改两处，必有一处忘记。

## 2. bridge 新增三个方法

```python
@_guard
def channels_meta(self) -> dict:
    """一次返回前端渲染通道页需要的全部静态结构。

    返回：
      {
        "groups": [{"label": "自建推送", "types": ["wxmp", "wecom_app"]}, ...],
        "meta":   {"wxmp": {"label", "summary", "help", "icon", "fields": [...]}, ...},
        "required": {"wxmp": ["appid", "secret", "template_id"], ...}
      }

    fields 的每一项转成对象，前端好遍历：
      {"key", "label", "type", "default", "hint"}
    """

@_guard
def channels_state(self) -> list[dict]:
    """每个通道的当前状态 + 已填的值。

    返回 [{type, enabled, ready, missing: [中文名...],
           subtitle, level, values: {key: value}}, ...]

    subtitle / level 直接用 insight.channel_state()，不要在前端重新判断
    —— 判断逻辑只许有一份，否则两版不一致。
    """

@_guard
def channel_test(self, ctype: str, fields: dict, cb_id: int) -> dict:
    """异步发测试消息。**立刻返回，结果用 evaluate_js 回调。**

    必须开线程。8 秒超时期间主线程不能阻塞，否则窗口冻死。
    """
    def work():
        ok, msg = insight.test_channel(ctype, fields or {})
        payload = json.dumps({"id": cb_id, "ok": ok, "msg": msg},
                             ensure_ascii=False)
        # 窗口可能已经关了，evaluate_js 会抛
        try:
            self._window.evaluate_js(f"window.__testDone({payload})")
        except Exception:
            pass

    threading.Thread(target=work, daemon=True).start()
    return {"started": True}
```

### 2.1 `evaluate_js` 的注入风险（必须处理）

`msg` 里有用户输入的内容（比如 webhook 返回的错误体）。直接拼进 JS 字符串，
一个引号就能把脚本拼断，甚至执行任意代码。

**必须 `json.dumps(..., ensure_ascii=False)` 后再插入**，且插入位置只能是
函数调用的参数位（`__testDone({payload})`），不能拼进字符串字面量。

同理，`fetch_openid` 的回调也要这么处理。

## 3. 页面结构

```
┌──────────────────┬──────────────────────────────────────────┐
│ 全部通道   2/10  │  微信测试号          [已启用]   [开关]   │
│                  │  官方免费、无需实名、不限条数…            │
│ 自建推送         │  ────────────────────────────────────────│
│  微信测试号  ●   │                                          │
│  企业微信自建应用│  appid *            appsecret *          │
│ 第三方           │  [____________]     [____________]        │
│  Bark       ○   │  测试号页面上的…     测试号页面上的…       │
│  ntfy       ○   │                                          │
│  ...             │  [测试此通道]              [自动获取 openid]│
│ 本机             │                                          │
│  写入本地日志 ●  │                                          │
└──────────────────┴──────────────────────────────────────────┘
```

### 3.1 左列表（240px，与侧栏同宽，形成"栏中有栏"的节奏）

每行：
- 图标 20px（线性，`--fg-subtle`）
- 主标题：`short_label(ctype)`（去掉括号补充）
- 副标题：`insight.channel_state()` 返回的 `subtitle`
- 右侧状态点 8px：`level` 为 `ok` 时 `--brand` 实心，`warn` 时 `--warn` 空心，
  `muted` 时不显示

**不要用"已启用"文字徽章**——列表里 10 行都挂徽章会变成一堵墙。
状态点 + 副标题已经说清了。

选中态：`--bg-subtle` 底 + 左侧 3px `--brand` 竖条（和侧栏导航同一套语言）。

### 3.2 右表单（从 schema 渲染）

```js
function fieldNode(f, value) {
  const wrap = document.createElement('div');
  wrap.className = 'field';
  wrap.innerHTML = `
    <label for="f-${f.key}">${esc(f.label)}${isRequired ? '<i>*</i>' : ''}</label>
    ${f.type === 'textarea'
      ? `<textarea id="f-${f.key}" rows="4">${esc(value)}</textarea>`
      : `<input id="f-${f.key}" type="${f.type === 'password' ? 'password' : 'text'}"
               value="${esc(value)}" placeholder="${esc(f.default)}">`}
    <p class="hint">${esc(f.hint)}</p>`;
  return wrap;
}
```

三条硬规则：

1. **`esc()` 必须用**。通道字段里有用户粘贴的 URL / token，直接插 `innerHTML`
   会 XSS（虽然是自己输入自己，但 `config.json` 可能来自别处）。
2. **`type=password` 的字段要有"显示"按钮**（眼睛图标），否则用户没法核对
   自己粘的 secret 对不对。这是现有 tkinter 版没有的，加上。
3. **`help` 字段单独一块**，放在表单底部、用 `--bg-subtle` 底 + 等宽字体
   （webhook 那段 JSON 示例需要等宽）。

### 3.3 必填与禁用

- 有 `*` 的字段来自 `REQUIRED[ctype]`
- 按钮禁用时**必须写明原因**：

```html
<button class="btn btn-primary" disabled
        title="还需要填写：appid、appsecret">保存配置</button>
<p class="hint">还需要填写：appid、appsecret</p>
```

理由：上一版就踩过"按钮灰了但不说为什么"，用户会以为程序坏了。

### 3.4 测试通道的异步交互

```
点「测试此通道」
  → 按钮进入 loading（转圈 + 文案变「发送中…」+ disabled）
  → 立即返回，窗口可拖可切页
  → 结果回来：
      成功 → 按钮旁出现绿色 ✓「已发送，去手机上看看」（3 秒后淡出）
      失败 → 按钮下方出现红色错误块，含 insight 返回的 redact 后的信息
  → 无论成败，按钮恢复
```

**不许**：整页 loading、禁用整个表单、`alert()`。

超时兜底：前端 `setTimeout` 后如果结果还没回推，显示「等待超时，请检查网络或看日志」
并恢复按钮。**防止 Python 侧线程挂了前端永远转圈。**

**但这个超时必须大于后端的真实最坏耗时，否则它不是兜底，是造假。**

后端的账（`wbn/channels.py`）：

```
微信测试号  取 access_token  _get_json(timeout=10)
          + 发消息        _post_json(timeout=8)
          = 18s
其余通道    只有一次 _post_json(timeout=8)  = 8s
```

`http_timeout` 还是可配的（`config.advanced.http_timeout`，默认 8）。所以前端那个数
**不许写死 10s**——本任务书初稿写的就是 10s，比后端最坏值小 8 秒，结果就是：网络慢的时候
用户看到「等待超时」，而那条消息其实正在发、并且真的发出去了。前端已经 `dropCb`，
真实结果回来时没人接，屏幕上永远停在一个假的失败上。

要求：`TEST_TIMEOUT = 10 + http_timeout*1000 + 2000`（取 token 的 10s + 一次发送 +
2 秒余量），下限 20s。`http_timeout` 由 `channels_meta()` 一并下发，前端不自己猜。

### 3.5 测试发送不许进今日统计

`pipeline.send_test()` 最后一行是 `store.log(f"test channel={ct} ok={ok} …")`，
而 `store.log()` 写的是 `logs/notify-YYYY-MM-DD.log`——**正是 `insight.stats()` 解析的那个文件**。

`stats()` 的过滤是 `if "channel=" not in line: continue`，于是 `test channel=bark ok=False`
被当成一条真实通知计入「失败」。配置 10 个通道、每个试两三次，运行状态页就会凭空多出
十几条失败，而且和「今日通知」对不上（今日通知数来自 `notifications.log`，按事件算；
成功/失败来自 `notify-*.log`，按通道算）。

现场证据（2026-10-28，本机）：

```
今日通知=7  成功=7  失败=6      ← 7+6=13 > 7
其中 3 行来自手动点「测试此通道」
```

要求：

1. 测试行改成**不含 `channel=` 子串**的写法（如 `test-send type=bark ok=False`），
   或让 `stats()` 明确跳过 `test ` 开头的行。两条选一条，**不许两条都不做**。
2. `insight.stats()` 的 docstring 现在写「只数 `channel=` 开头的行」，代码是「包含」。
   **文档和代码对不上就是 bug 的温床**——改成什么写法，docstring 同步改成能逐字对上代码的表述。
3. 加一条回归测试：往临时日志里塞一行测试行 + 一行真实失败行，断言 `fail == 1`。
4. 日志 tail 里测试行要**留着且能看出来是测试**（用户排查时需要），只是不进统计。

## 4. 数据流（保存时发生了什么）

```
前端本地 state（用户编辑，不实时保存）
   ↓ 点「保存配置」
POST channels 数组 + triggers + filters + templates（只提交改过的部分）
   ↓ bridge.config_save(patch)
insight.merge_save(patch)
   ↓ 1. config.load()          ← 重新读磁盘，拿最新的
     2. 只覆盖 patch 里出现的通道/字段
     3. channels.auto_enable(cfg)   ← 自动维护启用态
     4. config.save(cfg)      ← 原子写
   ↓ 返回 {ok, turned_on, cfg}
前端：用返回的 cfg 覆盖本地 state（不是用自己提交的那份）
      → 这样自动启用的结果能立刻反映到界面上
```

**第 4 步"用返回值覆盖本地"很关键。** 如果前端保存后仍用自己那份 state，
`auto_enable` 把某个通道自动打开的结果就看不见，用户会以为没生效。

## 5. 验收（8 条）

| # | 验收项 | 标准 |
|---|---|---|
| 1 | 10 个通道逐个点开 | 每个都能渲染出正确的字段数和类型，不报错 |
| 2 | 表单不是硬编码的 | 在 `CHANNEL_META` 里给 `bark` 加一个假字段，重启后前端自动多出一个输入框（验完删掉） |
| 3 | 异步测试 | 填一个错的 webhook，点测试，**期间窗口能拖动、能切页**；超时后显示错误 |
| 4 | 必填禁用 | 清空 appid，按钮变灰且提示「还需要填写：appid」 |
| 5 | 保存不丢数据 | 改通道 A 的字段 → 保存 → 手工改 `config.json` 的通道 B → 再改 A → 保存 → B 的改动还在 |
| 6 | 与 tkinter 版一致 | 同一份 config，两版截图并排，字段顺序、默认值、hint 文案逐项一致 |
| 7 | **测试不污染统计** | 连点 3 次「测试此通道」（含失败），`stats_today()` 的 `ok`/`fail` **一个都不许变**；日志 tail 里能看到这 3 行 |
| 8 | **超时口径对得上** | `TEST_TIMEOUT ≥ 10s + http_timeout + 2s`；把 `http_timeout` 改成 3，前端超时值跟着变 |

第 2 条是这一阶段的核心验收——**它证明表单是 schema 驱动的，不是抄了 10 遍。**

第 7、8 条是补的，原因见 §3.5 和 §3.4。这两条都不是「多做点事」，是**这两个数原来就是错的**：
统计里混着测试行，前端超时比后端最坏值短 8 秒。

## 6. 文档同步：11 篇通道文档指着这一页

`docs/channels/` 下有 10 篇配置说明（bark / dingtalk-bot / feishu-bot / log / ntfy /
smtp / webhook / wechat-sandbox / wecom-app / wecom-bot）加 1 篇索引，
全部在告诉用户「在设置中心选 X，填 Y，点『测试此通道』」。

**这意味着这一页有三样东西不能改**，否则 11 篇文档集体失效：

| 不能改 | 为什么 |
|---|---|
| 按钮文案「测试此通道」 | 10 篇文档逐字引用这五个字 |
| 每个通道一个独立开关 | 文档写「打开开关」，且 `auto_enable` 逻辑依赖它 |
| 通道显示名与 `CHANNEL_META["label"]` 一致 | 文档写「设置中心选 `Bark`」，名字变了用户找不到 |

**不许做的**：在文档里描述具体位置。

> **另有一条安全约束（W2 §2.4）在这一页最吃紧**：通道报错的原文是远端服务返回的

> 配合 `--no-sandbox` 就是一条从「某个通道返回恶意 body」到「读出全部通道密钥」的路。

### 6.2 为什么不许写位置

写位置 = 把文档绑死在某一版布局上。tkinter 版是「右侧面板右下角」，
web 版可能是「顶部工具条右侧」，下次改版又变。**写稳定的导航路径
（哪一页 → 哪个通道 → 哪个按钮），不写像素位置。**

这条规则对以后所有文档都成立，已写进 `docs/README.md` 的维护规则第 6 条。

### 6.3 输入框边框必须 ≥ 3:1（W2 的豁免不适用于表单）

W2 判定「`--border` 1.25:1 不达标但可以不动」，理由是卡片靠白底 + 阴影已经能区分，
描边纯装饰。**这条豁免只对卡片成立，不能顺延到输入框。**

原因：WCAG 1.4.11 管的是「识别控件所必需的视觉信息」。卡片不是控件，输入框是。
而现在的组合是：

```
输入框底  --bg-subtle  #f4f4f5
卡片底    --bg-card    #ffffff
两者对比               1.04:1     ← 靠底色区分不了
边框      --border     #e6e6e9
对白卡                 1.25:1     ← 靠边框也区分不了
```

**结果：用户看不出这里有个输入框。** 这不是审美问题，是「能不能用」的问题。

要求：

1. 新增 `--border-input`（亮/暗各一个），对 `--bg`、`--bg-card`、`--bg-subtle`
   **三种底色都要 ≥ 3:1**。参考值：W2 已经量过 `#8e8e97` 对白卡是 3.25:1，
   同一个数量级即可（暗色下要单独算）。
2. 输入框边框用 `--border-input`，**焦点态**再切 `--brand-ink` + `0 0 0 3px var(--ring)`。
3. 把 W2 的对比度脚本扩成三种底色 × 所有文字/边框 token 的全组合，**结果贴进汇报**。
4. `--border` / `--border-strong` 继续只做分隔线，不许被用在任何输入控件上。

> 顺带记一条：shadcn 的默认输入框边框 `#e4e4e7` 就是 1.25:1，**它是错的**，
> 别拿它当参照。W2 §1.1 已经说过「不抄它的色值」，这里再加一条「也不抄它的边框」。
