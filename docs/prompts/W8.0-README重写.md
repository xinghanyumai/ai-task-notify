### 5 条可直接执行的结论

1. **首屏没有一家放安装命令。** ntfy / ripgrep / apprise 的 40 行内全是「是什么 + 凭什么 + 长什么样」，`## Installation` 一律在第 2 屏之后。**本项目现在第 24 行就是 `## 快速开始`，这是要改的地方。**
2. **徽章 3–5 个就够。** ntfy 13 个属于「老牌项目的惯性」，uv 只用 3 个。徽章必须**每个都能追到一个事实**，装饰性徽章（stars / PRs welcome）不加。（本项目最终定 **6 个**：CI + 5 个静态，见 §2。）
3. **「Why」和「对比表」是高质量项目的分水岭。** 尤其是 ripgrep 敢写 **"Why shouldn't I use ripgrep?"** —— 这一节比前面所有优点加起来更能建立信任。
4. **对比表要能当查询工具用，不是形容词。** apprise 那张四列表 130+ 行，读者是来「查我的服务在不在支持列表里」的，不是来读排比的。
5. **可以长，但必须有结构。** 策展人原话是「长而有序」；ripgrep 600+ 行、uv 400+ 行都成立，因为它们每节都有明确标题和锚点。

### 本项目手上最强的素材（别人抄不走）

不是功能数量，是**有账可查的真实运行数据**：

- 开发期**真实投递 348 次**（`log` 247 / `wxmp` 99 / `webhook` 2）
- `wxmp` **失败 128 次，全部集中在 10-26 至 10-29 四天**，修复后 **10-30 单日 46/46 全绿**
- **10 个通道里 7 个从未在真实环境发过** —— 本项目自己写进 README
- **R60 承认「微信单通道」是重复建设**，还列了 4 个替代方案和它们的实测坑
- `563 passed, 1 skipped`

**这组数据正好填 ripgrep 那个「反向论证」的位置。** 大多数 README 只写能做什么，本项目可以写「哪里不行、多少条失败过、哪 7 个通道没验过」。这是本轮唯一不可复制的差异点，**不许为了好看把它删掉或挪到文末**。

## 3. 三个必写章节

### 3.1 `## 它解决什么`（≤25 行）

三块，顺序不许换：

**（a）一句话**——照抄：

> 挂在 AI 编程助手的 hooks 上，任务一停就把结果推到手机。不改宿主代码，不装插件，不依赖宿主的私有目录。

**（b）它解决的不是「怎么发」，是「什么时候该发」**——照抄这句（R60 结论，别重写）：

> 现成方案解决的是「**怎么把一句话送到我手机上**」；本项目解决的是「**哪些事该发、发什么、发过没有、发失败了算谁的**」。

后面接 5 行差异表，**事实只许来自下表**：

| 维度 | 只有推送脚本时 | 本项目 |
|---|---|---|
| 事件 | 一个 `push(text)`，发不发靠 prompt 里写 | 6 类事件各有模板与开关 |
| 去重 | 无 | 终态事件按「哪个会话的第几轮」去重，非终态按内容 |
| 静默 / 限流 | 无 | 静默时段 + 每分钟/每小时上限 |
| 投递结果 | 不知道发没发出去 | 每次投递落一行 `ok=True/False`，状态页可查 |
| 宿主 | 只服务一个 | WorkBuddy / CodeBuddy / 旧版目录三处都认 |

**（c）代价**——**这一块不许省，也不许挪到「已知限制」里**：

> - 只支持**已经装好 hooks 机制**的宿主。宿主不发 hook，本项目收不到任何东西。
> - 通知延迟取决于宿主：源码形态约 70ms；**单文件 exe 形态每次要自解压，1.5–2.2 秒**，一条通知端到端约 3–4.5 秒。对「任务完成提醒」无感，对「毫秒级告警」不合适。
> - 10 个通道里只有 3 个在真实环境验证过，见下面的「支持矩阵」。

### 3.2 `## 为什么不是一堆推送脚本`（≤30 行，ripgrep 式）

用**项目符号 + 每条一个可验证的证据**，不许写排比句。结构：

```markdown
## 为什么不是一堆推送脚本

一句话：推送脚本解决「怎么发」，本项目解决「什么时候发、发过没有、发失败了算谁的」。
下面每条都能在仓库里找到对应实现，不是设计意图。

- **事件有语义，不是一个 `push(text)`。** 6 类事件（任务完成/失败/等你确认/工具失败/会话开始/结束）
  各有标题模板、内容模板和独立开关。改标题不用改代码，改 `config.json` 就行。
- **终态事件按事件身份去重。** 同一个 turn 里宿主连发 3 次 `TaskCompleted`，你只收到 1 条；
  非终态（等你确认、工具失败）按内容去重，连按 3 次仍然收 3 条。见 `tests/test_dedup_turn.py`。
- **静默时段 + 频率上限。** 静默时段（`quiet_hours`）+ 每分钟 4 条 / 每小时 20 条上限，
  外加「工具连续失败 3 次才报」（`tool_fail_threshold`），避免一个坏命令刷你 40 条。
- **每次投递都留证据。** 一条通知落一行 `channel=wxmp ok=True msg=已送达微信`，
  失败落 `ok=False` + 服务端返回原文。状态页直接读这些行，不是猜的。
- **不读宿主的私有目录。** 只用公开的 hooks 协议（`settings.json` 的 `hooks` 字段）。
  宿主改内部结构，本项目不断。
```

> ⚠️ 上面 5 条的**事实依据**（已逐条核对过，2026-10-30）：
> ① `config.example.json` 的 `triggers` 6 项；`titles` / `templates` 各 6 个事件键 + `test`
> ② `wbn/pipeline.py` 的 `_dedup_key()` + `tests/test_dedup_turn.py` 10 条
> ③ `config.example.json` 的 `filters`：`quiet_hours=""`、`max_per_minute=4`、`max_per_hour=20`、`tool_fail_threshold=3`
> ④ `logs/notify-*.log` 的 `channel=… ok=…` 行
> ⑤ `install.py:69-72` 只写三个 `settings.json` 的 `hooks`，**不读 `claw-state/`**
>
> 名称对不上就按代码里实际的写，**不许照抄本任务书**。

### 3.3 `### 什么情况下别装本项目`（≤12 行，反向论证）

**这是本轮最有价值的一节，也是唯一一节「劝人别用」。** 至少写满 4 条，每条给替代方案：

### 6.1 例外：`## 快速开始` 里有一句**事实错误**，必须改

现第 35 行：

> `requirements.txt` 里只有 `pystray` 和 `Pillow`，托盘图标要用。不装也能跑，只是没有托盘。

**这句话是错的。** `requirements.txt` 里实际是 3 个包：

| 包 | 用途 | 缺了会怎样 |
|---|---|---|
| `pystray` + `Pillow` | 托盘图标 | 没有托盘，通知照发 |
| `pywebview>=6.2,<7` | 设置界面（依赖系统 WebView2） | 弹原生提示框，通知照发 |

`pywebview` 从 `507aa4b`（W1）就在文件里了，这句描述从写下那天起就没对过。

**改成**（大意，措辞自定，三个包都要出现、都要说清缺了会怎样）：

> `requirements.txt` 里是三个包：`pywebview` 负责设置界面（依赖系统 WebView2），

import pathlib, collections, re

per = collections.defaultdict(lambda: collections.Counter())
for p in sorted(pathlib.Path("logs").glob("notify-*.log")):
    day = p.stem.replace("notify-", "")
    for line in p.read_text(encoding="utf-8", errors="replace").splitlines():

            per[day]["ok" if m.group("ok") == "True" else "fail"] += 1
print("OK  :", dict(ok), "total", sum(ok.values()))
print("FAIL:", dict(bad), "total", sum(bad.values()))

EOF
