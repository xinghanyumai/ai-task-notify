# W3 收口审计：这一页对用户说了几句话

> 审计对象：W2（壳 + 状态页）+ W3/W3.1–W3.4（通道页）
> 方法：**不找"哪个数字错了"，而是列出界面对用户做的每一条断言，逐条追到数据源**
> 结论：18 条断言，11 条合格，**7 条不合格**，一次性修完（W3.5）

---

## 0. 为什么之前会修五轮

前五轮的验收方式都是「这个数字对不上 → 修这个数字」。结果同一个病换了五个形状：

| 轮次 | 症状 | 我以为的病 | 真实的病 |
|---|---|---|---|
| W3 | 7/7/6，13 > 7 | 过滤条件写错 | 日志行格式和判据耦合 |
| W3.1 | 同上 + `today` 也涨 | 又漏了一处过滤 | 数据源是 `log` 通道的副产物 |
| W3.2 | 关掉 log → `today` 冻结 | 取数来源选错 | — |
| W3.3 | 16 条"通知"里 14 条没到手机 | 单位不统一 | — |
| W3.4 | 绿点 + 「送到你手机」 | 文案不代表状态 | — |

每一轮都修对了，每一轮都只修了**那一个实例**。真正的病是：

> **界面上的每个字都有数据源，而我从来没有把所有字列出来一起看。**

所以这一段不修 bug，先做一张表。

## 2. 七处不合格，分三类

### 第一类：说假话（数据源错）

**A. 测试发送污染健康信号**
`_LOG_CHANNEL` 的正则里带 `(?:test-send |test )?`，所以 `_last_send_times()` 会读进测试行，
`delivery_health()` 拿它判成败。实测：

```
空日志                    → ('…经微信测试号，送到你手机', 'ok')
只写一条测试失败          → ('…但最近一次没送到', 'danger')
```

两个问题叠在一起：
1. **D14 已经定了「测试不是投递」**，这里又把测试当投递，自己打自己。
2. 测试用的是**表单里未保存的值**。用户想看看报错长什么样，故意填个错地址点一下测试，
   侧栏从此变红——而磁盘上的配置可能是对的。要等到下一次真实发送成功才恢复。

**B. `recent` 仍依赖 `log` 通道**
W3.2 修的是 `today`，`recent` 没动。它读 `notifications.log`，而全项目只有 `_send_log` 写这个文件。
关掉 log 通道 → 「最近通知」永久为空 → 空态文案「还没收到通知」是假话（明明发了 20 条）。

**C. 跨天条目显示成今天**
`recent` 不限今天（标签写「最近通知」，本来就该跨天），但渲染只取 `HH:MM`。
昨天 23:50 的条目和今天 00:10 的条目在界面上看不出区别。

### 第二类：丢数据

**D. 保存 B 通道会把 A 通道的未保存改动一起冲掉**
`saveChannel()` 里是 `adopt(list, null)`——第二个参数 `keep` 传了 `null`，
于是所有通道的草稿都从磁盘重读，**包括另一个通道里用户刚改还没保存的内容**。

```
改 Bark 的 webhook → 切到微信测试号 → 改 appid → 保存微信
→ Bark 的改动消失，「有未保存的改动」标记也消失，没有任何提示
```

`toggle()` 里传的是 `isDirty(state.current) ? state.current : null`，只保当前一个——
同样的洞，只是少踩一点。

**E. 填一半关窗全丢**
必填没填完时「保存配置」是禁用的（§3.3 的要求），所以半成品**存不下来**；
关窗又没有拦截。用户填了 8 个字段差 1 个，关窗，全丢。

### 第三类：生命周期

**G. 测试完成不刷新侧栏和列表**
`channel_test` 回来只 `showResult`，不调 `refreshChain()` / `channels_state()`。
所以「最后发送时间」要切页才更新——用户刚点完测试，列表还显示昨天。

> 注意：A 修好之后，测试**不应该**影响健康信号，所以 G 只刷新时间，不刷新健康。

**F. 切页不清理在飞回调**
`cbMap` 里注册的回调，页面切走后没有 `dropCb`。测试还在飞的时候切到状态页，
回调回来会写进**已经 detach 的 DOM 节点**，`state.timer` 也会在死页面上再挂一个定时器。
不崩、不报错，就是漏 + 幽灵更新。壳里没有 `page.destroy` 这个概念。

## 3. 三处记入 roadmap，这一段不改

| 项 | 为什么现在不改 |
|---|---|
| **I.** 「启用通道 2/10」含 `log` | 这张卡说的是"配置里有几条通道开着"，不是"几条能投递"。含 log 不算错，但和上面三个数不同宇宙，属于**文案**问题，等 W4 统一梳理标签时一起看 |
| **J.** 改了 `http_timeout` 后前端超时值陈旧 | 现在没有界面能改它（W4 才有高级设置页）。W4 做那一页时必须在保存后重算 `testTimeout` |
| **K.** 状态页的圆点/徽章没有 `aria-label` | 读屏用户拿不到「通道失败 15」以外的信息。W6 有 a11y 专项，那里统一补 |

---

## 4. 结论

七处不合格里，**A / B / C 是"界面说假话"，D / E 是"用户数据会丢"**，G / F 是卫生问题。
A 和 B 是同一个病的最后两个实例——**"数据源是某个可选通道的副产物"**。

W3.5 一次修完这七处，之后 W3 全段冻结：
`stats()` / `chain_sentence()` / `channel_state()` / `channels_state()` 的语义不再动，
W4 发现新问题记 roadmap 不插队。
