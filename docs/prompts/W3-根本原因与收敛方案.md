# W3 为什么修了七轮还没收敛

## 0. 一句话

**不是每个 bug 难，是这一层的结构错了，所以每加一个需求就暴露一次。**
七轮修的都是同一个函数，每轮加一层判断。第七轮之后，那七层判断叠在一起，
已经没人能说出它们合起来是什么语义。

---

## 1. 数据：七轮改的是同一个地方

| 轮次 | 修的"表面现象" | 改的文件 |
|---|---|---|
| W3.1 | 测试发送污染统计 | `insight.py` |
| W3.2 | `today` 依赖可关闭的通道 | `insight.py` |
| W3.3 | `log` 冒充投递 | `insight.py` |
| W3.4 | 界面替失败背书 | `bridge.py` + `insight.py` |
| W3.5 | `recent` 依赖 log 通道 | `bridge.py` + `insight.py` |
| W3.6 | 跨天累加 / 零点失忆 | `bridge.py` + `insight.py` |
| W3.7 | 一个槽位装两种事实 | `bridge.py` + `insight.py` |

**7 / 7 改 `insight.py`，6 / 7 改 `bridge.py`。**

七次都在同一层。这不是「bug 多」，是**这一层每被用一次就漏一次**。

### `stats()` 现在长这样

```python
for day, tag in ((yesterday, "yesterday"), (today, "today")):   # ① 跨天（W3.6）
    for line in text.splitlines():
        em = _EVENT_LINE.match(line)                            # ② 事件行
        if em:
            if em.group("remote_ok") == "True":                 # ③ 只算远端（W3.3）
                if tag == "today":                              # ④ 只算今天（W3.6）
                    delivered += 1
            continue                                            # ⑤ 事件行走掉，别掉进通道行（W3.5）
        if _is_test_line(line):                                 # ⑥ 跳过测试（W3.1）
            continue
        m = _CHANNEL_LINE.match(line)                           # ⑦ 锚定首段（W3.4）
        if not m or m.group(2) == "log":                        # ⑧ 排除 log（W3.3）
            continue
        if tag != "today":                                      # ⑨ 再判一次今天（W3.6）
            continue
        if m.group(3) == "True":                                # ⑩ 状态字段锚定（W3.4）
            ok += 1
        else:
            fail += 1
```

**十层判断，每一层对应一次修复。** 这段代码是七轮迭代的化石层。

它能工作，但它有三个结构性问题：

1. **判断顺序即语义**，而顺序没有任何地方写明。W3.6 的任务书里我专门写「位置不能提前，
   否则会把 `recent` 断掉」——一个函数的正确性依赖「某行代码在另一行之上」，
   这只能靠注释维持。
2. **每加一个消费者就要重读一遍这段**，然后决定自己要不要某几层。
3. **它和 `_last_send_times()` 是两份独立实现**，读同样的文件、用不同的正则、
   各自决定读几天。W3.6 之所以要改两个文件，就是这个原因。

---

## 2. 根本原因：这一层没有中间表示

现在的数据流：

```
notify-*.log ──┬──▶ insight.stats()        ──▶ today / ok / fail / recent
               └──▶ bridge._last_send_times() ──▶ chain_sentence / channel_state / last
```

**两个消费者，各自解析同一批文件。**

### 结构事实

| 项 | 现状 |
|---|---|
| 读 `notify-*.log` 的地方 | **2 处**（`insight.py:237`、`bridge.py:121`） |
| 解析日志的正则 | **3 个**（`_EVENT_LINE`、`_CHANNEL_LINE`、`_LOG_CHANNEL`） |
| 判定函数 | 4 个，分散在两个模块（`stats` 在 insight，`_last_send_times` 在 bridge） |
| 一次状态页加载读几个文件 | `stats` 读 2 个 + `_last_send_times` 读 2 个 = **4 次打开**（文件有重叠） |

### 为什么这必然导致七轮

每加一个消费者，就多一份「读日志 + 过滤」的实现：

- 要 `today` → 写一份
- 要 `ok`/`fail` → 在同一份里加判断
- 要 `recent` → 换数据源，加判断
- 要 `last` → **另起一份**（在另一个模块）
- 要 `health` → 在第二份上加标记
- 要跨天 → **两份各改一次**，规则还不一样（`stats` 只数今天，`last` 读两天）

**消费者的数量在增长，解析代码的数量跟着增长，而它们之间的一致性只能靠人记。**

W3.6 的 `ok`/`fail` 跨天累加就是直接后果：`stats` 里加了 `tag == "today"`，
`_last_send_times` 里没有对应概念——两份实现，两种时间口径。

## 3. 验收方式也有问题：我在验「清单」，不是在验「性质」

七轮的任务书都是这个形状：

> 修这三处：① … ② … ③ …
> 做完给我：1) 改后的代码 2) 三组返回值 3) 截图

**执行者只能覆盖我列的清单。** 我没想到的，他不会碰；我列错的（W3.1 写「三种按钮」，
实际只有两种），他也只能按错的做。

W3-收口审计是我唯一一次换方法（列出 18 条断言逐条追源），一次捞到 7 处——
**这说明「换维度」有效，「加清单」无效**。

但审计只做了一次，之后 W3.6 / W3.7 又回到「修这一处」的模式。

---

## 4. 收敛方案：加一层，然后穷举

### 4.1 结构

```
notify-*.log ──▶ wbn/logs.py ──▶ Facts ──┬──▶ insight.stats(facts)
                                          ├──▶ insight.chain_sentence(cfg, facts)
                                          └──▶ insight.channel_state(cfg, facts)
```

`logs.py` 是**全项目唯一读日志文件的地方**。它只做一件事：文本 → 结构。
不做任何业务判断（什么算成功、要不要降级）。

`Facts` 里装两天的事件和投递，每条是一个不可变的记录：

```python
@dataclass(frozen=True)
class Delivery:
    time: str; day: str; channel: str; ok: bool; msg: str; test: bool

@dataclass(frozen=True)
class Event:
    time: str; day: str; event: str; kind: str
    sent: bool; remote_ok: bool; title: str

@dataclass(frozen=True)
class Facts:
    events: tuple[Event, ...]        # 两天，时间升序
    deliveries: tuple[Delivery, ...]  # 两天，时间升序
```

「今天 / 昨天」「含不含测试」「排不排 log」这些口径，全部变成 `Facts` 上的
**一个属性或一个参数**，而不是散在循环里的 `if`：

```python
facts.events_of("today")                       # 今日事件
facts.deliveries_of("today", remote_only=True) # 今日远端投递
facts.last_by_channel()                        # 双槽记录（D19）
```

### 4.2 为什么这样能收敛

| 现在的病 | 加层之后 |
|---|---|
| 两个消费者两份解析 | 一个 `logs.read()`，所有消费者拿同一份 |
| 三个正则 | 一个（`_LINE`，按行首关键字分派） |
| 判断顺序即语义 | 口径变成命名的方法，顺序写死在方法里，改一处全体生效 |
| 加需求要改 N 个地方 | 加一个方法 |
| 跨天规则不一致 | `events_of("today")` 和 `last_by_channel()` 各自定义一次，都在同一个文件 |

### 4.3 验收改成「矩阵」，不是「清单」

穷举状态空间，而不是穷举我想到的场景：

| 维度 | 取值 | 数 |
|---|---|---|
| 数据分布 | 今天有 / 只有昨天 / 两天都有 / 两天都无 | 4 |
| 记录类型 | 无 / 只有测试 / 只有真实 / 测试+真实 | 4 |
| `log` 通道 | 开 / 关 | 2 |

**4 × 4 × 2 = 32 格。** 每格跑 6 条不变量 + 4 个出口的具体值。

不变量（可执行，写进测试）：

1. `today == len([e for e in events_of("today") if e.remote_ok])`
2. `ok + fail == len(deliveries_of("today", remote_only=True))`
3. `recent` 的每一条都能在 `events` 里找到（同 `day` + `time` + `title`）
4. `last_by_channel()[c].ok is not None` ⟹ 该通道至少有一条非测试记录
5. 只有测试记录时 `ok is None`（不是 `True` 也不是 `False`）
6. `Facts` 只由文件内容决定（同一批文件读两次结果相同）

**32 格 × 10 条断言 = 320 个检查。** 一次跑完，比我手写 6 组返回值覆盖得全。

### 4.4 收敛条件（硬，不满足就不算完）

| # | 条件 | 怎么验 |
|---|---|---|
| 1 | 只有一处读日志 | `grep -rn 'notify-{' wbn/` 只命中 `logs.py` 和 `store.py`（写入） |
| 2 | `insight.py` 里没有日志正则 | `grep -c "re.compile" wbn/insight.py` = 0 |
| 3 | 32 格全绿 | 矩阵测试全过 |
| 4 | 6 条不变量全过 | 同上 |
| 5 | 变异测试 | 塞一行缺字段 / 超长 / `msg` 含 `ok=False` / `msg` 含 `channel=log` 的脏行 → 不崩、不误算 |
| 6 | 真机数字不变 | 手算 vs `stats()` 并排 |
| 7 | 一次加载只读一遍 | 加计数器，`stats` + `chain` + `channels_state` 共用一份 `Facts` |

第 7 条是这次结构改造的**验收标志**：如果还要读两遍，说明中间层没起作用。

### 4.5 冻结条款（这次带惩罚）

W3.8 之后，`logs.py` / `stats()` / `chain_sentence()` / `channel_state()` /
`delivery_health()` / `_last_send_times()` **不许再改**。

W4 起如果发现这一层还有问题，处理方式是：
1. 先在矩阵里加一格能复现的用例（**加用例，不加 if**）；
2. 用例红了才允许改；
3. 改完用例必须变绿，且 32 格其余全绿。

**不允许「先修代码再补测试」。** 七轮里每一轮都是先修后补，所以补的测试只能证明
「这个具体场景修好了」，证明不了「这类场景都不会再错」。

## 5. 这次改动的风险

| 风险 | 处理 |
|---|---|
| 312 个测试依赖现在的函数签名 | 保持 `stats(cfg)` / `chain_sentence(cfg, last)` 签名不变，内部改为先 `logs.read()` 再算；`Facts` 作为可选参数注入，测试可以先不迁移 |
| tkinter 退路 | `ui.py` 只调 `stats(cfg)` 和 `chain_sentence(cfg, last)`，签名不变就不用改 |
| 一次改太多 | 分两步：W3.8 先建 `logs.py` + `Facts` + 让 `stats`/`_last_send_times` 用它（行为不变，312 测试全绿）；W3.8 之后再加矩阵 |

**先搬家，再改行为。** 搬家这一步要求「312 个测试一个都不许改、一个都不许红」——
这是判断搬家是否忠实的唯一标准。

## 6. 后续步骤

| 步 | 内容 | 完成标志 |
|---|---|---|
| **W3.8a** | 建 `wbn/logs.py`：`Delivery` / `Event` / `Facts` / `read()`；`insight.stats` 和 `bridge._last_send_times` 改成消费它 | 312 测试**一个不改**全绿；`grep 'notify-{'` 只命中 1 处 |
| **W3.8b** | 矩阵测试 32 格 + 6 条不变量 + 变异测试 | 32 格全绿；矩阵里能复现 W3.1–W3.7 的**每一个**历史 bug |
| **W3.8c** | 收敛检查：一次加载只读一遍 | 计数器证明 |
| **W3.9** | 回填：把 W3.1–W3.7 七个 bug 各写成矩阵里的一格（如果 32 格里还没有） | 七个历史 bug 全部有对应格，且都是绿的 |

**W3.8b 的判据很硬**：矩阵必须能复现那七个 bug。
如果某一格在旧代码上不红，说明那一格没覆盖到，矩阵不完整。
这是「矩阵是不是真的穷举了」的唯一客观检验。

---

## 7. 一句话总结

前七轮我一直在问「这个数字为什么不对」，正确的问法是
「**这一层必须满足什么性质**」。前者只能一个个修，后者一次修完。
