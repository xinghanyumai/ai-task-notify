**这条测试不存在。** 实测：


用户永远开不了它——而它照样会被 `filters.check` 认（只要有人手改 config）。

## 1. 补两条测试

写在 `tests/test_bridge_w4.py`，紧挨着 `test_ui_meta_lists_every_template_kind`。

### 1.1 触发类型：键序 + 说明不许缺

```python
def test_ui_meta_lists_every_trigger_kind():
    """6 个触发类型一个都不能少，顺序 = config 的键序，且每个都有说明。

    与 template_kinds 那条同构。多出来的一层：`desc` 不许为空——
    `_KIND_DESC` 是**第三处**事件中文说明（R37），漏一个的表现是
    「开关在那儿，下面没有一行字解释它是什么」，比缺开关更难发现。
    """
```

断言三条：

1. `[k["key"] for k in data["kinds"]] == list(config.DEFAULT_CONFIG["triggers"])`
2. 每个 `desc` 非空
3. `label` 与 `events.KIND_LABELS` 对得上（不新写第 4 份中文名）

### 1.2 过滤字段：键集双向对齐

```python
def test_ui_meta_fields_cover_every_filter_key():
    """页面上的字段表必须覆盖 config.filters 的每一个键，不多不少。

    「多」的表现：页面显示一个 config 里不存在的字段，保存时被
    `normalize_filters` 丢掉——用户改了没反应。
    「少」的表现：config 里有的字段用户永远改不了（A2 那个洞）。
    """
```

断言两条：

1. `{f["key"] for f in data["fields"]} == set(config.DEFAULT_CONFIG["filters"])`
2. 每个 `kind` 在 `{"int", "text", "list", "bool"}` 里（拼错一个，前端会当 text 处理）
