## 1. 登记 R61：`dedup_seconds` 兼任「turn 去重」的总开关

**事实**（PM 已复核，不是推断）：

- `wbn/pipeline.py` 的 turn 键在 `store.dedup_hit(key, dedup_window)` 里判，而
  `store.dedup_hit` 第一行是 `if window_seconds <= 0: return False`
- 所以 `filters.dedup_seconds = 0` 时，**turn 去重一起关掉**，重复通知原样复发
- 这个行为被 `tests/test_dedup_turn.py:207` 的
  `test_dedup_disabled_still_sends_everything` **钉成预期**：断言 `[True, True, True]`

**为什么现在不咬人**：默认 `180`，且界面不暴露这个字段（PM 查过 `webui/` 里
`dedup` 零命中），只有手改 `config.json` 才会设成 0。

**为什么还要登记**：`dedup_seconds` 的字面语义是「N 秒内重复**内容**」，现在它同时是
「一个 turn 只发一条」的**总开关**和**时间窗口**。以后任何人做下面任意一件事，
重复通知就会静默回来，而且没有任何测试会红：

- 把 `dedup_seconds` 调小到 2 秒（三条 `TaskCompleted` 间隔 3 秒，窗口盖不住）
- 把 `dedup_hit` 的 `window <= 0` 短路逻辑重构掉
- 给界面加一个「关闭去重」开关

**登记内容**（填进 roadmap 表格，编号 R61，优先级 P3）：

| 字段 | 内容 |
|---|---|
| 现象 | `filters.dedup_seconds <= 0` 时，终态事件的 turn 去重一并失效，一个 turn 连发三条 `TaskCompleted` 会发三条通知（W7.3 修的那个 bug 原样复发） |
| 依据 | `store.dedup_hit` 首行 `if window_seconds <= 0: return False`；`tests/test_dedup_turn.py:207` 把这个行为钉成预期 |
| 严重性 | 低：默认 180、界面不暴露该字段。但语义耦合——一个「内容去重窗口」的旋钮同时控制「事件身份去重」的开关 |
| 处置 | **P3 不改代码。** 若 W8 之后再动去重，优先拆开：终态事件用「turn 已通知」标记（写在 `state/runtime.json`，不参与时间窗口），`dedup_seconds` 只管内容去重。**拆之前先问用户**，因为「设 0 = 全发」是现有测试写明的预期行为 |

## 2. 登记 R62：同一 turn 内「多个不同任务」会被合成一条

**事实**：

- 新键 `kind|session|turn:<turn_index>` 对终态事件**不含 title、不含 content**
- 所以同一个 turn 里若有**两个不同任务**各报一次 `TaskCompleted`，只会发一条
- M2 守卫只覆盖「不同 turn」，覆盖不到这一层

**为什么现在不咬人**：实测那三条 `TaskCompleted` 的标题都是
`✅ WorkBuddy 任务完成`，内容除 `{duration}` 外完全一致——**本来就无法区分**，
合并等于去掉噪声，不是丢信息。

**为什么还要登记**：宿主一旦并行跑多个子任务，并在 payload 里给出可区分的
`task_id` / 不同标题，这个键就会把真通知吃掉，而且**没有任何测试会红**。

**登记内容**（编号 R62，优先级 P3）：

| 字段 | 内容 |
|---|---|
| 现象 | 同一 turn 内多个不同任务的终态事件被合并成一条通知 |
| 触发条件 | payload 里出现 `task_id`，或同一 turn 内出现**不同 title** 的 `TaskCompleted` |
| 严重性 | 当前低（不可区分 = 不丢信息）；宿主改事件形状后变高 |
| 处置 | **P3 不改代码。** 触发条件一旦成立，键里必须加 `task_id`（没有 `task_id` 就退回 `title`）。**判据**：构造同一 turn 两条 `title` 不同的 `TaskCompleted`，必须发两条 |
