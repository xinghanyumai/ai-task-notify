### exe 形态的 A 与内存（W7 实测，2026-10-30）

**源码数字对 exe 不成立，必须单列一条。** 差别只有一处：onefile 每次启动都要
把 19MB 解压到 `%TEMP%\_MEIxxxx`，而 `_PROCESS_T0` 在解压**之后**——
所以 `bench_ui.py` 打出来的 A 不含这一段，用户感受到的那一段不含不行。

| 口径 | 值 | 怎么量 |
|---|---|---|
| A 源码形态（同机同时段） | **1321ms**（5 轮 2147 / 1321 / 1240 / 1256 / 2096） | `python tools/bench_ui.py --runs 5` |
| A exe 进程内口径 | **1581ms**（5 轮 1581 / 1653 / 1772 / 1552 / 1240） | `python tools/bench_ui.py --exe --cold --runs 5` |
| A exe **双击口径**（含自解压） | **2549ms**（5 轮 2634 / 2446 / 2666 / 2549 / 1981） | 同上，看「双击口径」那行 |
| 其中自解压 + bootloader | **≈ 970ms** | 双击口径 − 进程内口径 |
| B 自研代码段 | 源码 17–27ms / exe 15–30ms | 同上 |

**新预算：exe 双击口径 ≤ 3500ms**（`A_BUDGET_EXE_MS`）。定法：5 轮中位数
2549 + 约 37% 余量。源码那条 2500 **不动**。
任务书 §2 的冷启动判据「≤ 3.0s」也过（2549 < 3000），但**判据和预算不是一回事**：
判据是一次性验收门，预算是回归线，贴着实测定会在机器忙的时候天天报警。

> **这条预算靠人跑，CI 不跑。** `tools/bench_ui.py` 要真起窗口、真等首屏，
> `tests/` 里零引用它——所以「预算是回归线」不等于「超了 CI 会红」。
> 改启动路径的人自己跑一遍 `python tools/bench_ui.py --exe --cold --runs 5`。

> **第一次启动会到 4000ms 上下**（清掉 `_MEI` 且系统文件缓存是冷的）。
> 那是冷缓存，不是回归——所以判据取多次的**中位数**，不看单次。
> 想复现「用户第一次双击」的体感，就 `--cold --runs 1`。

**沙箱开关不影响启动（本机实测）**：带沙箱 5 轮中位数 2549ms、关沙箱 5 轮 2674ms，
差在噪声里。所以 W7 把默认从「无条件关沙箱」改回「带沙箱 + 失败即降级」
（见 `app.py` 的 `_sandbox_off_args`），不是拿速度换安全。
**「别的机器上带沙箱也能画出来」没验**——本机两种形态都能渲染，仅此而已，
所以别把这条当已定案引用（R55 第 7 条要在干净机器上复验）。

**exe 没有让我们的代码变慢**：B 数两种形态同一量级，进程内口径只差 ~260ms
（frozen 解释器启动）。exe 比源码多出来的 ~1230ms 里 80% 是自解压。
这条结论很重要——它意味着以后要压启动时间，唯一有意义的方向是
「减少解压量」（裁剪体积 / 换 onedir），而不是去优化 Python 代码。

**内存（整棵进程树，8 个进程）**：

| 形态 | 工作集 | 私有 | 我们自己的进程 |
|---|---|---|---|
| 源码 `pythonw app.py` | 590.3 MB | 396.7 MB | pythonw 101.7 / 64.2 MB |
| exe `通知.exe` | 578.2 MB | 381.3 MB | 通知.exe 108.4 / 68.7 MB（+ bootloader 父进程 11.5 MB） |

**新预算：私有 ≤ 450MB、工作集 ≤ 700MB。** 依据：两种形态实测都在
私有 381–397 / 工作集 578–590，余量 **18% / 21%**（450/381.3、700/578.2）。
**这两条预算基本不由我们决定**——
8 个进程里 6 个是 `msedgewebview2.exe`，合计占了工作集的 80%。
所以「内存涨了」先看是不是 WebView2 自己的波动，别急着改代码。
（`349.6 / 601` 那组旧数字是另一个时间点测的，与本次不可比；
「切 20 页后堆不增长」那条不受形态影响，仍是源码侧的判据。）

## 删预热换来了什么、付出了什么

P0 删预热的理由不是「它慢」，是「它**同步**建页」：开窗后那 2 秒里，它每隔
260ms 在**主线程**上建一页，一次冻住 790ms。这跟「发送期间不冻结」直接冲突。

删掉之后，`check_responsive [B]` 的发送期间最大停顿是 20~25ms（阈值 120ms），
P0 的主诉解决。

代价在别处：以前用户点进某页时，预热多半已经在后台建好了，点击是**缓存命中**
（2~10ms）；现在第一次点进任何一页都要现付 1.2~1.7 秒。

**`bench_ui` 的「首次进入」量不到这个差别。** 它故意在 `App()` 之后只跑
`update_idletasks()`、不跑 `update()`，也就是赶在预热定时器（`after(400, ...)`）
之前取样——两个状态下量的是同一件事。各跑 3 次实测：

| 首次进入 | 有预热（`redesign-base`） | 删预热后 | 预算 |
|---|---|---|---|
| triggers | 1196 / 1406 / 1458 ms | 1370 / 1364 / 1200 ms | 900 ms |
| template | 768 / 916 / 786 ms | 943 / 882 / 912 ms | 900 ms |
| status | 1035 / 1078 / 940 ms | 1139 / 1013 / 1140 ms | 900 ms |
| guide | 1587 / 1656 / 1469 ms | 1579 / 1388 / 1723 ms | 900 ms |

两组数字在噪声内没有差别，而且**两组都超预算**——这个预算在 `redesign-base`
上就已经破了，不是 P0 造成的。启动建界面 255~305ms（预算 400ms）、
切页 2~4ms（预算 100ms）、整页重建 56~61ms（预算 300ms）都在预算内。

所以 P1 的启动层要同时做到两件事：把这 1~1.7 秒挪到用户看不见的地方
（**且不能冻主线程**），并让这张表回到预算内。只做前者是旧预热，只做后者
是自欺欺人。

## 已知缺陷（P0 不修，留给 P1）

> 下面两条**都已在本轮（P1 第 3 步）修掉**。原文保留，因为「当时怎么定位的」
> 比「最后怎么改的」更难重建。改法与验证见 `docs/archive/design-redesign.md` 第九节。

### D1 · 切换主题后内容区变空 —— **P1 已修（两道锁）**

**现象**：点主题切换（跟随 / 浅色 / 深色），侧栏、顶栏、底栏都正常重建，
但中间的内容区变成一片空白，一个控件都没有。

**原因**：`_rebuild()` 销毁了 `root` 的全部子控件，却没清 `self._pages`。
页面缓存字典里还留着那批**已销毁**的 frame，于是 `_show_page(current_page)`
在 681 行撞上 `if key == self.current_page and key in self._pages: return`
提前返回，页面永远不会被重建。

```python
# ui.py:619  _rebuild()
for w in self.root.winfo_children():
    w.destroy()
# ← 这里缺一句 self._pages.clear()
```

**引入点**：`ca59c3d`（第四轮视觉重做）——页面缓存和 `_rebuild` 是同一次改动，
缓存没有跟着一起失效。也就是说，这是 `redesign-base` 标签上就存在的回归，
不是删预热带出来的。

**最小改法**：`_rebuild()` 里 `destroy()` 之后加一行 `self._pages.clear()`。
一行，不动别的。

### D2 · 最小窗口下「可用占位符」第三列被裁 —— **P1 已修（三列改两列）**

**现象**：窗口缩到 960×660 时，模板页「可用占位符」卡片里的三列占位符
（`{duration}`/耗时、`{summary}`/回复摘要、`{host}`/主机名）超出卡片右边界，
被裁掉 28–85px。1360px 宽时没有这个问题（`audit` 的响应式检查是绿的）。

**原因**：卡片内容按固定三列排，列宽不随卡片宽度收缩；卡片被压到 640px 时
三列加起来装不下。

**最小改法**：列宽改成按卡片宽度等分，或者窄于阈值时降成两列。属于布局参数，
不是结构问题。

## 附：尺子自身的问题

P0 定的规矩是「不许改检查脚本——失败是产品的错，不是尺子的错」。这条规矩
在这一轮**撞上了两个例外**，都是尺子算不出来，不是判据太严：

修之前 `check_responsive.py` **跑不完**，退出码不可能是 0。实测 `timeout 40` 下
`[A]`、`[B]` 正常打印（`[B]` 全绿），到 `[C]` 就再也不出来了，退出码 124。
`tools/check_responsive.py` 最后一次改动是 `c620992`，也就是说从那之后每次运行
都卡在这里。

**1. `switch_pages` 无限递归。** 174 行：

```python
todo_now = list(keys or ["triggers", "status", "template", "channels"])
```

递归调用传进来的是 `[]`，`[]` 是假值，于是又播种回默认的 4 个页面——链条永不结束。

永远排不空，脚本就卡在 `[C]` 段进不去 `[D]`、`[E]`。
把这一行改成 `list(keys) if keys is not None else [...]` 就能正常跑完 4 次切页。

**2. `block_of` 把「分栏容器」当成了「块」。** 通道页的正文是
「左列表 / 2px 分隔 / 右表单」三栏并排，`block_of` 对三栏里的控件都返回
同一个容器，于是「同一块内自上而下」这条判据要求 y 单调递增——
而「左列走完再走右列」必然往回跳。这条判据对两栏布局**不可能成立**。
块应该是**栏**，不是分栏容器。
